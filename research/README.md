# Part 1. 무엇을 하려는가

## 문제 설정

LLM 추론은 두 단계다.

```
prefill : 프롬프트 전체를 처리해 KV 캐시를 만든다     ← 연산 병목
decode  : 토큰을 하나씩 생성한다                      ← 메모리 대역폭 병목
```

**TTFT**(Time To First Token, 첫 글자가 나오기까지의 시간)는 거의 전부 prefill 이다.
사용자가 체감하는 반응성이고, 프롬프트가 길수록 급격히 나빠진다.

우리 실측(Llama-3-8B Q4_0, Pi5 4코어 단일 노드):

| 프롬프트 | TTFT |
|---|---|
| 447 토큰 | **37.9 초** |
| 1,789 토큰 | **155.4 초** |

2,000 토큰짜리 문서 하나를 넣으면 **2분 반을 기다려야** 첫 글자가 나온다. 실용성이 없다.

## 왜 SBC 클러스터인가

- 프라이버시·오프라인·비용 때문에 온디바이스 추론 수요가 있다
- 단일 SBC 는 메모리도 연산도 부족하다 → 여러 대를 묶는 시도가 많다
- 그런데 **기존 분산 추론 기법은 전부 GPU·고대역폭·초장문을 전제**로 설계됐다
- SBC 클러스터는 **CPU only / 1GbE / 짧은 프롬프트(0.5~4K)** 라는 다른 체제다

## 선행 프로젝트와의 관계

[layer-skip-bypass](https://github.com/inpyu/layer-skip-bypass) (PiPP) 는
**decode** 구간에서 스테이지를 건너뛰어 토큰 생성 지연을 줄였다.
이 프로젝트는 같은 클러스터에서 **prefill** 을 대상으로 한다. 축이 다르다.

## 핵심 질문

> **노드를 늘릴수록 TTFT 가 줄어들게 만들 수 있는가?**

의외로 이게 쉽지 않다. prefill 은 **깊이 방향으로 순차**이기 때문이다.

```
x_{l+1} = x_l + Attn_l(x_l) + FFN_l(x_l)     ← 레이어 32개를 순서대로
```

토큰끼리는 독립이라 병렬이 되지만, 깊이는 안 된다.
그래서 단순히 노드를 늘리면 통신과 대기만 늘고 오히려 느려진다.

# Part 2. distributed-llama 에 무엇이 문제였나

우리는 [distributed-llama](https://github.com/b4rtaz/distributed-llama) 를 포크해 쓴다.
**분산 추론 인프라(TP/PP, 워커 프로토콜)가 이미 있기 때문**이다.

그런데 이 엔진은 **decode 최적화에 맞춰져 있어** prefill 경로에 문제가 많았다.
"알고리즘이 baseline 을 이겼다"고 말하려면 baseline 이 정상이어야 하므로,
이것부터 고쳐야 했다.

> **아래 다섯 가지는 전부 논문 기여가 아니라 baseline 위생이다.**
> 상세는 [06-baseline-status.md](06-baseline-status.md).

## 발견 #1 — 빌드 플래그가 SIMD 명령어를 꺼버림

`Makefile` 이 aarch64 에서 `-march=native -mtune=native` 를 함께 지정했는데,
이 조합은 CPU 기능셋을 기본 armv8-a 로 되돌려 **`__ARM_FEATURE_DOTPROD` 가 사라진다.**

그 결과 `llamafile_sgemm` 의 Q4_0×Q8_0 배치 경로가 통째로 비활성화되고,
prefill 이 **토큰별 matvec 폴백**으로 떨어졌다 — 배치 이득이 0이었다.

```
증상: prefill 496 ms/tok  ≈  decode 525 ms/tok     ← 거의 같으면 이상하다
```

prefill 은 토큰을 묶어 처리하므로 decode 보다 몇 배 빨라야 정상이다.

**수정**: aarch64 에서 `-mcpu=native` 사용 (arch 와 tune 을 동시에 설정).
llama.cpp 도 같은 방식을 쓰고 dotprod 를 컴파일 타임에 검사한다.

**효과**: GEMM 배치 32에서 **3.2~4.0×** (마이크로벤치)

## 발견 #2 — decode 용 attention 커널을 prefill 이 그대로 사용

`multiheadAtt_F32` 의 시그니처는 인자로 **위치 하나**를 받는다.
즉 처음부터 decode(쿼리 1개)용으로 설계됐고, prefill 은 이걸
배치 크기만큼 **반복 호출**했다.

거기에 GQA 에서 `kvMul = 4` 이므로 같은 KV 헤드를 4번씩 다시 읽었다.
결과적으로 KV 캐시가 **(batchSize × kvMul) 번** 스트리밍됐다.

```
S=1789 기준 메모리 트래픽 추정 약 1.7 TB → 약 210초
실측 attention 355.6초 (prefill 의 57%)
```

**수정**: `multiheadAttBatch_F32` 신설
- GQA 그룹화 — 같은 KV 헤드를 공유하는 쿼리 헤드 4개를 함께 처리
- 쿼리 타일링 — `t` 루프를 바깥으로 빼 배치 전체가 KV 한 번 읽기를 공유

**효과**: attention 최대 **8.5×** (355.6 → 41.9초)

> 부수 효과: 이때 attention 을 배치 커널로 분리해 둔 덕에,
> 나중에 블록 병렬을 구현할 때 **블록별 마스크만 추가하면 되는** 구조가 됐다.

## 발견 #3 — 토큰 임베딩이 F32 로 저장됨

`src/llm.cpp:196` 에서 임베딩 테이블을 F32 로 잡는다.

```
128,256 × 4,096 × 4 B = 2.10 GB   (Q4_0 이면 0.30 GB)
모델 파일 6.32 GB vs GGUF Q4_0 4.34 GB
```

임베딩은 룩업이라 **연산 성능에는 영향이 없다.** 그러나 노드당 메모리를
1.8 GB 잠식한다. 블록 병렬/CP 는 **가중치를 복제**하므로 이게 제약이 된다.

**상태**: 미수정. 8 GB 노드까지 쓰려면 필요.

## 발견 #4 — Q4_0 가중치 repack 부재

llama.cpp 는 로드 시점에 Q4_0 을 **SIMD 친화적 레이아웃으로 재배치**한다.
distributed-llama 가 벤더링한 sgemm 에는 이 개념이 아예 없다.

기존 커널은 GEMM 마다 4비트를 풀어야 해서, (i,j,l) 조합당 명령어 11개 중
**6개가 언팩**이었다. 게다가 가중치 언팩을 출력 열마다 반복했다.

```
유효 64 FLOP / 명령어 11개 ≈ 5.8 FLOP/instr
→ 이론 111 GFLOPS,  실측 97~110 GFLOPS   (정확히 일치)
```

**수정**: llama.cpp/ggml(MIT)에서 repack 커널을 이식
- zero-point(−8)를 pack 시점에 XOR 로 흡수 → 런타임 뺄셈 제거
- 출력 행 4개를 인터리브 → 로드 1회가 4행을 커버

`NnBlockQ40` 4개(72 B) = `block_q4_0x4`(72 B) 로 크기가 같아 **in-place 변환**이
가능했고, 추가 메모리가 0이다.

**효과**: 마이크로벤치 105 → **330 GFLOPS (3.1×)**, 실측 prefill **2.0×**

## 발견 #5 — 소켓 재시도의 1 ms 고정 sleep

**분산 측정 전체를 오염시키던 버그.** 단일 노드에서는 드러나지 않는다.

논블로킹 소켓이 `EAGAIN` 을 반환할 때마다 1 ms 를 통째로 잤다.
리눅스 타이머 해상도상 실제로는 1~2 ms 이고, 집합통신 하나에서 재시도가
수십 회 발생하므로 **배리어 1회가 수십 ms 로 부풀었다.**

```
TP 2노드: 배리어 896회에 syncWait 39.3초 = 배리어당 43.9 ms
          그중 회선 시간은 6.9 ms 뿐  →  37 ms 가 sleep
```

**수정**: `poll()` 로 교체. 데이터 도착 즉시 깨어나면서도 커널 대기라
CPU 를 점유하지 않는다 (코어가 4개뿐인 SBC 에서 스핀은 연산 스레드를 뺏는다).

**효과**: TP2 58.3 → **33.6초 (42% 개선)**, 배리어 43.9 → **16.3 ms**

> 이 수정으로 **TP2 가 처음으로 단일 노드를 앞섰다**(1.13×).
> "분산이 단일보다 느리다"는 이전 결론은 알고리즘의 한계가 아니라 이 sleep 이었다.

## 그 밖에 고친 것

| 항목 | 내용 |
|---|---|
| lm_head prefill 낭비 | prefill 은 로짓을 전혀 읽지 않는데 모든 위치에 대해 계산하고 있었다. 마지막 행만 계산하도록 제한 (**4%**) |
| 종료 시 트래픽 요약 무한 출력 | 로그가 14 GB·5.5 GB 까지 자람. 출력 횟수 제한 + 로그 크기 감시 |
| `dllama-fast` 타깃 | 발견 #1 의 잘못된 플래그를 하드코딩하고 있었음 |

## 누적 효과

**단일 노드** (S=447):

| 단계 | prefill | tok/s | llama.cpp 대비 |
|---|---|---|---|
| 원본 | (496 ms/tok) | 2.01 | 12 % |
| + 발견 #1 | 78,150 ms | 5.72 | 35 % |
| + 발견 #2 | 72,938 | 6.13 | 38 % |
| + 발견 #4 | 35,889 | 12.45 | 77 % |
| **+ lm_head** | **32,417** | **13.79** | **85 %** |

**누적 6.9×**. 네 항목 모두 출력이 **byte-for-byte 동일**함을 확인했다.

외부 기준선인 llama.cpp(pp512 16.15 tok/s) 대비 85 % 까지 왔다.
이 대조가 있어야 "우리 baseline 이 원래 느린 것 아니냐"는 질문을 막을 수 있다.

# Part 3. 측정이 알려준 것

baseline 을 고친 뒤 분산 축을 하나씩 측정했다 (S=447, 단일 37.9초 기준).

| 축 | prefill | syncWait | syncXfer | gemm | 단일 대비 |
|---|---|---|---|---|---|
| 단일 노드 | 37,939 | — | — | 33,079 | 1.00× |
| **TP 2노드** | **33,633** | 14,611 | 1,965 | **13,942** | **1.13×** |
| PP 4노드+wave | 39,825 | 23,102 | 829 | — | 0.95× |
| SP 2노드 | 43,620 | 1,785 | 537 | 36,502 | 0.87× |
| SP 4노드 | 47,374 | 8,178 | 1,687 | 32,766 | 0.80× |

## (a) 연산은 잘 나뉜다

gemm 이 prefill 의 **87 %** 이고, TP 에서 33.1 → 13.9초로 떨어졌다.
**분할 자체는 문제가 없다. 남는 문제는 동기뿐이다.**

## (b) 비용은 바이트가 아니라 배리어 수

```
syncWait : syncXfer = 7 : 1
```

통신 시간의 대부분이 **전송이 아니라 대기**다. 배리어 1회가 16.3 ms 이고,
TP 는 레이어당 2회 × 32레이어 = **청크당 64회** 기다린다.

> GPU 문헌은 통신 비용을 `bytes / bandwidth` 로 본다. 그래서 압축·저비트 통신이
> 나온다. **SBC 에서는 그 항이 1.7 % 에 불과하다.** 최적화 방향이 반대다.

## (c) 깊이 축(PP)의 대기는 구조적이다

발견 #5 의 poll 수정이 **축마다 다르게 작용했다.**

```
TP2      42 % 개선   ← 대기가 구현 아티팩트였음
PP4+wave  3 % 개선   ← 대기가 구조적임
```

PP4 는 전송량이 TP2 의 절반 이하인데 대기는 더 크다. 청크가 스테이지를
**순서대로** 통과해야 하기 때문이고, 튜닝으로 줄지 않는다.

## (d) 토큰 축은 아예 구현돼 있지 않다

dllama 의 `--sp-size` 는 **KV 저장만** 시퀀스 방향으로 쪼갠다.
모든 노드가 같은 토큰을 계산한다. **SP2/SP4 의 gemm 이 단일 노드와 동일**한 것이 증거다.
메모리 최적화이지 병렬화가 아니다.

> prefill 에서 **본질적으로 병렬인 축은 토큰 축**인데(레이어 안의 모든 토큰은 서로 독립),
> 그 축으로 연산을 나누는 기능이 없다. **이것이 우리가 만들 것이다.**

## (e) prefill 은 토큰 수에 거의 선형

| 토큰 | prefill | ms/tok |
|---|---|---|
| 96 | 7,224 ms | 75.2 |
| 193 | 15,462 | 80.1 |
| 447 | 36,740 | 82.2 |

토큰이 4.6배 늘어도 ms/tok 은 9 % 만 증가한다.
**따라서 토큰을 N 등분해 노드에 나눠주면 노드당 시간은 대략 1/N 이 된다.**

# Part 4. 제안하는 알고리즘

상세는 [07-design-block-parallel.md](07-design-block-parallel.md).

## 축 ① 토큰 축 블록 병렬

```
S 토큰을 N 블록으로 나눠 노드당 1블록, 레이어별 동시 계산
블록 간 attention 은 생략(근사), anchor 로 손실 완화
KV 는 토큰 구간별로 샤딩 유지 → decode 도 같은 축이면 통합 불필요
```

attention 이 O(S²) 이므로 블록으로 쪼개면 **총 연산량 자체가 줄어든다**
(447토큰 단일 2,770 ms vs 4블록×112토큰 약 880 ms). TP/PP 에는 없는 이득이다.

**SBC 특유의 설계 결정**: [Star Attention](https://arxiv.org/pdf/2411.17116) 은
anchor 를 모든 노드가 **중복 계산**해 연산이 2배가 된다. 우리는 **KV 를 브로드캐스트**한다.

```
재계산      : 노드당 +9.5초
브로드캐스트: 32 MB 전송 0.3초 + 배리어 32회×16.3 ms ≈ 0.8초   → 12배 차이
```

측정된 배리어 비용으로 직접 계산되므로 GPU 와 비교할 필요가 없다.

## 축 ② 깊이 분해 — **기각됨**

TTFT 의 산출물은 **KV 캐시 + 마지막 토큰 로짓**뿐이다. 그런데 토큰 0..S−2 의
상위 레이어 residual stream 은 **오직 그 레이어의 KV 를 만들기 위해서만** 존재하고,
KV 는 단순 선형 사영이다(레이어 비용의 3.9 %).

$$
K_l = A_l\,\varphi(x_k),\qquad V_l = A^V_l\,\varphi(x_k)\qquad (l>k)
$$

`A_l` 은 소량 캘리브레이션으로 **최소제곱**을 풀어 얻는다 — 학습이 아니라 닫힌 형태 해다.

**검증 결과 기각**. 캘리브레이션 12,000행으로 적합한 결과
K 평균 0.126 / **V 평균 0.323** 으로 기준(0.10)을 넘겼다.
온전성 검사(`l=k` 자기적합 0.00079)는 통과했으므로 데이터 문제가 아니다.

실패 이유가 명확하다: `x_l[t]` 는 `x_k[t]` 하나가 아니라 **`x_k[0..t]` 전체**에
의존한다(attention 이 토큰을 섞으므로). 우리가 적합한 **토큰별 사상**에는
다른 토큰의 정보가 구조적으로 빠져 있다. `k` 를 올려도 해결되지 않는다
(레이어 17에서 이미 K 0.092 / V 0.306).

> SwiftKV 가 distillation 을 요구하는 이유가 이것이다. GPU 없이는 불가능하다.
> **이 부정 결과 자체는 보고할 가치가 있다** — SwiftKV 계열을 엣지에 적용하려는
> 후속 연구가 알아야 할 사실이다.

→ 상세: [07 §4.9](07-design-block-parallel.md)

## SwiftKV 와의 차별 — CPU 가 강제하는 설계

| # | 내용 | 근거 |
|---|---|---|
| ① | **레이어 공유 저랭크 기저** `A_l ≈ U diag(d_l) V` | dense 는 상위 16레이어에 134 M 파라미터 = 청크마다 75 MB 스트리밍. 공유 기저는 1.58 M = 0.9 MB → **83×** |
| ② | 양자화 인지 최소제곱 | CPU 추론은 전부 Q4_0/Q8_0 |
| ③ | 클러스터 자체 캘리브레이션 | 최소제곱은 닫힌 형태 + 레이어별 독립 → **GPU 불필요** (SwiftKV 는 distillation 필수) |

①이 핵심이다. GPU 는 메모리 대역폭이 넉넉해 dense 로도 충분하지만,
**SBC 는 대역폭이 병목이라 이 절감이 결정적**이다.

## 노드 수에 따른 스케일링

실측 3점으로 적합: `T(B) ≈ 73.35 B + 0.0198 B²` (B = 노드당 토큰 수).
이차항이 attention 이라 **블록을 쪼개면 초선형으로 빨라진다.**

| N | 연산 | 통신 | 합계 (S=447) | 단일 대비 |
|---|---|---|---|---|
| 4 | 8,444 | 1,830 | 10,274 ms | 3.58× |
| 8 | 4,160 | 1,700 | 5,860 | 6.27× |
| 14 | 2,362 | 1,644 | 4,006 | **9.17×** |

**두 개의 벽**이 있다.

```
① 블록 크기 하한: S/N ≥ 32  →  N ≤ S/32  (S=447 이면 14)
② 직렬 상수 항  : KV 수집 1.05초 + anchor 배리어 0.52초
```

미는 방법은 [07 §4.96](07-design-block-parallel.md):
**(a) KV 수집 파이프라인화**(1.05초 → 0, Phase A 에 포함),
(b) anchor 배리어 묶기(0.52 → 0.13초), (c) 하이브리드 2D 로 N 상한 돌파.
(a)+(b) 적용 시 N=14 에서 **14.6×** 로 이상값 15.6× 에 근접한다.

**그리고 두 벽 모두 S 가 커지면 완화된다** — TTFT 가 실제로 문제인
긴 프롬프트 구간에서 가장 잘 확장된다.

해소책 두 가지를 [07](07-design-block-parallel.md) §4.5 에 정리했다.
- 하이브리드 2D (블록 × TP) — 남는 노드를 다른 축에
- **GEMM 배치와 블록 경계 분리** — FFN/projection 은 토큰 간 의존이 없으므로
  여러 블록을 한 GEMM 으로 묶고 attention 만 블록별로 한다

# Part 5. 선행연구

## 우리가 서 있는 자리

기존 연구는 대부분 **초장문(128 K) · 고대역폭 · GPU** 전제다.
우리는 **짧은 프롬프트(0.5~4 K) · 1GbE · CPU only** 라는 다른 체제이고,
그 체제에서는 설계 선택이 달라진다.

## 카테고리별

### 병렬 컨텍스트 인코딩 — 우리 축 ①의 조상

| 연구 | 요지 | 우리와의 차이 |
|---|---|---|
| [Star Attention](https://arxiv.org/pdf/2411.17116) (ICML'25) | 블록별 로컬 attention(통신 0) + 쿼리 단계 단일 merge. 최대 11×, 정확도 97~100 % | **S=128 K 전제.** 호스트당 여러 블록이라 anchor 를 amortize 할 수 있다. 우리는 노드당 1블록이라 anchor 가 2× 연산으로 남는다 → **브로드캐스트로 해결** |
| [APE](https://arxiv.org/pdf/2502.05431) (ICLR'25) | 병렬 인코딩 KV 의 분포 정렬(shared prefix, attention temperature) | 정확도 회복 기법으로 차용 가능 |
| [Pulsar Attention](https://arxiv.org/html/2607.20457) | anchor 를 통계 요약으로 대체 | **정확도 각도로 충돌.** 우리는 비용 각도로만 다룬다 |

### KV 생성 연산 축소 — 우리 축 ②의 조상

| [KVSharer](https://arxiv.org/pdf/2410.18517) · [CommonKV](https://arxiv.org/abs/2508.16134) | 레이어 간 KV 유사성을 이용한 공유·압축 | 우리 "공유 기저" 가설의 방증 |
