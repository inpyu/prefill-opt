# 측정 방법론 — 왜 이렇게까지 하는가

이 연구에서 **가장 자주 틀린 것은 가설이 아니라 측정**이었다.
아래는 그때마다 도입한 규율이고, 각각 실제 사고에서 나왔다.

## 1. 정확성 게이트 (`prefill_bench/verify.sh`)

```
bash verify.sh ref                     # 단일 노드 기준 생성
bash verify.sh check <이름> [인자...]   # 구성 검사
```

세 가지를 본다:

| 검사 | 근거 |
|---|---|
| 고유 토큰 3종 미만이면 실패 | 깨진 구성은 `!!!!` 반복을 낸다. 가장 먼저 걸린다 |
| 앞 8토큰 일치 | 부동소수점 재결합으로 뒤쪽 argmax 는 갈릴 수 있다 |
| 배치 perplexity 편차 ≤ 1.0 % | argmax 뒤집힘에 휘둘리지 않는 스칼라 |

**도입 이유**: SP 축을 검증 없이 쓰다가 깨진 채로 성능만 재 왔다.
그 수치(SP2 43,620 / SP4 47,374 ms)는 무엇을 잰 것인지 알 수 없어 폐기했다.

**게이트가 실제로 잡은 것 (4건)**
1. SP2 가 `!!!!` 만 생성 — 사전 결함
2. 진짜 TP4 가 편차 653,245 % — 사전 결함
3. `--pp-layers` 불균등 분할에서 가중치가 엉뚱한 노드로 (편차 25.9 %)
4. (아래) 가지치기에서 지표 자체가 무효

> **게이트가 없었다면 3번은 "빨라졌다"고 보고됐을 것이다.**

### 게이트도 두 번 틀렸다

- **임계값**: 0.5 % 로 뒀더니 정상 구성인 TP2 가 0.740 % 로 탈락.
  **게이트가 정상 구성을 떨어뜨리면 게이트가 틀린 것이다.** 정상 구성으로 보정했다.
- **프롬프트 길이**: 13토큰으로 재니 TP4 가 5.35 % 로 탈락. 예측 12개만 평균내면
  지표가 불안정하다. perplexity 용 프롬프트를 128토큰으로 분리하니 0.707 % 로 안정.

### 지표가 조용히 무효가 될 수 있다

토큰 가지치기를 켜자 `keep=0.9` 인데 perplexity 가 38 → 18,570(486배)로 나왔다.
**생성은 기준과 완전히 동일했다.** 원인은 압축하면 `logitsPipe` 의 행 `i` 가 더 이상
토큰 `i` 가 아닌데 지표가 그 대응을 전제한다는 것.

> 이 지표를 믿었다면 "가지치기가 품질을 파괴한다"고 결론 내리고 방향을 버렸을 것이다.
> **측정 대상이 바뀌면 지표도 다시 검증해야 한다.**

대안: `--ppl-eval-tail N` — 앞부분을 배치 prefill 로 처리한 뒤 마지막 N 토큰을
`batchSize=1` 로 평가한다. 행↔토큰 대응 문제가 없다.

## 2. 교차 실행 (`prefill_bench/run_ab.sh`)

설정을 **번갈아** 실행한다. 순차로 돌리면 뒤에 오는 쪽이 일관되게 불리하다.

**도입 이유**: 융합 attention 을 순차 비교했다가 "1.3 % 손해"라는 반대 결론을 냈다.
커널과 무관한 `gemm`(+558)과 `ffn`(+517)까지 같이 늘어난 것이 드리프트의 증거였다.
번갈아 4라운드 돌리자 **4/4 라운드 모두 융합이 빨랐다.**

`run_one.sh` 의 워밍업·반복 중앙값은 **한 설정 안의** 편차만 잡는다.
설정 간 순서 효과는 못 막는다.

## 3. 워밍업 제외

5회 측정에서 첫 실행만 일관되게 이상치였다 (49,992 / 34,077 / 34,824 / 34,418 / 32,414).
시작 온도는 rep1 이 오히려 평범했으므로 열이 아니라 **콜드 스타트**다.
rep1 을 버리면 편차가 51 % → 7 % 로 떨어진다.

## 4. 바이너리 md5 대조

매 실행 전 root 와 워커의 md5 를 대조한다.

**도입 이유**: 재배포 전 바이너리로 스윕을 돌려 같은 에러를 다시 보고, 원인을
코드에서 찾다가 한 시간을 날렸다. 이후에도 가드가 두 번 더 잡았다.

관련: Makefile 이 헤더 의존성을 추적하지 않아 **`make` 가 rc=0 인데 아무것도
재컴파일하지 않는** 경우가 있었다 (`-MMD -MP` 로 수정).

## 5. OOM 가드 (`run_one.sh`)

동시 실행 금지 / 가용 메모리 확인 / 프롬프트에 맞춘 `--max-seq-len` / 로그 크기 상한.
각각 실제 OOM 또는 디스크 고갈(14 GB 로그)에서 나왔다.

## 6. 노드별 계측

`syncWait` 이 크다고 통신 문제인 것이 아니다. **실제 전송(`syncXfer`)은 언제나
1초 미만**이었고, 대기는 늘 다른 노드가 무언가에 막혀 있었기 때문이다.

워커 루프에 prefill 스테이지 계측(recv / forward / send)을 넣자 병목이 즉시 드러났다:

```
node=1  recv=0.1ms  fwd=247ms  send=0.3ms
node=2  recv=0.2ms  fwd=335ms  send=0.3ms
node=3  recv=22ms   fwd=304ms  send=5667ms   <- 여기
```

`recv ≈ 0` 은 파이프라인이 **이미 겹치고 있다**는 뜻이었다. 그전까지 "겹침이
안 된다"고 보고 소켓 버퍼를 고쳤는데 틀린 방향이었다.

> 기존 `recordStageTiming` 은 decode + `batchSize==1` 에서만 기록해 prefill 이
> 누락돼 있었다. **계측이 있다고 계측되고 있는 것이 아니다.**

## 7. 원인 귀속을 위한 대조 실험

- **워커 순서 치환**: 느림이 기계를 따라가는지 스테이지 위치를 따라가는지 갈랐다
  → 기계 요인 + 위치 요인, **둘 다 정적**
- **구버전 리비전 빌드**: SP 결함이 사전 결함인지 오늘 회귀인지 갈랐다 → 사전 결함
- **스위치로 A/B**: `--attn-fused 0`, `DLLAMA_NO_BATCHED_SYNC=1`, `DLLAMA_SP_NOSHARD=1`
  — 새 코드를 끄고 같은 실험을 돌려 내 변경 탓인지 가렸다

## 8. 요약: 이 프로젝트에서 얻은 규칙

1. 성능을 재기 전에 **정확성을 게이트로 통과**시킨다
2. 게이트가 정상 구성을 떨어뜨리면 **게이트를 의심**한다
3. 측정 대상이 바뀌면 **지표를 다시 검증**한다
4. 설정 간 비교는 **번갈아** 실행한다
5. 큰 대기는 통신 문제가 아닐 수 있다 — **노드별로 계측**한다
6. 새 코드를 끄는 스위치를 남겨 **내 탓인지 가린다**
7. `make` 가 성공했다고 **재컴파일된 것이 아니다**
