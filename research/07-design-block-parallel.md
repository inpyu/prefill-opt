# 설계: 토큰 축 블록 병렬 prefill (SBC 클러스터)

**목표: TTFT 를 단일 노드 대비 3배 이상 단축한다.**

이 문서는 [06-baseline-status.md](06-baseline-status.md) 의 baseline 위에서
**논문 기여가 될 알고리즘**을 설계한다. 여기부터는 baseline 위생이 아니다.

---

## 1. 측정이 정한 출발점

전부 이 클러스터에서 직접 잰 값이다 (llama3-8b_q40, Pi5 4코어, 1GbE, S=447).

| 구성 | prefill | syncWait | syncXfer | gemm | 단일 대비 |
|---|---|---|---|---|---|
| 단일 노드 | 37,939 ms | — | — | **33,079** | 1.00× |
| TP 2노드 | 33,633 | 14,611 | 1,965 | **13,942** | 1.13× |
| PP 4노드+wave | 39,825 | 23,102 | 829 | — | 0.95× |
| SP 2노드 | 43,620 | 1,785 | 537 | **36,502** | 0.87× |
| SP 4노드 | 47,374 | 8,178 | 1,687 | **32,766** | 0.80× |

### 여기서 읽어야 할 세 가지

**(a) 연산이 전체의 87 % 이고, 나누면 정확히 나뉜다.**
gemm 33.1초는 prefill 37.9초의 87 %. TP2 에서 13.9초로 떨어졌다(2.37×, 이상값 2× 초과는
캐시 효과). **즉 연산 분할은 잘 되고, 남는 문제는 동기뿐이다.**

**(b) 깊이 축(PP)의 대기는 구조적이라 튜닝으로 안 줄어든다.**
[발견 #5](06-baseline-status.md#7-알려진-기존-버그-distributed-llama-원본)의 poll 수정으로
TP2 는 42 % 빨라졌는데 PP4 는 3 % 밖에 안 줄었다. PP4 는 전송량이 TP2 의 절반 이하인데
대기는 더 크다(23.1 vs 14.6초). 청크가 스테이지를 **순서대로** 통과해야 하기 때문이다.

**(c) dllama 의 `--sp-size` 는 토큰 축 병렬이 아니다.**
`sliceKvCache()` 의 `localSeqStart/localSeqLen` 은 **KV 저장을 시퀀스 방향으로 쪼갤 뿐**,
모든 노드가 같은 토큰을 계산한다. 측정이 이를 확인한다 — SP2/SP4 의 gemm 이
단일 노드와 동일(36.5 / 32.8초 vs 33.1초)하다. 메모리 최적화이지 병렬화가 아니다.

> **prefill 에서 본질적으로 병렬인 축은 토큰 축인데(레이어 안의 모든 토큰은 서로 독립),
> 그 축으로 연산을 나누는 기능이 없다.** 이것이 우리가 만들 것이다.

### (d) prefill 은 토큰 수에 거의 선형이다 — 블록 병렬의 직접 근거

단일 노드에서 프롬프트 길이만 바꿔 측정:

| 토큰 | prefill | gemm | attn | ms/tok |
|---|---|---|---|---|
| 96 | 7,224 ms | 6,666 | 161 | **75.2** |
| 193 | 15,462 | 13,765 | 887 | 80.1 |
| 447 | 36,740 | 32,298 | 2,770 | **82.2** |

토큰이 4.6배 늘어도 ms/tok 은 9 % 만 증가한다. 그 증가분이 O(S²) attention 항이다.
**따라서 토큰을 N 등분해 노드에 나눠주면 노드당 시간은 대략 1/N 이 된다.**

96 토큰에서도 75.2 ms/tok 으로 효율이 유지된다 — 블록이 작아져도 고정 오버헤드는 크지 않다.

### 이론 상한

```
TTFT_ideal ≈ gemm/N + attention + merge
N=4 →  33.1/4 + α ≈ 9.5초   (3.99×)
N=8 →  33.1/8 + α ≈ 5.1초   (7.4×)
```

**attention 은 N 배보다 더 줄어든다.** O(S²) 이므로 블록으로 쪼개면 총 연산량 자체가 감소한다:

| | 단일 447토큰 | 4블록 × 112토큰 |
|---|---|---|
| attention 총합 | 2,770 ms | 4 × ~220 = **880 ms** (3.1× 감소) |

TP/PP 는 attention 연산량이 그대로다. **블록 병렬만 이 이득이 있다.**

## 2. "KV 를 통합해야 하나" — 아니다, 조건부로

각 노드가 자기 토큰 구간의 KV 만 만들면, 그걸 하나로 합쳐야 하는 것 아닌가?

**decode 를 같은 축으로 돌리면 합칠 필요가 없다.** Context Parallel 의 표준 결과다.

decode 시 각 노드가 **자기 KV 구간에 대해 partial attention 과 log-sum-exp** 를 계산하고,
LSE 를 작은 all-reduce 로 병합하면 전체 attention 과 **수학적으로 동일**하다.
교환량은 레이어당 헤드당 `(head_dim + 1)` float 로 무시할 수준이다.
근거: [vLLM CP RFC](https://github.com/vllm-project/vllm/issues/26133),
[Meta Context Parallelism](https://arxiv.org/pdf/2411.01783) 의 pass-Q,
[Tree Attention](https://arxiv.org/html/2408.04093v2).

| decode 구성 | KV 통합 비용 |
|---|---|
| **토큰 축 (prefill 과 동일)** | **0** |
| 한 노드로 수집 | S=447 → 117 MB ≈ 1초 / S=2048 → 537 MB ≈ 4.8초 |
| TP (현행 dllama) | 헤드 축으로 재분배 → all-to-all, 가장 비쌈 |

> **설계 제약: prefill 축 = decode 축.**
> 현행 dllama decode 는 TP 이므로, 최종적으로는 decode 도 토큰 축으로 바꿔야 한다.
> 다만 v1 에서는 수집(gather)으로 우회한다 — §5 참조.

## 3. 알고리즘: Anchor-shared block-parallel prefill

```
입력 S 토큰을 N 블록으로 분할, 노드당 1블록

  노드 0: 블록 0 (= anchor)  ┐
  노드 1: 블록 1             ├─ 레이어별로 동시 계산
  노드 2: 블록 2             │
  노드 3: 블록 3             ┘

각 레이어 l 에서:
  노드 0   : 자기 블록 계산 → layer-l anchor KV 를 브로드캐스트
  노드 i>0 : [anchor KV ⊕ 자기 블록] 에만 attention
             그 외 노드 간 통신 없음

종료 후:
  KV 는 토큰 구간별로 샤딩된 채 유지
  쿼리 토큰만 분산 softmax(LSE merge)로 단일 병합
```

블록 간 attention 을 생략하므로 **근사**다. anchor 가 그 손실을 완화한다
([Star Attention](https://arxiv.org/pdf/2411.17116) 의 핵심 아이디어).

### 연산량

| 항목 | 단일 노드 | 블록 병렬 (노드당) |
|---|---|---|
| gemm | O(S·h²) | **O(S/N·h²)** |
| attention | O(S²·h) | **O((S/N + A)²·h)** |
| 통신 | 0 | anchor KV 브로드캐스트만 |

attention 은 N² 로 줄어든다(총합 기준 S²/N). **연산량 자체가 TP/CP 보다 적다.**

---

## 4. 핵심 설계 결정: anchor 를 재계산하지 말고 브로드캐스트한다

Star Attention 은 anchor 블록을 **모든 노드가 중복 계산**한다. 노드당 처리 토큰이
`S/N + A` 가 되고, `A = S/N` 이면 연산이 2배 → speedup 이 N → N/2 로 반토막 난다.

우리 클러스터 실측값으로 두 선택지를 비교하면 (N=4, S=447, L=32):

| 방식 | 비용 |
|---|---|
| anchor 재계산 | 노드당 +9.5초 (연산 2배) |
| **anchor KV 브로드캐스트** | 전송 32 MB ≈ 0.3초 + 배리어 32회 × **16.3 ms** ≈ **0.8초** |

**약 12배 차이.** 배리어 비용 16.3 ms 는 [발견 #5](06-baseline-status.md) 수정 후
TP2 에서 직접 측정한 값이다(syncWait 14,611 ms ÷ 896 배리어).

> 이전 초안에서 이를 "GPU 대비 반전"으로 서술했다가 근거 부족으로 철회했다.
> 지금은 **우리 하드웨어의 측정값만으로** 성립한다. GPU 와 비교할 필요가 없다.

### 브로드캐스트의 의존성 처리

노드 0 이 레이어 l 의 anchor KV 를 만들어야 노드 i>0 이 레이어 l 을 계산할 수 있다.
→ **노드 0 을 한 레이어 앞서 달리게 한다.** 스큐는 1 레이어(전체의 1/L = 3 %)뿐이고,
전송은 단방향이라 연산 뒤로 숨길 수 있다.

anchor 는 어차피 블록 0 이므로 노드 0 이 자기 일을 하면서 부산물로 만든다.

## 4.5. 설계 제약: 블록이 너무 작아지면 안 된다

[05-kvcache-ttft-guide.md](05-kvcache-ttft-guide.md) B-3 의 machine balance 규칙에서,
Pi5 는 GEMM 배치가 32 이상이어야 memory-bound 를 벗어난다(실측 포화점과 일치).

```
블록 크기 = S / N ≥ 32   →   N ≤ S / 32

S=447  → N ≤ 14   (8노드까지 안전)
S=224  → N ≤ 7
S=112  → N ≤ 3    ← 8노드 클러스터에서 5대가 논다
```

> **프롬프트 길이가 병렬화 가능한 노드 수를 제한한다.**
> 짧은 프롬프트에서 노드를 늘려도 이득이 없고, 오히려 GEMM 효율이 떨어져 손해다.

### 해소책 1 — 하이브리드 2D 분할 (블록 × TP)

남는 노드를 **다른 축**에 쓴다. `N = N_block × N_tp` 로 인수분해한다.

```
8노드, S=224 인 경우
  블록만:        N_block=8 → 블록당 28토큰  ✗ (임계 미만)
  하이브리드:    N_block=4 × N_tp=2 → 블록당 56토큰 ✓
                 블록 안에서는 TP 로 GEMM 을 다시 절반
```

TP 는 배리어가 많지만(레이어당 2회), **2노드 그룹 안의 all-reduce 는 전체 all-reduce 보다
훨씬 싸다** — 참여 노드가 적고 데이터도 1/N_block 이다.

이건 표준적인 접근이다. [Unified Sequence Parallelism](https://arxiv.org/html/2405.07719v3) 은
Megatron-SP 와 Ulysses-SP 를 입력 길이에 따라 동적으로 고르고,
[CloudMatrix384](https://arxiv.org/pdf/2506.12708) 는 시퀀스 길이 편차로 생기는 유휴를
지적한다. **우리 기여는 기법 자체가 아니라, SBC 체제의 제약(배치 하한 32, 배리어 16.3 ms)
아래에서 인수분해를 고르는 규칙이다.**

### 해소책 2 — GEMM 배치와 블록 경계를 분리한다

더 근본적인 방법이 있다. **FFN 과 projection 은 토큰 간 의존이 전혀 없다.**
블록 경계는 오직 attention 에만 의미가 있다.

```
한 노드가 블록 2개(각 16토큰)를 맡는 경우
  FFN/projection : 32토큰을 한 GEMM 으로   ← 배치 하한 충족
  attention      : 블록별로 따로            ← 정확도 의미 유지
```

즉 **"노드당 토큰 수 ≥ 32"** 만 지키면 되고, **"블록당 토큰 수"** 는 자유로워진다.
블록을 잘게 쪼개도 GEMM 효율을 잃지 않으므로, 정확도(블록 수)와 효율(배치)을
독립적으로 조절할 수 있다.

이 분리는 우리 구현에서 자연스럽다 — 이미 [발견 #2](03-attention-batching.md) 에서
attention 을 배치 커널로 분리해 두었고, 거기에 블록별 마스크만 추가하면 된다.

> 다만 Phase A 에서는 노드당 블록 1개로 단순화한다. 해소책 2 는 Phase B 이후,
> 노드 수가 프롬프트 길이를 초과하는 구성에서 필요해질 때 적용한다.

## 4.9. 깊이 분해(축 ②) — **기각**

`K_l = A_l φ(x_k)` 형태의 깊이 분해를 검증했고, **학습 없이는 불가능**하다는 결론이다.

### 검증 조건

캘리브레이션 12,000행(미지수 4,096의 2.9배), float64, 홀드아웃 20 %.
**온전성 검사 통과**: `l = k` 자기적합 rel.err = **0.00079**
(`K_k = W_k^k φ(x_k)` 이므로 정의상 0에 수렴해야 하며, 통과했으므로 아래 수치는 유효하다).

### 결과 (k = 16)

| 레이어 | K rel.err | V rel.err |
|---|---|---|
| 16 (자기적합) | 0.0008 | 0.0029 |
| **17** | **0.0920** | **0.3061** |
| 24 | 0.1358 | 0.3459 |
| 31 | 0.1331 | 0.2811 |
| **평균** | **0.126** | **0.323** |

K 는 경계선(기준 0.10 초과), **V 는 명백히 부족**하다.

### 왜 실패했는지

**오차가 레이어 17에서 이미 0.092 / 0.306 으로 뛰고 그 뒤로는 완만하다.**
"멀어져서 나빠지는" 것이 아니라 **한 레이어만 건너뛰어도 안 되는** 구조다.
따라서 `k` 를 올려도 해결되지 않는다.

이유는 수식에 있다.

$$
x_{l}[t] = x_k[t] + \sum_{j=k}^{l-1}\big(\underbrace{\text{Attn}_j(x_j[0..t])}_{\text{다른 토큰에 의존}} + \text{FFN}_j(x_j[t])\big)
$$

`x_l[t]` 는 `x_k[t]` 하나가 아니라 **`x_k[0..t]` 전체**에 의존한다. Attention 이
토큰들을 섞기 때문이다. 그런데 우리가 적합한 것은 **토큰별 사상**
`φ(x_k[t]) → K_l[t]` 이라, 다른 토큰의 정보가 **구조적으로 빠져 있다.**

> SwiftKV 가 distillation 을 요구하는 이유가 이것이다 — 학습으로 **모델 자체를 바꿔**
> 상위 레이어 KV 가 `x_k` 만으로 예측 가능해지도록 만든다.
> 사후 적합만으로는 원리적으로 불가능하다.

공유 저랭크 기저도 함께 무의미해졌다(rank 256 에너지 0.629, dense 대비 1.34× 악화).

### 논문에서의 취급

**이 부정 결과 자체가 보고할 가치가 있다.** SwiftKV 계열을 GPU 없는 환경에
적용하려는 후속 연구가 반드시 알아야 하는 사실이고, 근거(attention 이 토큰 간
정보를 섞으므로 토큰별 사상으로는 복원 불가)가 명확하다.

→ **축 ①(토큰 축)만 남는다.** 이하 설계는 축 ① 단독을 전제로 한다.

## 4.95. 노드 수에 따른 스케일링 — 실측 기반 모델

측정 3점으로 노드당 시간을 적합했다 (B = 노드당 토큰 수).

| 토큰 | 실측 prefill |
|---|---|
| 96 | 7,224 ms |
| 193 | 15,462 |
| 447 | 36,740 |

$$
T(B) \;\approx\; 73.35\,B \;+\; 0.0198\,B^2 \quad[\text{ms}]
$$

선형항은 GEMM(FFN·projection), 이차항은 attention 이다. 193토큰 예측 14,894 vs
실측 15,462 (오차 3.7 %)로 측정 구간 내에서 잘 맞는다.

### 이상적인 경우 (통신 0)

`B = S/N` 을 넣으면, **이차항 덕분에 초선형으로 빨라진다.**

| N | T (S=447) | 단일 대비 |
|---|---|---|
| 1 | 36,742 ms | 1.00× |
| 2 | 17,383 | 2.11× |
| 4 | 8,444 | **4.35×** |
| 8 | 4,160 | **8.83×** |
| 14 | 2,362 | **15.6×** |

attention 이 O(S²) 이므로 블록을 쪼개면 **총 연산량 자체가 줄어드는** 효과다.
TP/PP 에는 없다.

### 실제 (통신 포함)

두 개의 **N 에 무관한 상수 항**이 붙는다.

| 항목 | 비용 | N 의존성 |
|---|---|---|
| anchor 배리어 | 32회 × 16.3 ms = **0.52초** | **상수** |
| anchor 전송 | 29 MB × (4/N) / 1GbE | 1/N |
| **KV 수집 (Phase A)** | 117 MB / 1GbE = **1.05초** | **상수** (전체 KV 는 고정) |

| N | 연산 | 통신 | 합계 | 단일 대비 |
|---|---|---|---|---|
| 4 | 8,444 | 1,830 | 10,274 ms | 3.58× |
| 8 | 4,160 | 1,700 | 5,860 | 6.27× |
| 14 | 2,362 | 1,644 | 4,006 | **9.17×** |

**노드를 늘릴수록 계속 빨라지지만, 상수 항이 점점 지배한다.**
N=14 에서 통신이 41 % 다. 이것이 Amdahl 한계이고, 무한대로 가면 speedup 이
36.74/1.57 = **23× 에서 포화**한다.

### 두 개의 벽

```
① 블록 크기 하한:  S/N ≥ 32   →  N ≤ S/32
                   S=447 이면 N ≤ 14

② 직렬 상수 항:    KV 수집 1.05초 + anchor 배리어 0.52초 = 1.57초
```

**두 벽을 어떻게 미는지가 §4.96 이다.**

## 4.96. 스케일링을 개선하는 방법

### (a) KV 수집을 파이프라인화 — 1.05초 → 거의 0

가장 큰 상수 항이고, 가장 쉽게 없앨 수 있다.

각 노드는 레이어 l 의 KV 를 계산한 **즉시** root 로 흘려보내고 레이어 l+1 을 계속한다.
전체 전송(1.05초)이 연산(8.4초) 뒤에 숨는다. 마지막 레이어의 KV 전송만 남는다.

```
현재 : [연산 8.4초 전부] → [수집 1.05초]
개선 : [연산 8.4초] 과 [수집] 을 겹침 → 꼬리 0.03초만 노출
```

레이어당 전송량은 117 MB / 32 = 3.7 MB 로, 레이어 연산 시간(263 ms)에 충분히 묻힌다.

### (b) anchor 배리어를 줄인다 — 0.52초 → 0.13초

현재 레이어마다 1회, 총 32회 동기한다. **여러 레이어분을 묶어 한 번에 보내면**
배리어가 줄어든다. 대신 노드 0 이 그만큼 더 앞서 달려야 한다.

| 묶는 레이어 수 | 배리어 | 비용 | 노드 0 스큐 |
|---|---|---|---|
| 1 (현재) | 32 | 0.52초 | 3 % |
| 4 | 8 | **0.13초** | 12.5 % |
| 8 | 4 | 0.07초 | 25 % |

4레이어 묶음이 균형점으로 보인다. 스큐는 노드 0 만 부담하므로,
**노드 0 에 더 작은 블록을 주어** 상쇄할 수 있다(불균등 블록 분할).

### (c) 블록 크기 하한을 넘어서기 — 하이브리드 2D

`N = N_block × N_tp` 로 인수분해한다.

```
S=447, 노드 28대
  블록만    : 28블록 × 16토큰  ✗ (하한 32 미만)
  하이브리드: 14블록 × TP2      ✓ (블록당 32토큰, 블록 안에서 TP 로 재분할)
```

TP 는 배리어가 많지만(레이어당 2회), **2노드 그룹 안의 all-reduce 는 참여 노드도
적고 데이터도 1/N_block 이라 훨씬 싸다.** 실제 비용은 측정이 필요하다.

### (d) 긴 프롬프트일수록 유리하다 — 이것이 핵심 성질

두 벽 모두 **S 가 커지면 완화된다.**

| S | N 상한 (S/32) | KV 수집(상수) | 연산(N=상한) |
|---|---|---|---|
| 447 | 14 | 1.05초 | 2.4초 |
| 1,789 | 55 | 4.2초 | 9.6초 |
| 4,096 | 128 | 9.6초 | 22초 |

**TTFT 가 실제로 문제가 되는 것은 긴 프롬프트일 때**이고, 바로 그 구간에서
이 방법이 가장 잘 확장된다. (a)의 파이프라인화를 적용하면 KV 수집 상수도 사라진다.

### 정리

| 개선 | 효과 | 난이도 |
|---|---|---|
| **(a) KV 수집 파이프라인화** | 상수 1.05초 제거 | 낮음 — Phase A 에 포함할 것 |
| (b) anchor 배리어 묶기 | 0.52 → 0.13초 | 낮음 — Phase B |
| (c) 하이브리드 2D | N 상한 돌파 | 중간 — Phase B 이후 |
| Phase C (토큰 축 decode) | 수집 자체가 불필요 | 높음 |

(a)+(b) 적용 시 N=14 에서 **2,362 + 160 ≈ 2,520 ms → 14.6×**.
이상값 15.6× 에 근접한다.

## 5. 구현 계획 (dllama 기준)

### Phase A — 블록 병렬 prefill + KV 수집 (v1 프로토타입)

> §4.96(a) 의 **KV 수집 파이프라인화를 Phase A 에 포함한다.**
> 상수 1.05초는 N 이 커질수록 지배적이 되므로 나중에 붙이면 측정을 다시 해야 한다.

decode 를 건드리지 않고 prefill 만 바꾼다. **TTFT 이득을 먼저 확인하는 것이 목적.**

| # | 작업 | 비고 |
|---|---|---|
| A-1 | 새 토폴로지 모드 `--block-parallel N` | 가중치를 **복제**한다(슬라이스 아님). 노드당 6.32 GB → 16 GB 노드 4대 필요 |
| A-2 | root 가 토큰 구간을 노드에 배정 | `controlPacket` 에 blockStart/blockLen 추가 |
| A-3 | 각 노드가 자기 구간을 position offset 과 함께 prefill | 기존 `setPosition`/`setBatchSize` 재사용 |
| A-4 | anchor 없이 먼저 동작시킨다 | 정확도는 나쁘지만 **속도 상한을 먼저 잰다** |
| A-5 | prefill 후 각 노드가 자기 KV 를 root 로 전송 | S=447 → 117 MB ≈ 1초 |
| A-6 | root 가 기존 방식으로 decode | 변경 없음 |

**예상 TTFT**: `33.1/4 + attention + 1.0 ≈ 10초` → **3.8×**

A-4 가 중요하다. anchor 를 붙이기 전에 "토큰 축이 실제로 gemm 을 1/N 로 줄이는가"를
먼저 확인해야 한다. 여기서 안 나오면 나머지 설계가 무의미하다.

### Phase B — anchor 도입 및 정확도 회복

| # | 작업 |
|---|---|
| B-1 | anchor KV 브로드캐스트 (`SYNC_ANCHOR_KV` 신설, 노드 0 → 나머지) |
| B-2 | 노드 0 을 한 레이어 앞서 실행하는 스큐 스케줄 |
| B-3 | anchor 크기 A 스윕 → 정확도-속도 파레토 |
| B-4 | 비교군: anchor 재계산 방식(Star 원본) 도 구현해 §4 의 12배 주장을 실측 검증 |

### Phase C — 토큰 축 decode (수집 제거)

| # | 작업 |
|---|---|
| C-1 | decode 시 각 노드가 partial attention + LSE 계산 |
| C-2 | LSE all-reduce 로 병합 |
| C-3 | A-5 의 KV 수집 제거 → TTFT 에서 1초 회수, 긴 프롬프트일수록 이득 큼 |

### 선행 조건

- **토큰 임베딩 F32 → 양자화** ([발견 #3](03-attention-batching.md#65-발견-3-부수적-토큰-임베딩이-f32-로-저장된다))
  가중치를 복제하므로 노드당 6.32 GB 다. 4.5 GB 로 줄이면 KV·활성화 여유가 생긴다.
  8 GB 노드까지 쓰려면 필수.
- 16 GB 노드 4대 확보됨: root(.105) + .113 + .166 + .191

## 6. 검증 계획

| 항목 | 방법 | 기준 |
|---|---|---|
| 속도 | S=447/1789, N=1/2/4 스윕 | Phase A 에서 3× 이상 |
| 연산 분할 확인 | `gemmMs` 가 1/N 로 떨어지는가 | SP 처럼 안 줄면 설계 실패 |
| 정확도 | RULER / LongBench / needle-in-haystack | Star Attention 은 4~8블록에서 97~100 % 보고 |
| exact 대비 | Ring CP 를 별도 구현해 동일 정확도 지점 비교 | Phase B 이후 |

**정확도에 유리한 조건**: 우리는 블록 수가 4~8 로 적다. 초장문을 겨냥한 기존 연구들은
수십 블록을 쓰므로 블록 간 attention 손실이 훨씬 크다.

## 8. 선행연구 상의 위치

| 연구 | 관계 |
|---|---|
| [Star Attention](https://arxiv.org/pdf/2411.17116) | 블록 독립 인코딩 + 단일 merge 의 원형. **anchor 를 재계산**한다 |
| [APE](https://arxiv.org/pdf/2502.05431) | 병렬 인코딩 KV 의 분포 정렬. 정확도 회복 기법으로 차용 가능 |
| [Meta CP](https://arxiv.org/pdf/2411.01783) | exact 비교군(Ring, pass-KV/pass-Q). decode 병합 방식의 근거 |
| [Pulsar Attention](https://arxiv.org/html/2607.20457) | anchor 를 통계 요약으로 대체. **정확도 각도로 충돌하므로 우리는 비용 각도로만 다룬다** |
| [Galaxy](https://arxiv.org/pdf/2405.17245) | 엣지 클러스터 분산 추론. GPU 보드 대상이라 배리어 비용 체계가 다르다 |

**우리 차별점**: 기존 연구는 전부 초장문(128 K)·고대역폭·GPU 전제다.
우리는 **짧은 프롬프트(0.5~4 K)·1GbE·CPU only** 체제이고, 그 체제에서는
anchor amortization 이 성립하지 않아 설계가 달라진다. 그 차이를
**측정된 배리어 비용(16.3 ms)** 으로 정량화한 것이 기여의 핵심이다.
