# 스케줄링 모델 — 청크 크기와 노드 수의 결합 제약

## 1. 문제

프롬프트 길이 `S`, 노드 수 `N` 이 주어질 때 **청크 크기 `B` 와 레이어 배분 `{L_k}`**
를 정해야 한다. 기존 구현은 `B` 를 휴리스틱으로 정했고, 그 휴리스틱이
**긴 프롬프트에서 1.85배 손해**를 냈다([11 §9](11-results.md)).

## 2. 두 제약이 반대 방향으로 작용한다

| | 작은 `B` | 큰 `B` |
|---|---|---|
| 커널 효율 | **나쁨** — `B < B_min` 이면 토큰당 최대 2배 | 좋음 |
| 파이프라인 충전 `M = ⌈S/B⌉` | 좋음 | **나쁨** — `M < N` 이면 미성립 |

따라서 실현 가능 구간은

```
B_min  ≤  B  ≤  S / N
```

`B_min` 은 커널 효율 포화점(Pi5 실측 **16**), 상한은 파이프라인이 채워질 조건이다.

## 3. 실측이 이 구간을 확인한다

PP8, 패딩·균형 배정 적용. 프롬프트 길이별로 `B` 를 바꿔 측정:

| S | B | M | `M ≥ N` | PP8 (ms) | 배수 |
|---|---|---|---|---|---|
| 112 | 16 | 7 | **위반** | 6,614 | 0.82× |
| 112 | 32 | 4 | **위반** | 6,609 | 0.84× |
| 224 | **16** | 14 | OK | **2,902** | **4.12×** |
| 224 | 32 | 7 | **위반** | 3,899 | 3.09× |
| 512 | **16** | 32 | OK | **5,363** | **5.30×** |
| 512 | 32 | 16 | OK | 6,396 | 4.49× |
| 2048 | 8 | 256 | OK (`B<B_min`) | 60,952 | 2.34× |
| 2048 | **32** | 64 | OK | **31,174** | **4.60×** |

- **S=112**: 어떤 `B` 로도 구간이 공집합(`16 > 112/8 = 14`). 실측이 **단일보다 느리다**(0.82×).
- **S=224 / 512**: `B=32` 는 `M` 을 너무 줄여 손해. `B=16` 이 최적.
- **S=2048**: `B=8` 은 커널 효율 손해. `B=32` 가 최적.

**구간 위반이 실측 실패와 정확히 대응한다.**

## 4. 알고리즘

```
입력: S, N, 플랫폼 상수 c(·)·B_min, 노드 프로파일 {α_k, β_k}
출력: N*, B*, {L_k}, 패딩

1. 실현 가능성:  B_min ≤ S/N  이 아니면 N ← ⌊S / B_min⌋ 로 낮춘다
2. B* = argmin_B  T(S, N, B)   over  B ∈ [B_min, S/N],  B mod 4 = 0
3. {L_k} = argmin  max_k (α_k L_k c(B*) + β_k)      ← 레이어당이 아니라 스테이지 실측
4. S 를 4의 배수로 패딩                              ← N·e 증폭 제거
```

### 각 단계의 근거 (전부 실측)

| 단계 | 근거 |
|---|---|
| 1 | S=112 에서 구간 공집합 → 실제로 0.82× |
| 2 | 같은 S 에서 `B` 가 1.85배를 가름 |
| 3 | 레이어당 프로파일이 root 를 최저→최고로 오판([11 §8](11-results.md)) |
| 4 | 비정렬 청크의 초과분이 위치와 무관하게 `N·e` ([12 #15](12-findings.md)) |

## 5. 기존 구현과의 차이

현재 `resolvePrefillChunkBatchSize` 는

```c
autoChunk = nBatches / ppSize;
if (ppSize >= 4) autoChunk /= 2;
if (nPrefillTokens / threshold >= 8)  autoChunk /= 2;   // 길수록 줄인다
if (nPrefillTokens / threshold >= 16) autoChunk /= 4;
```

**프롬프트가 길수록 청크를 줄인다.** 위 모델은 정확히 반대를 처방한다 —
길수록 `S/N` 상한이 느슨해지므로 `B` 를 키울 수 있고, 키워야 한다.

## 6. GPU 와 다른 이유

이 제약이 문제가 되려면 `B_min` 이 작아야 한다.

- **CPU**: `B_min = 16`. `S=224` 같은 짧은 프롬프트도 `M=14` 로 8단 파이프라인이 성립한다.
  그래서 `B` 를 고를 자유도가 있고, 잘못 고르면 1.85배를 잃는다.
- **GPU**: `B_min` 이 수백. `M` 이 한 자릿수라 파이프라인 깊이를 못 키우고,
  애초에 prefill 을 이렇게 잘게 쪼개지 않는다. 선택 문제 자체가 없다.

즉 **`B_min` 이 작다는 CPU 의 성질이 이 스케줄링 문제를 만든다.**

## 7. 미검증

- 모델 `T(S,N,B)` 의 예측 오차를 정량화하지 않았다. 지금은 **제약(1단계)만 검증**됐다.
- `B*` 를 탐색이 아니라 닫힌 형태로 구할 수 있는지 확인하지 않았다.
- 노드 수를 낮추는 1단계가 실제로 이득인지(S=112 에서 N=4) 측정하지 않았다.
