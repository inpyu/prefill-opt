# 발견 목록 — 무엇이 문제였고 어떻게 고쳤나

각 항목: **증상 → 원인 → 수정 → 효과**. 상세는 [06-baseline-status.md](06-baseline-status.md).

## A. 단일 노드 (발견 #1~#7)

### #1 `-mtune=native` 가 dotprod 경로를 죽이고 있었다
- **증상**: prefill 이 llama.cpp 의 12 %
- **원인**: ARM 에서 `-march=native -mtune=native` 는 dotprod 를 켜지 않는다. llama.cpp 는 `-mcpu=native` 를 쓴다
- **효과**: 496 → 78 ms/tok (**6.4×**)

### #2 prefill 이 decode 용 attention 커널을 재사용
- **원인**: 쿼리 1개 전제 커널을 배치 크기만큼 반복 호출 → KV 캐시를 `배치 × kvMul` 번 스트리밍
- **수정**: `multiheadAttBatch_F32` — GQA 그룹화 + 쿼리 타일링
- **효과**: 78,150 → 72,938 ms

### #3 토큰 임베딩이 F32 로 저장 (부수)
- 1.96 GiB, 모델 파일의 33 %. **성능이 아니라 RAM 문제**
- 워커는 임베딩이 없으므로(loadRoot) 양자화 없이도 8 GB 노드로 충분 → **불필요 판정**

### #4 Q4_0 가중치 repack 부재
- **원인**: llama.cpp 의 `block_q4_0x4` 재배치가 없어 SDOT 4행 GEMM 을 못 씀
- **효과**: 마이크로벤치 105 → 330 GFLOPS, 실측 prefill **2.0×**

### #5 소켓 재시도의 1 ms 고정 sleep
- **원인**: `EAGAIN` 마다 1 ms sleep. 집합통신 1회에 재시도 수십 회 → 배리어가 수십 ms
- **수정**: `poll()` 로 교체
- **효과**: 배리어 43.9 → 16.3 ms

### #6 제어 패킷 배열이 청크 폭을 64 로 묶고 있었다
- **원인**: `MAX_CONTROL_BATCH_POS` 검사가 `setBatchSize()` 에 있었으나, 그 배열은 decode 의 명시 위치 모드에서만 쓰인다. prefill 은 `position + i` 로 재구성하므로 무관
- **부수**: `NnByte nBatches` 가 uint8_t 라 청크 폭이 255 에서 0 으로 돌았다
- **부수**: Makefile 이 헤더 의존성을 추적하지 않아 헤더 수정이 반영 안 됨 (`-MMD -MP` 추가)

### #7 attention 의 청크 폭 천장은 점수 행렬이 아니라 **쿼리 워킹셋**
- **증상**: B=448 에서 attn 이 43,838 ms (B=32 의 16배)
- **첫 진단(틀림)**: 점수 행렬 `att` 실체화. 온라인 소프트맥스로 없앴으나 **무변화**
- **진짜 원인**: `t`(키)가 바깥 루프라 매 `t` 마다 배치 전체의 쿼리/누적기를 다시 훑는다. FlashAttention 은 KV 와 **쿼리를 모두** 타일링하는데 KV 만 했었다
- **수정**: 쿼리 축 `BR=32` 타일 추가
- **효과**: B=448 에서 attn 43,838 → 2,731 ms (**16×**). B 천장 제거

## B. 분산 (발견 #8~#9 + 후속)

### #8 집합통신을 배치 **행마다** 호출
- **증상**: syncWait 59초(전체의 80 %)인데 실제 전송은 0.84초
- **원인**: sync 루프가 행 단위로 집합통신 호출. B=448 이면 allreduce 1회가 448 왕복
- **수정**: 배치 전체를 한 번에 (28,672 → 64 왕복)
- **효과**: **거의 없음** (6 %). 이 가설도 지배 요인이 아니었다
- **부수 소득**: 정확도 개선 (TP2 편차 0.740 → 0.022 %)

### #9 `--workers` 는 자동으로 PP 다 — **TP 는 실행된 적이 없다**
- **증상**: "TP4"(73,907)와 "PP4"(73,374)가 같은 시간. 통신량은 21배 차이인데
- **원인**: [app.cpp:1868](../src/app.cpp) 의 `Auto PP heuristic` 이 `ppSize = nNodes` 로 덮어씀
- **파장**: 이 프로젝트의 모든 "TP" 측정치가 사실 PP 였다. #8 의 가설들(통신량/배리어/왕복)이 전부 기각된 이유가 이것
- **추가**: `--auto-pp 0` 으로 진짜 TP 를 돌리자 **결과가 틀렸다**(사전 결함).
  SP 도 깨져 있다(애초에 P/D 분리용 축). **동작하는 축은 PP 하나뿐**

### #10 `--wave-pipeline` 이 꺼진 채로 측정돼 왔다
- 마이크로배치 겹침이 **이미 구현돼 있었다**(`forwardPrefillNoWait`)
- 켜자 B=16 에서 193 k → 87 k ms (2.2×)

### #11 `--n-batches` 가 `ppSize` 로 나뉜다
- **원인**: `autoChunk = nBatches / ppSize`. `--n-batches 32` 가 실효 청크 8 이 되고, **B=8 은 최악 구간**(단일에서 2배 손해)
- **효과**: 실효 청크를 32 로 맞추자 0.99× → **1.88×**

### #12 prefill 에서 로짓을 **전체 행** 전송
- **증상**: 마지막 스테이지의 `send` 가 5,667 ms 막힘
- **원인**: `16 × 128,256 × 4 = 8.2 MB`/마이크로배치, 28개면 230 MB. root 는 즉시 읽지 않으므로 버퍼가 참
- **핵심**: `lm_head` 는 **이미 마지막 행만 계산**하고 있었는데(`lmHeadRowRange`) 전송은 전체를 보냈다. 계산 최적화와 전송이 어긋나 있었다
- **효과**: 230 MB → 0.5 MB, **1.88 → 2.46×**

### #13 불균등 레이어 분할 — 그래프와 로더가 다른 분할을 가정
- **증상**: `--pp-layers 9,9,7,7` 이 게이트 편차 25.9 %
- **원인**: `buildLayerStartOffsets` 는 불균등을 지원하는데 `getLayerOwnerPpRank`(가중치 로더)는 균등을 가정 → **가중치가 엉뚱한 노드로**
- **효과**: 수정 후 N=4 에서 2.52 → **2.81×** (정확도도 0.707 → 0.289 % 로 개선)

### #14 N=8 에서는 균형화가 실패한다 — 입자도
- 최적 배정 `5,4,3,4,5,4,4,3` 으로도 7,165 → 7,360 ms (개선 없음)
- 레이어 1개가 목표 스테이지 시간의 22 % 라 조정 단위가 너무 크다
- **다음**: 서브레이어 분할 (`attn | FFN` 경계). FFN 이 레이어 FLOPs 의 81 %

## C. 기각된 가설 (전부 실측으로)

| 가설 | 반증 |
|---|---|
| 통신 대역폭 | TP4(448 MB)와 PP4(21 MB)가 21배 차이인데 시간 동일 |
| 배리어 횟수 | 896 → 64 회로 줄여도 1.6배만 개선 |
| 집합통신 왕복 횟수 | 28,672 → 64 회로 줄여도 6 % |
| 소켓 버퍼 크기 | 8 MB 로 올려도 7 % |
| 마지막 스테이지 lm_head 계산량 | 이미 처리되고 있었음 (중복 수정, 철회) |
