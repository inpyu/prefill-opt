# 용어 가이드

이 프로젝트에서 실제로 쓴 용어만 모았다. 정의보다 **우리 측정값으로 설명**한다.

---

# Part 1. 추론의 두 단계

## prefill / decode

LLM 추론은 성격이 다른 두 단계로 나뉜다.

| | prefill | decode |
|---|---|---|
| 하는 일 | 입력 프롬프트 전체를 한 번에 처리 | 토큰을 하나씩 생성 |
| 처리 토큰 | S개 (예: 447) | 1개 |
| 병목 | **연산** (compute-bound) | **메모리 대역폭** (memory-bound) |
| 우리 실측 | 447토큰에 36.7초 | 토큰당 약 0.5초 |

**왜 성격이 다른가**: prefill 은 토큰 447개가 같은 가중치를 공유해 쓰므로,
가중치를 한 번 읽어 447번 계산한다 → 연산이 병목.
decode 는 토큰 1개를 위해 가중치 6.3 GB 를 전부 읽어야 한다 → 메모리가 병목.

## TTFT (Time To First Token)

프롬프트를 넣고 **첫 글자가 나오기까지의 시간**. 사용자가 체감하는 반응성이다.
prefill 시간이 거의 전부를 차지한다. 이 연구의 목표 지표.

## KV 캐시

Attention 이 "이전 토큰들"을 참조할 때 쓰는 저장소.
각 토큰 t, 각 레이어 l 마다 `K_l[t]`, `V_l[t]` 벡터를 저장한다.

```
Llama-3-8B 기준
  토큰 1개 · 레이어 1개당 : 2 × 1024 × 4B = 8 KB
  토큰 1개 (32레이어)     : 256 KB
  2048토큰 프롬프트       : 512 MB
```

**TTFT 의 산출물은 정확히 두 개다**: 전체 KV 캐시 + 마지막 토큰의 로짓.
그래서 이 연구는 "KV 캐시를 어떻게 빨리 만드는가"의 문제가 된다.

## GQA (Grouped-Query Attention)

쿼리 헤드는 32개인데 KV 헤드는 8개만 두고, 4개씩 공유하는 구조.
KV 차원이 hidden(4096)의 1/4인 1024로 줄어든다.
→ **KV 캐시가 작아지고, 노드 간 KV 교환도 싸진다** (분산 설계에 유리).

## RoPE / RMSNorm

- **RMSNorm**: 벡터 크기를 정규화하는 연산. 우리 수식의 `φ(·)` 가 이것.
- **RoPE**: 위치 정보를 회전으로 넣는 기법. **위치에 의존**하므로,
  위치 무관 선형 사상을 적합하려면 **RoPE 적용 전 값**을 써야 한다
  (캘리브레이션 덤프를 사영 직후에 뜨는 이유).

# Part 2. 연산 용어

## GEMM / GEMV

- **GEMM** (General Matrix-Matrix Multiply): 행렬 × 행렬. prefill 이 여기 해당.
- **GEMV** (General Matrix-Vector Multiply): 행렬 × 벡터. decode 가 여기 해당.

GEMM 이 훨씬 효율적이다 — 가중치 한 번 읽고 여러 토큰을 처리하니까.

## compute-bound / memory-bound

연산 유닛이 노는지, 메모리가 노는지의 문제.

```
산술 강도(arithmetic intensity) = 연산량 / 메모리 접근량   [FLOP/byte]

이 값이 기계의 균형점보다 크면 compute-bound, 작으면 memory-bound
```

**우리 Pi5 의 균형점**:
```
연산 ~110 GFLOPS ÷ 메모리 대역폭 ~8 GB/s ≈ 11~14 FLOP/byte
```

GEMM 에서 산술 강도는 대략 배치 크기와 같다. 그래서 **배치 32 이상**이어야
memory-bound 를 벗어난다(실측 포화점과 일치). 이것이 설계 제약
"블록 크기 ≥ 32 토큰"의 근거다.

## 양자화 (Q4_0, Q8_0, F32, F16)

숫자를 몇 비트로 저장하는가.

| 표기 | 비트 | 용도 |
|---|---|---|
| F32 | 32 | 원본 정밀도 |
| F16 | 16 | 절반 |
| **Q8_0** | 8 (+블록당 스케일) | 활성화 |
| **Q4_0** | 4 (+블록당 스케일) | 가중치 |

`Q4_0` 은 값 32개를 한 블록으로 묶어 4비트 정수 + fp16 스케일 하나로 저장한다.
8B 모델이 4.5 GB 로 줄어든다.

## dotprod (SDOT)

ARM CPU 의 명령어. int8 4개씩의 내적을 한 번에 계산한다.
`-mtune=native` 때문에 이게 꺼져 있어서 GEMM 이 3~4배 느렸다 (발견 #1).

## repack

가중치를 **SIMD 가 먹기 좋은 순서로 미리 재배치**하는 것.

```
기존: GEMM 마다 4비트를 풀어야 함 (명령어의 절반 이상이 언팩)
repack: 미리 풀어두고, 출력 행 4개를 교차 배치
        → 로드 1회가 4행을 커버, zero-point 뺄셈도 사전 흡수
```

우리 실측: 105 → 330 GFLOPS (3.1배). 발견 #4.

# Part 3. 분산 용어

## 분산 축 네 가지

같은 모델을 여러 노드에 어떻게 쪼개느냐의 선택지.

| 축 | 무엇을 쪼개나 | 비유 |
|---|---|---|
| **TP** (Tensor Parallel) | 행렬을 세로로 잘라 각 노드가 일부 열을 계산 | 한 문제를 여럿이 나눠 풀고 매번 답을 합침 |
| **PP** (Pipeline Parallel) | 레이어를 나눠 각 노드가 일부 레이어 담당 | 컨베이어 벨트 |
| **CP/SP** (Context/Sequence Parallel) | **토큰**을 나눠 각 노드가 일부 토큰 담당 | 책을 나눠 읽기 |
| 블록 병렬 | CP 인데 노드 간 참조를 생략(근사) | 나눠 읽되 서로 안 물어봄 |

우리 실측 (447토큰, 단일 노드 37.9초 기준):

| 축 | prefill | 판정 |
|---|---|---|
| TP 2노드 | 33.6초 | 유일하게 단일을 이김 |
| PP 4노드+wave | 39.8초 | 구조적 대기로 실패 |
| dllama 의 SP | 43.6초 | **연산을 안 나눔** (KV 저장만 나눔) |

## barrier (배리어) / 동기

여러 노드가 **서로를 기다리는 지점**. 가장 느린 노드에 전부 맞춰진다.

TP 는 레이어마다 2번, 32레이어면 **청크당 64번** 기다린다.
우리 실측 배리어 1회 비용: **16.3 ms** (1ms sleep 버그 수정 후).

## all-reduce / ring / P2P

노드 간 데이터를 합치는 방식.

- **all-reduce**: 모두가 값을 내고 합쳐서 모두가 받음. 전원이 참여 = 배리어.
- **P2P** (point-to-point): 한 노드가 다른 한 노드에게만 보냄. 배리어 아님.
- **ring**: 원형으로 이웃에게만 넘김. P2P 의 연쇄. 연산과 겹칠 수 있음.

**우리 측정의 핵심**: 통신 시간의 대부분은 **전송이 아니라 대기**였다.
```
TP2 : syncWait 14.6초  vs  syncXfer 2.0초   → 7:1
```
즉 **바이트를 줄이는 것보다 배리어 수를 줄이는 것이 중요**하다.
이것이 GPU 문헌의 최적화 방향과 다른 지점이다.

## wave / chunked prefill

프롬프트를 청크로 쪼개 파이프라인에 흘려보내는 것. PP 의 유휴(버블)를 줄인다.
우리 실측: PP4 가 73.7 → 41.0초로 개선됐지만 여전히 단일 노드보다 느렸다.

# Part 4. 우리 알고리즘의 수학

여기가 핵심이다. 천천히 쌓아 올린다.

## 4-1. 문제: 깊이는 순차다

```
x_{l+1} = x_l + Attn_l(x_l) + FFN_l(x_l)
```

레이어 l+1 을 계산하려면 레이어 l 이 끝나야 한다. **32번 순차**.
토큰끼리는 독립이라 병렬이 되지만, 깊이는 안 된다.

## 4-2. 관찰: KV 는 단순한 곱셈이다

```
K_l = W_k^l · φ(x_l)        ← 행렬 하나 곱하는 것이 전부
```

레이어 비용의 **3.9 %** 뿐이다. 나머지 96 % (Attention, FFN)는
**오직 x_l 을 만들기 위해서** 존재한다.

## 4-3. 아이디어: 중간 지점에서 끊는다

레이어 k 까지만 정상 계산하고, 그 위 레이어들의 KV 는 **x_k 에서 직접** 만든다.

```
K_l = A_l · φ(x_k)          (l > k)
```

`A_l` 은 "x_k 를 보고 레이어 l 의 K 를 맞추는 행렬".
이렇게 하면 **레이어 k+1 부터 31까지가 서로 독립**이 되어,
노드에 아무렇게나 나눠줘도 통신이 0이다.

### 선형 사상 (linear map)

`A_l · φ(x_k)` 처럼 **행렬 곱 하나로 표현되는 변환**.
가장 단순한 형태이고, 그래서 빠르다.
실제 관계가 비선형이면 오차가 생긴다 — 그게 우리가 검증하는 것.

### 최소제곱 적합 (least squares fit)

`A_l` 을 어떻게 정하나? **실제 값과 가장 가깝게** 맞춘다.

```
A_l* = argmin_A  ‖ A·φ(x_k) − K_l ‖²
```

읽는 법: "A 를 곱한 결과와 진짜 K_l 의 차이(제곱합)를 최소로 만드는 A".

**학습(training)이 아니다.** 연립방정식을 푸는 것이라 **닫힌 형태 해**가 있고,
몇 분이면 끝난다. GPU 도 역전파도 필요 없다.
→ SwiftKV 는 distillation(증류 학습)이 필요해 GPU 가 있어야 한다. 우리의 차별점.

## 4-4. dense / 랭크 / 공유 기저

여기가 가장 헷갈리는 부분이다.

### dense (조밀) 적합

`A_l` 을 **아무 제약 없는 꽉 찬 행렬**로 두는 것.

```
A_l : 4096 × 1024  =  4.2 M 개의 숫자
상위 16레이어의 K,V 를 모두 하려면 → 134 M 개
Q4_0 으로 저장해도 75 MB
```

가장 정확하지만, **CPU 에서는 이 75 MB 를 매번 메모리에서 읽어야 한다.**
Part 2 에서 봤듯 SBC 는 메모리가 병목이라 치명적이다.

### 랭크 (rank)

행렬이 담고 있는 **실질적인 정보의 차원 수**.

```
4096×1024 행렬이라도, 실제로는 256차원 정보만 담고 있을 수 있다
→ "랭크가 256이다"
```

랭크가 낮으면 **작은 행렬 두 개의 곱으로 쪼갤 수 있다**:

```
A (4096×1024)  ≈  P (4096×256) · B (256×1024)
   4.2 M 개              1.05 M + 0.26 M = 1.3 M 개   → 3.2배 절약
```

이것을 **저랭크 근사(low-rank approximation)** 라 한다.

### SVD / 특이값 / 에너지

랭크를 찾는 표준 도구.

**SVD** (특이값 분해)는 행렬을 "방향들 + 각 방향의 세기"로 분해한다.
그 세기가 **특이값(singular value)** 이다.

```
특이값이 큰 순서로: σ₁ ≥ σ₂ ≥ σ₃ ≥ ...

에너지 비율 = (상위 r개 특이값의 제곱합) / (전체 제곱합)
```

에너지가 0.95 라면 "상위 r개 방향이 정보의 95 %를 담는다"는 뜻이고,
나머지를 버려도 5 % 만 잃는다. **랭크를 얼마로 할지 정하는 기준**이 된다.

### 공유 기저 (shared basis) ← 우리 아이디어

저랭크를 **레이어별로 따로** 하면 여전히 레이어마다 `P_l`, `B_l` 두 행렬이 필요하다.

**핵심 가설**: 상위 레이어들의 KV 는 **같은 부분공간**에 산다.
그렇다면 `P` 를 레이어끼리 공유하고, 레이어별 차이는 **대각 스케일링**만 두면 된다.

```
A_l  ≈  U · diag(d_l) · V

  V      : 공유 (256 × 4096)   — x_k 를 256차원으로 압축
  d_l    : 레이어별 (256개)     — 레이어마다 다른 가중치
  U      : 공유 (1024 × 256)   — 256차원을 K 로 복원
```

계산 순서가 바뀐다:

```
z = V·φ(x_k)              ← 한 번만 (모든 레이어 공통)
K_l = U·(d_l ⊙ z)         ← 레이어마다 원소곱 + 작은 행렬 곱
```

`⊙` 는 원소별 곱(element-wise product). 벡터 두 개를 같은 자리끼리 곱하는 것.

**절감 효과** (상위 16레이어, K+V):

| | 파라미터 | 스트리밍량 | 연산 |
|---|---|---|---|
| dense | 134 M | 75 MB | 268 MFLOP/token |
| **공유 기저** | **1.58 M** | **0.9 MB** | **18.9 MFLOP/token** |
| 절감 | **85×** | **83×** | **14×** |

CPU 에서는 **83× 메모리 절감이 결정적**이다. GPU 연구가 이 구조를 안 쓰는 이유는
GPU 에서는 메모리 대역폭이 넉넉해 dense 로도 충분하기 때문이다.

# Part 5. 검증 용어

## 재구성 오차 (relative error)

`A_l·φ(x_k)` 가 진짜 `K_l` 과 얼마나 다른가.

```
rel.err = ‖ 진짜 − 예측 ‖ / ‖ 진짜 ‖
```

0 이면 완벽, 0.1 이면 "평균적으로 10 % 틀림".
우리 판정 기준: **0.10 미만이면 유망**.

## holdout / 과적합 / 일반화

**과적합(overfitting)**: 연립방정식의 미지수가 관측보다 많으면,
주어진 데이터는 완벽히 맞추면서 새 데이터에서는 엉망이 된다.

```
A_l 의 미지수: 4096 × 1024
필요한 관측 : 최소 4096 토큰
우리 첫 시도 : 460 토큰  ← 부족해서 다시 수집
```

**holdout**: 데이터의 일부(20 %)를 **적합에 쓰지 않고 남겨** 두었다가,
거기서 오차를 재는 것. 이래야 **일반화**(새 입력에서도 되는가)를 알 수 있다.

## ridge (정칙화)

관측이 부족할 때 해가 불안정해지는 것을 막는 보정.
`(XᵀX + λI)` 처럼 대각선에 작은 값을 더한다.

# 부록: 우리 연구를 한 문단으로

> SBC(라즈베리파이) 클러스터에서 LLM 의 첫 응답 시간(TTFT)을 줄이려 한다.
> TTFT 는 곧 KV 캐시를 만드는 시간이고, 그 계산은 **깊이 방향으로 순차**라
> 노드를 늘려도 잘 안 빨라진다. 우리는 두 가지로 이를 깬다.
> ① **토큰을 노드에 나눠** 동시에 KV 를 만든다(블록 병렬).
