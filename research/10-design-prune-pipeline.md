# 설계: 깊이별 축소 × 파이프라인 재분할 (SBC prefill)

## 1. 왜 이 조합인가

단독으로는 둘 다 새롭지 않다.

- **토큰 가지치기**: LazyLLM(2024)이 prefill TTFT 단축 목적으로 이미 제안했다.
- **이종 엣지 PP 분할**: PipeEdge(2022) 등이 프로파일 기반 정적 분할을 다뤘다.

새로운 것은 **둘의 상호작용**이다.

```
가지치기 → 깊은 레이어일수록 토큰이 줄어듦 → 스테이지 부하가 깊이에 따라 감소
        → 정적 균등 분할이 원리적으로 틀림 → 온라인 재분할이 필수가 됨
```

GPU 에서 이 문제가 안 보이는 이유가 있다. GPU 는 prefill 을 이렇게 잘게
파이프라인하지 않는다 — 산술 강도 임계가 높아 마이크로배치를 작게 못 쪼갠다.
**Pi5 는 B=16 에서 이미 compute-bound** 이므로([06 §4.7](06-baseline-status.md))
M=28 짜리 파이프라인이 성립하고, 그래서 이 상호작용이 처음으로 문제가 된다.

CPU/SBC 라서 가능한 조건 세 가지가 모두 걸린다:

| 조건 | 근거 | 이 설계에서의 역할 |
|---|---|---|
| 잘게 쪼갤 수 있다 | B=16 에서 compute-bound (실측) | M=28 파이프라인 |
| 메모리가 연산보다 흔하다 | PP8 노드당 가중치 0.8 GB, 여유 6 GB | 중첩 소유로 무비용 경계 이동 |
| 분기 페널티가 없다 | SIMT 아님 | 가변 토큰 수가 그대로 이득 |

## 2. 연산 감축 상한 (FLOPs 기준)

레이어당 FLOPs: **FFN 81 %**, attention projection 19 %.
레이어 `k` 이후 잔존율 `r` 로 가지치기하면 연산비 = `k/32 + (32-k)/32 · r`.

| k \ r | 0.7 | 0.5 | 0.3 |
|---|---|---|---|
| 4 | 1.36× | 1.78× | **2.58×** |
| 8 | 1.29× | 1.60× | **2.11×** |
| 12 | 1.23× | 1.45× | 1.78× |
| 16 | 1.18× | 1.33× | 1.54× |

**감축만으로는 2배 남짓이다.** 분산(현재 3.78×)과 곱하면 6~9× 가 목표 범위다.
"몇십 배"는 정확 연산으로 불가능하다 — 단일 노드가 이미 하드웨어 피크의 68 % 다.

## 3. 구현상 진짜 어려운 지점

### 3-1. 가지친 토큰의 KV 가 없어진다

prefill 에서 토큰 `i` 의 K/V 는 뒤 토큰 `j>i` 가 참조한다. `i` 를 레이어 8 에서
버리면 레이어 9~31 에서 `i` 의 K/V 가 만들어지지 않아 **뒤 토큰이 참조할 수 없다.**

이것은 **근사**다. 피할 수 없고, 품질 비용으로 계상해야 한다.
LazyLLM 도 같은 선택을 한다. 따라서:

> **품질-속도 트레이드오프 곡선으로 제시한다.** 단일 수치로 "N배 빠름"을
> 주장하지 않는다. 게이트(`verify.sh`)의 perplexity 가 그대로 품질 축이 된다.

### 3-2. 그래프의 batchSize 는 고정이다

실행기는 forward 당 하나의 `batchSize` 로 모든 op 를 돈다. 레이어 중간에서
행 수를 줄이는 경로가 없다.

**해법: 압축(compaction).** 가지치기 지점에서 살아남은 행을 버퍼 앞쪽 `[0,k)` 로
모으고, 이후 op 는 `activeRows` 만 돈다. 살아남은 행이 연속이므로 GEMM 타일이
그대로 채워진다 — 마스크 방식(비연속)보다 CPU 에서 훨씬 유리하다.
이미 있는 행 범위 기계(`lmHeadRowRange` / `cpRowWindow`)를 확장해 쓴다.

압축 대상: `x` 버퍼, `positions` 파이프. 원래 위치를 유지해야 RoPE 와 attention 이
맞는다.

### 3-3. attention 이 빈 위치를 읽는다

레이어 8 이후 KV 버퍼에는 살아남은 위치만 채워진다. 그런데 attention 커널은
`t = 0..maxPos` 를 순회하며 KV[t] 를 읽으므로 **버려진 위치에서 쓰레기를 읽는다.**

해법: 살아남은 위치 목록을 유지하고 attention 이 그 목록만 순회한다.
융합 커널([06 §4.8](06-baseline-status.md))을 이미 우리가 다시 썼으므로 변경 지점이 명확하다.

### 3-4. 마지막 토큰은 절대 버리면 안 된다

prefill 의 출력은 마지막 토큰의 로짓 하나다. 중요도와 무관하게 고정 보존한다.

## 4. 중요도 점수

후보:

1. **직전 레이어의 attention 수신량** — 토큰 `i` 가 다른 토큰들로부터 받은
   attention 가중치 합. LazyLLM 이 쓰는 방식. 추가 연산이 거의 없다(이미 계산된 값).
2. 활성화 노름 `||x_i||`.
3. 둘의 결합.

**1번으로 시작한다.** 융합 attention 커널이 `stateL`(정규화 분모)을 이미 들고 있어
누적이 싸다.

## 5. 분산과의 결합 — 이 설계의 핵심

가지치기 비율이 **고정**이면 스테이지 부하를 미리 계산할 수 있으므로
"가지치기를 아는 정적 분할"로 충분하다. 그러면 새로울 것이 없다.

**비율을 데이터 의존으로 두면** (임계값 기반, 프롬프트마다 잔존 수가 다름)
스테이지 부하를 사전에 알 수 없다. 이때 온라인 재분할이 **필수**가 된다.
품질 측면에서도 고정 비율보다 임계값이 낫다 — 정보가 고른 프롬프트는 덜 자르고
중복이 많은 프롬프트는 더 자른다.

### 무비용 경계 이동

각 노드가 담당 레이어에 더해 경계 **±δ** 를 미리 보유한다.
그러면 실행 중 경계 이동에 **가중치 전송이 0** 이다.

| 구성 | 노드당 가중치 |
|---|---|
| PP8 기본 (4레이어) | 0.8 GB |
| PP8 + δ=2 (8레이어) | 1.6 GB |

8 GB 노드에 6 GB 가 남는다. **PP 라서 가능하다** — 단일 노드는 6.3 GB 전체를,
TP 는 슬라이스를 들고 있어 이 여유가 없다.

## 6. 검증 계획 — 매 단계 게이트

[07.6 의 게이트 규율](09-design-ring-cp.md)을 그대로 따른다. 다만 가지치기는
**의도적 근사**이므로 게이트의 의미가 달라진다:

| 단계 | 게이트 기준 |
|---|---|
| P1. 압축 경로 (잔존율 1.0) | 기존과 **동일 출력** — 배선만 검증 |
| P2. 가지치기 켬 (단일 노드) | perplexity **곡선**을 기록 (통과/실패 아님) |
| P3. 품질 임계 선택 | perplexity 저하 ≤ X % 인 최대 감축 |
| P4. 분산 결합 (PP4/PP8) | P3 설정에서 단일 노드와 동일 품질 |
| P5. 온라인 재분할 | 정확성 불변, 속도만 개선 |

P1 이 중요하다. 잔존율 1.0 에서 출력이 바뀌면 압축·attention 변경에 버그가 있는
것이고, 그 상태로 P2 의 품질 곡선을 그리면 **가지치기 탓으로 오인**하게 된다.

## 7. 순서

```
P0. eta_balance 원인 규명 (워커 순서 치환)   <- 선행
P1. 압축 경로 (잔존율 1.0, 무손실 검증)
P2. 중요도 점수 + 가지치기 (단일 노드 품질 곡선)
P3. 분산 결합
P4. 데이터 의존 임계 + 온라인 재분할
```

**P0 가 선행인 이유**: 지금 η_balance 가 59 % 인 원인을 모르는 상태에서 가지치기를
얹으면, 스테이지 불균형이 가지치기 때문인지 원래 있던 것인지 구분할 수 없다.
그러면 이 논문의 핵심 주장("가지치기가 불균형을 만든다")을 증명할 수 없다.

## 8. P0 결과 — 기존 불균형은 **정적**이다 (완료)

워커 순서를 치환해 느림이 기계를 따라가는지 스테이지 위치를 따라가는지 갈랐다.

| 기계 | 순서 A | 순서 B |
|---|---|---|
| .113 | rank1 → **238 ms** | rank3 → 303 ms |
| **.166** | rank2 → **371 ms** | rank1 → **354 ms** |
| .191 | rank3 → 344 ms | rank2 → 269 ms |

- **기계 요인**: `.166` 은 어느 위치에서도 가장 느리다(371 / 354).
  GEMM 마이크로벤치는 노드 간 3 % 이내로 동일했으므로([06 §4.15](06-baseline-status.md))
  연산 속도가 아니라 메모리 대역폭이나 열 상태로 보인다.
- **위치 요인**: rank3(마지막 스테이지)는 위치 자체로 약 65 ms 를 더 쓴다
  (.113: 238 → 303, .191: 344 → 269 역방향). 최종 norm + lm_head 때문이다.

총 시간은 두 순서에서 같다(12,607 vs 12,549) — 어느 쪽이든 `.166` 이 상한을 정한다.

### 이 결과가 설계에 주는 것

**둘 다 정적이다.** 따라서 기존 불균형은 **1회 프로파일링 기반 정적 분할로 해결된다**
— PipeEdge 가 이미 하는 일이고, 여기에 새로울 것은 없다.

이것은 오히려 논지를 **깨끗하게 만든다**:

| 불균형의 원인 | 성질 | 해법 | 신규성 |
|---|---|---|---|
| 하드웨어 개체차 (`.166`) | 정적 | 1회 프로파일 + 정적 분할 | 없음 (PipeEdge) |
| 마지막 스테이지 lm_head | 정적·구조적 | 분할 시 상수 보정 | 없음 |
| **가지치기로 인한 깊이별 부하 감소** | **데이터 의존** | **온라인 재분할** | **여기** |

즉 **정적 요인은 기존 방법으로 처리하고, 그 위에 얹히는 데이터 의존 요인이
이 논문의 대상**이다. 동적 메커니즘을 "열 드리프트 때문"이라고 주장했다면
근거가 약했을 텐데(드리프트는 관측되지 않았다), 가지치기라는 명확한 원인이 있으므로
주장이 선다.

> **부수 확인**: `.166` 이 GEMM 속도는 같은데 스테이지가 1.4배 느린 이유는
> 아직 모른다. 메모리 대역폭 측정이 필요하다. 다만 정적이므로 이 설계의
> 진행을 막지 않는다.
