## 3. 발견 #4 — Q4_0 가중치 repack 부재

llama.cpp 는 로드 시점에 Q4_0 을 SIMD 친화 레이아웃으로 재배치한다
(`ggml/src/ggml-cpu/repack.cpp:4583`, Cortex-A76 은 `q4_0_4x4_q8_0` 경로).
distributed-llama 가 벤더링한 llamafile sgemm 에는 이 개념이 없다.

기존 커널은 (i,j,l) 조합마다:

| 용도 | 명령어 |
|---|---|
| 4비트 언팩 (load/and/shr/sub) | ~6 |
| 실제 연산 (vdotq_s32) | 2 |
| 누적 (cvt, mla) | 2 |
| 스케일 (fp16 스칼라 곱) | ~1 |

유효 64 FLOP / 명령어 11개 ≈ 5.8 FLOP/instr → 이론 111 GFLOPS.
**실측 97~110 GFLOPS 와 정확히 일치한다.**

repack 이 바꾸는 것:
1. **zero-point(-8) 를 pack 시점에 XOR(`0x88888888`) 로 흡수** → 런타임 `vsubq_s8` 제거
2. **출력 행 4개를 인터리브** → 로드 1회가 4행을 커버 (`vdotq_laneq_s32`)
3. 스케일 `d[4]` 가 연속 → `vmulq_laneq_f32` 로 벡터화

### 이식 (src/nn/nn-repack.{hpp,cpp}, 출처 llama.cpp MIT)

마이크로벤치 (`prefill_bench/bench_repack.cpp`), 4스레드:

| shape | batch 32 기존 | batch 32 repack | 배율 |
|---|---|---|---|
| qkv/o (4096×4096) | 105.2 | 317.6 | 3.02× |
| ffn_w1 (14336×4096) | 106.2 | 307.0 | 2.89× |
| ffn_w2 (4096×14336) | 103.2 | 331.3 | 3.21× |

정확성 (`prefill_bench/test_repack.cpp`): gemm/gemv 모두 **L2 상대오차 ~1e-6**
(양자화 차이가 아니라 fp32 누적 순서 차이 수준).

### 통합 설계 판단 3가지

1. **in-place repack** — `NnBlockQ40 4개(72B) == block_q4_0x4(72B)` 라 추가 메모리 0.
   `static_assert` 로 강제한다.
   또한 행 그룹 g 의 원본 바이트 범위와 목적지 범위가 정확히 겹치므로
   그룹 하나 분량(kBlocks×72 B)만 임시로 잡으면 된다.
   (초기 구현은 op 마다 가중치 전체 사본을 잡았다 — lm_head 는 295 MB 로 Pi5 8GB 에서 위험)
2. **로드 완료 감지** — `NnCpuDeviceSegment::loadWeight` 에서 `loadedBytes` 누적.
   root/worker 가 모두 이 경로를 지나므로 훅을 두 곳에 만들 필요가 없다.
3. **배리어 없는 스레드 분할** — 실행기는 op 경계에서만 동기화한다.
   출력 **열**로 나누고 각 스레드가 활성화 변환을 자기 `thread_local` 스크래치에 중복 수행.
   - 중복 비용: batch 32 / k 4096 기준 스레드당 ~139 kB 셔플
   - **행**으로 나누면 배리어는 불필요하지만 모든 스레드가 가중치 전체(FFN w1 28 MB)를
     읽어 트래픽이 nThreads 배. 연산 11.4 ms vs 트래픽 14 ms 로 역전되어 기각.

폴백은 유지된다 — repack 미지원 형상(d 가 4의 배수가 아님)이나 비-aarch64 는
기존 `matmulForward_llamafile` 로 자동 폴백. decode(batch=1)는 gemv 가
평범한 `NnBlockQ80` 을 그대로 받으므로 활성화 변환 없이 동작한다.

### 실측 대비 마이크로벤치 갭

마이크로벤치 3.1× 인데 실측 GEMM 은 2.2× 다. 후보:
- 활성화 변환의 스레드별 중복
- GEMM 이 3배 빨라지며 드러난 메모리 대역폭 한계

## 4. lm_head prefill 제한

**근거**: prefill 루프는 위치 0..n-2 만 처리하고 `forward()` 후 로짓을 **전혀 읽지 않는다.**
decode 첫 스텝이 마지막 입력 토큰을 처리해 첫 출력 로짓을 만든다.
즉 prefill 의 lm_head 계산은 전부 낭비다.

**구현**: 그래프 형태와 sync 는 그대로 두고 행렬곱 행 범위만 제한
(`lmHeadRowRange`, `nn-cpu-ops.cpp`). phase 는
`NnExecutor::setDecodePhase` → `nnCpuOpsSetDecodePhase` 로 전달된다.

**다중 노드 정합성 확인됨**: `controlPacket.phase` 가 root→worker 브로드캐스트되고
(`app.cpp:1242`), 워커도 매 forward 마다 `executor.setDecodePhase()` 를 호출한다
(`app.cpp:2070`). 따라서 모든 노드가 같은 판단을 한다.

### 남은 기회: 세그먼트 통째 스킵

현재는 청크마다 마지막 행 1개를 계산하는데, 그 한 행 때문에
**lm_head 가중치 295 MB 를 청크마다 스트리밍**한다 (메모리 바운드, 청크당 ~32 ms).

`end` 세그먼트를 prefill 동안 통째로 건너뛰면:

| | 연산 절감 | logits sync 절감 |
|---|---|---|
| 행 제한 (현재) | 97 % | ✘ |
| 세그먼트 스킵 | 100 % | ✔ **청크당 ~16 MB** (batch 32 × vocab 128256 × 4 B) |

1GbE 에서 청크당 0.14 초다. **다중 노드 단계에서 승격할 것.**
(단 wave 모드는 `drainPrefillLogits` 가 로짓을 읽으므로 예외 처리 필요)

## 4.5. 발견 #5 — 소켓 재시도의 1 ms 고정 sleep

**분산 측정 전체를 오염시키던 버그.** 단일 노드에서는 드러나지 않는다.

```cpp
static inline void sleepOnSocketRetry() {
    std::this_thread::sleep_for(std::chrono::milliseconds(1));   // ← 이것
}
```

논블로킹 소켓이 `EAGAIN` 을 반환할 때마다 1 ms 를 통째로 잔다.
리눅스 타이머 해상도상 실제로는 1~2 ms 이고, 집합통신 하나에서 재시도가
수십 회 발생하므로 **배리어 1회가 수십 ms 로 부풀었다.**

```
실측(TP 2노드, S=447): 배리어 896회에 syncWait 39.3초 = 배리어당 43.9 ms
                       그중 회선 시간은 6.9 ms 뿐  →  37 ms 가 sleep
```

### 수정: poll() 로 교체

```cpp
poll(&pfd, 1, 1);   // 데이터 도착 즉시 깨어남 (마이크로초 단위)
```

**스핀(`yield` 반복)이 아니라 `poll` 을 택한 이유**: 코어가 4개뿐인 SBC 에서
스핀은 연산 스레드를 직접 뺏는다. `poll` 은 커널 대기라 CPU 를 점유하지 않으면서도
데이터 도착 즉시 깨어난다. TP 집합통신 경로는 여러 소켓을 한 번에 `poll` 한다.

### 효과 — 축마다 다르게 작용한 것이 핵심

| 구성 | 수정 전 | 수정 후 | 개선 |
|---|---|---|---|
| **TP2** | 58,280 ms | **33,633 ms** | **42 % ↓** |
| PP4+wave | 41,026 ms | 39,825 ms | 3 % ↓ |
| TP2 syncWait | 39,297 ms | **14,611 ms** | 2.7× ↓ |
| 배리어 1회 | 43.9 ms | **16.3 ms** | |

**TP 의 대기는 대부분 구현 아티팩트였고, PP 의 대기는 구조적이다.**
PP4 는 전송량이 TP2 의 절반 이하인데 대기는 더 크다(23.1 vs 14.6초) —
청크가 스테이지를 **순서대로** 통과해야 하기 때문이다.

이 수정으로 **TP2 가 처음으로 단일 노드를 앞섰다**(1.13×).
"분산이 단일보다 느리다"는 이전 결론은 알고리즘의 한계가 아니라 이 sleep 이었다.

## 4.7. 발견 #6 — 제어 패킷의 위치 배열이 prefill 청크 폭을 묶고 있었다

### 증상

`--n-batches` 를 32 → 112 로 올리자 즉사한다.

```
🚨 Critical error: batchSize exceeds MAX_CONTROL_BATCH_POS
```

가중치는 정상 로드되고 prefill 진입 직후에 죽는다. 즉 메모리 문제가 아니다.

### 왜 이 파라미터가 중요한가

`nBatches` 는 prefill 청크 폭이다. 청크마다 32레이어 FFN 가중치 **3.2 GB 를 다시
읽으므로**, 청크 수가 곧 가중치 재스트리밍 양이다.

| 청크 폭 | 청크 수 (S=447) | 가중치 재스트리밍 |
|---|---|---|
| 32 (기본) | 14 | 44.4 GB |
| 112 | 4 | 12.7 GB |

Pi5 의 메모리 대역폭이 ~8 GB/s 이므로 이 차이가 그대로 시간일 **것으로 봤다**
— 아래 §"그래서 청크를 키우면 빨라지는가"에서 이 가설은 실측으로 기각된다.
그래도 이 파라미터가 중요한 이유는 남는다:
[Ring CP](09-design-ring-cp.md) 에서 **이 값이 곧 노드당 블록 크기 `B`** 가 된다.
설계의 통합 원리("산술 강도는 `B` 에만 의존한다")가 구현상으로도 이 파라미터
하나에 모여 있다.

### 원인 — 검사가 엉뚱한 곳에 걸려 있었다

`MAX_CONTROL_BATCH_POS` 는 제어 패킷의 `batchPositions[]` **배열 길이**(64)다.
그런데 그 배열은 명시 위치 모드에서만 쓰인다.

| 경로 | `positionMode` | `batchPositions[]` |
|---|---|---|
| **prefill** (`setPosition`) | 0 = contiguous, 위치를 `position + i` 로 재구성 | **쓰지 않음** |
| decode continuous batching (`setBatchPositions`) | 1 = explicit | 씀 |

prefill 청크의 위치는 항상 연속이라 배열이 필요 없다. 그런데 검사가
`setBatchSize()` — **모든 경로의 공통 진입점** — 에 있어서, 배열을 쓰지도 않는
prefill 이 배열 길이에 묶여 있었다.

### 수정 — 검사를 배열에 실제로 쓰는 곳으로

| 위치 | 변경 |
|---|---|
| `RootLlmInference::setBatchSize` | 검사 **제거** (배치 크기는 배열과 무관) |
| `RootLlmInference::setBatchPositions` | 유지 (여기가 배열에 쓴다) |
| `dllama.cpp` continuous batching | `nBatches` → `maxActive` (동시 활성 요청 수) 로 대상 변경 |
| `app.hpp` | `MAX_CONTROL_BATCH_POS` 64 → 512 (decode 폭 여유. 패킷 648 → 2440 B, 청크당 1회 전송이라 무시 가능) |

이로써 **prefill 청크 폭이 패킷 상한에서 분리**됐다.

### 부수 발견 — `nBatches` 가 8비트로 잘리고 있었다

상한을 풀고 나니 다음 벽이 나왔다.

```
--n-batches 448  -> Assertion failed: 448 != 192
--n-batches 1024 -> Assertion failed: 1024 != 0
```

`448 & 255 = 192`, `1024 & 255 = 0`. 8비트 잘림이다. 범인은 `nn-cpu-ops.hpp` 의

```c
typedef struct {
    const char *name;
    NnByte nBatches;   // NnByte = uint8_t
```

이 구조체에서 `NnByte` 는 **바이트 포인터용** 타입인데(`NnByte *bufferFlags`,
`NnByte **buffers`) 개수 필드에 잘못 쓰였다. `NnUint` 로 고쳤다.
즉 청크 폭이 255 에서 **조용히 0 으로 무너지고** 있었다.

### 그리고 빌드가 헤더를 추적하지 않고 있었다 (측정 1시간을 날림)

`Makefile` 의 규칙이 `app.o: src/app.cpp` 뿐이라 **헤더를 고쳐도 재컴파일되지 않는다.**
`MAX_CONTROL_BATCH_POS` 를 512 로 올리고 `make` 했더니 rc=0 이면서 실제로는 아무것도
컴파일되지 않았고, 옛 상한 그대로인 바이너리로 스윕을 돌려 같은 에러를 다시 봤다.

수정: `CXXFLAGS += -MMD -MP` + `-include $(wildcard *.d)`.
`.d` 는 헤더를 **전제조건으로 추가**하므로 규칙의 `$^` 를 그대로 두면 헤더까지
컴파일러 인자로 넘어간다(`cannot specify '-o' with '-c' ... multiple files`).
컴파일 규칙은 `$<` 로, 링크 규칙은 `$(filter-out %.spv %.hpp %.h, $^)` 로 바꿨다.

> [§6 운영 교훈](#6-운영-교훈)의 "빌드했다고 믿지 말 것"이 세 번째로 적중했다.
> 이번엔 사람 실수가 아니라 빌드 시스템이 거짓말을 한 경우다.

### 그래서 청크를 키우면 빨라지는가 — **아니다** (모델이 틀렸다)

상한 두 개를 다 풀고 실측한 결과, 위에서 세운 가중치 재스트리밍 모델은 **기각된다.**

S=448, seqLen=704, 단일 노드 4스레드 (워밍업 제외 중앙값):

| 청크 폭 `B` | prefill | **attn** | ffn | 청크 수 | `att` 버퍼 |
|---|---|---|---|---|---|
| 8 | 63,023 | 2,537 | 46,636 | 56 | 0.7 MB |
| 16 | 32,610 | 2,524 | 23,232 | 28 | 1.4 MB |
| 24 | 43,270 | 2,520 | 32,762 | 19 | 2.1 MB |
| **32** | **32,564** | 2,548 | **22,879** | 14 | 2.8 MB |
| 48 | 35,327 | 2,755 | 25,288 | 10 | 4.1 MB |
| 64 | 37,224 | 3,622 | 28,189 | 7 | 5.5 MB |
| 112 | 39,137 | 9,340 | 22,702 | 4 | 9.6 MB |
| 448 | 76,076 | 43,838 | 23,863 | 1 | 38.5 MB |
| 1024 | 86,432 | 42,329 | 36,061 | 1 | 88.0 MB |

> `B=64` 는 편차 16%(34,321~40,128)로 신뢰도가 낮다. 나머지는 1~3%.

**FFN 이 거의 줄지 않는다.** 청크를 14 → 4 개로 줄여 가중치 재스트리밍을
44.4 → 12.7 GB 로 낮췄는데 FFN 은 23,721 → 22,702 ms, 겨우 1 초다.
FFN GEMM 은 이미 32행에서 compute-bound 라 행을 더 쌓아도 얻을 것이 없다.

대신 **attention 이 16배로 폭발한다.** 원인은 중간 버퍼

```
att = size2D(F_32, nBatches, nHeads0 * seqLen)
```

가 캐시를 벗어나는 것이다. Pi5 의 L3 는 2 MB 인데 청크 32 에서 2.8 MB 로 이미
경계에 있고, 그 위로는 매 청크가 통째로 DRAM 왕복이 된다.
`B ≤ 32` 에서 attn 이 2,520~2,548 로 **완전히 평평한 것**이 그 증거다.

### 미규명 — `B` 가 16의 배수가 아니면 FFN 이 나빠진다

`B=32` 의 행당 FFN 비용을 1.00 으로 두면:

| `B` | 8 | 16 | 24 | 32 | 48 | 64 |
|---|---|---|---|---|---|---|
| 배수 | 2.04 | 1.02 | 1.43 | 1.00 | 1.10 | 1.23 |

"16 의 배수로 패딩된다"는 모델은 8·16·32 는 맞히지만 **48 을 못 맞힌다**(예측 1.00,
실측 1.10). 스레드 불균형도 아니다 — `SPLIT_THREADS` 는 나머지를 고르게 분배한다.
`matmulForward_repack` 은 출력 **열**로 스레드를 나누고 행은 4단위(`rowCount & ~3u`)라
16 이 나올 자리가 없다. **원인 미규명으로 남긴다.** 6개 점으로 모델을 세우면
48 같은 반례를 설명하지 못한 채 굳게 된다.

실용적으로는 `B` 를 16 의 배수로 두는 것으로 충분하다.

> **결론: prefill 청크 폭의 상한은 메모리 용량이 아니라 캐시다.**
> 처음 넣은 `auto` 의 `memCap`(≈2,700)은 완전히 틀린 기준이었다 —
> 실제 최적은 그보다 두 자릿수 작다.

### `--n-batches auto` 최종 규칙 (실측 기반)

```
cacheCap = L3 / (nHeads · seqLen · 4)          # att 가 L3 안에 들어오는 B
B = clamp( floor16( min(cacheCap, promptCap) ), 16, 32 )
```

검증: `auto` 가 16 을 선택(`cacheCap 21, att 96 KB/batch`)해 **33,582 ms** —
직접 지정한 최적 32,564 / 32,610 과 노이즈 내 동일하다.

> **기존 기본값 32 는 이미 최적이었다.** 이번 작업의 성과는 속도가 아니라,
> "청크를 키워 재스트리밍을 줄인다"는 [Ring CP](09-design-ring-cp.md) 의 전제를
> **구현 전에 실측으로 죽인 것**이다.

### 설계에 미치는 영향 ([Ring CP](09-design-ring-cp.md))

09 의 통합 원리는 "산술 강도는 노드당 토큰 수 `B` 에만 의존한다" 였다.
방향은 맞지만 **`B` 에 천장이 있다**: `att` 버퍼가 캐시를 벗어나는 지점이다.

```
B_max ≈ L3 / (nHeads0 · seqLen · 4)
```

seqLen=704 에서 ≈ 23, seqLen=4096 이면 ≈ 4 다. 즉 **긴 프롬프트일수록 천장이 낮다** —
정확히 CP 가 필요한 영역에서 불리하게 작동한다.

이 천장을 걷어내는 방법은 이미 [§5 남은 항목](#5-남은-항목)에 적혀 있다:
**online softmax 융합** — `att` 를 실체화하지 않으면 이 항이 사라진다.
지금까지는 "attention 2~3× 개선" 정도의 선택지로 봤지만, 이제는
**`B` 를 키울 수 있게 하는 전제 조건**이다. 우선순위를 올려야 한다.


## 4.8. 발견 #7 — attention 의 `B` 천장은 점수 행렬이 아니라 **쿼리 워킹셋**이었다

§4.7 에서 `att` 버퍼(`B × nHeads × seqLen × 4B`)가 L3 를 벗어나는 것이 원인이라고
적었다. **틀렸다.** 온라인 소프트맥스 융합으로 `att` 실체화를 없애고 측정한 결과:

| `B` | attn 기존 | attn **KV만 융합** | `att` 워킹셋 |
|---|---|---|---|
| 32 | 2,548 | 2,464 | 2.8 MB → 64 kB |
| 112 | 9,340 | **9,338** | 9.6 MB → 224 kB |
| 448 | 43,838 | 38,148 | 38.5 MB → 896 kB |

B=112 에서 워킹셋을 9.6 MB → 0.66 MB 로 줄였는데 **9,340 → 9,338 ms, 무변화**다.
`att` 는 원인이 아니었다.

### 진짜 원인

이 커널은 `t`(키 위치)를 바깥 루프에 두어 K/V 의 한 위치를 배치 전체가 재사용한다.
그 대가로 **매 `t` 마다 배치 전체의 쿼리·누적기·스크래치를 다시 훑는다.**
그 워킹셋은 헤드 그룹당 약 `B × 6 kB` 이고, `B` 가 커지면 코어당 L2 512 kB 를
넘어가 매 `t` 가 DRAM 왕복이 된다.

FlashAttention 은 KV 와 **쿼리를 모두** 타일링한다. 나는 KV 만 타일링했고,
그래서 아무것도 나아지지 않았다. 쿼리 축에 `BR = 32` 타일을 추가하자:

| `B` | 32 | 112 | 448 |
|---|---|---|---|
| attn 기존 | 2,548 | 9,340 | 43,838 |
| attn **쿼리 타일링** | 2,551 | **2,664** | **2,731** |

B=448 에서 **16배**. attention 이 이제 `B` 에 거의 무관하다.

정확성: 세 경우 모두 greedy 생성 토큰 33개가 기존 커널과 **완전 일치**.

### 측정 방법론 정정 — 설정을 순차로 돌리면 비교가 오염된다

한때 "B=32 에서 융합은 1.3% 손해"라고 적었다. **실행 순서 효과였다.**

| 설정 | prefill | attn | gemm | ffn |
|---|---|---|---|---|
| B=32 융합 off (먼저 실행) | 31,865 | 2,538 | 28,181 | 22,766 |
| B=32 융합 on (나중 실행) | 32,968 | **2,351** | 28,739 | 23,283 |

`gemm`(+558)과 `ffn`(+517)은 **attention 커널과 아무 상관이 없는데** 같이 늘었다.
커널이 실제로 바꾼 `attn` 은 오히려 187 ms 줄었다. 총합 +1,103 ms 중 커널의 몫은
**−187** 이고 나머지는 드리프트다.

`run_one.sh` 의 워밍업·반복 중앙값은 **한 설정 안의** 편차만 잡고 설정 간 순서 효과는
못 막는다. off/on 을 번갈아 4라운드 돌리자 결론이 뒤집혔다 (B=32, attn ms):

| round | f=0 | f=1 |
|---|---|---|
| 1 | 2,468 | 2,370 |
| 2 | 2,483 | 2,367 |
| 3 | 2,519 | 2,369 |
| 4 | 2,485 | **2,326** |

**4/4 라운드 모두 융합이 빠르다**(~5%). prefill 총합의 차이는 부호가 엇갈려
(−245/+388/+1,191/−477) 노이즈다.

> **`prefill_bench/run_ab.sh` 를 만들었다.** 설정을 번갈아 실행해 드리프트가
> 모든 설정에 똑같이 걸리게 한다. **설정 간 비교는 앞으로 이 스크립트로만 한다.**
> 이 정정 이전의 설정 간 비교(§4.7 청크 스윕 포함)는 모두 이 편향을 갖고 있다.

### 그래서 융합을 항상 켠다

`expf_neon` 으로 맞춘 뒤(§4.9) 융합은 attention 에서 일관되게 빠르고, 더 정확하고
(float64 대비 9.311e-4 vs 9.789e-4), `B` 천장도 없앤다. 임계값을 둘 이유가 없다.

판단은 전역 플래그가 아니라 **커널이 호출 시점의 `batchSize` 로** 한다 — 워커는
root 의 CLI 를 받지 않으므로 전역으로 두면 root 와 워커가 다른 커널을 돌게 된다.
`--attn-fused 0` 으로 기존 커널 복귀 가능(A/B 비교용).

### 정리 — `B` 를 막던 것

| 후보 | 실측 판정 |
|---|---|
| 제어 패킷 배열 상한 (`MAX_CONTROL_BATCH_POS`) | 실재 (§4.7) — 검사 위치 오류 |
| `NnByte nBatches` 8비트 잘림 | 실재 (§4.7) |
| 가중치 재스트리밍 | **기각** — 청크 14→4 인데 FFN 1초 |
| `att` 점수 행렬 실체화 | **기각** — 없애도 무변화 |
| **쿼리 워킹셋** | **실재** — 이것이 천장이었다 |

`--attn-fused 0` 으로 기존 커널로 되돌려 A/B 비교할 수 있게 남겼다.
구현은 `multiheadAttFused_F32` (`nn-cpu-ops.cpp`), 타일은 `TILE=128`(키) / `BR=32`(쿼리).

> **설계 영향**: [Ring CP](09-design-ring-cp.md) 의 노드당 블록 `B` 에 있던 캐시 천장이
> 사라졌다. 이제 `B` 는 캐시가 아니라 FFN 의 하한(16의 배수, §4.7)에만 묶인다.

## 4.9. 다중 노드 정확성 검증 (처음으로 수행)

지금까지 다중 노드는 **속도만** 재고 정확성은 한 번도 확인하지 않았다.
Ring CP 구현에 들어가기 전에 이것부터 했다.

### 토큰 일치는 지표로 못 쓴다

TP2 와 단일 노드의 생성 토큰을 비교하니 22번째에서 갈렸다.

```
단일: ... The resulting prompt length. Communication patterns that are ...
TP2 : ... The resulting prompt is not. Understanding where the time ...
```

둘 다 정상적인 영어 연속이다. 프롬프트가 반복적인 합성문이라 두 후보의 로짓이
근접했고, TP 의 리덕션 순서 차이로 argmax 가 뒤집힌 것이다. 앞 21토큰이 일치하므로
prefill 자체는 일관된다. **greedy 토큰 일치는 이런 근접 상황에서 너무 취약하다.**

### perplexity 를 지표로 — 그런데 기본 경로는 배치를 안 탄다

`perplexity` 모드는 `setBatchSize(1)` 로 토큰을 하나씩 흘린다. 즉
**prefill 배치 attention 커널을 전혀 타지 않는다.** 그대로 쓰면 검증이 헛돈다.

`--ppl-batch <n>` 을 추가했다. `decodePhase(true)` 를 유지해 lm_head 가 모든 행을
계산하게 하고(prefill 은 마지막 행만 계산한다, §4), 배치 폭 n 으로 청크를 흘린다.

### 결과

| 구성 | perplexity | batch=1 대비 |
|---|---|---|
| 단일 `batch=1` (기준) | 6.228231 | — |
| 단일 `batch=112` 기존 커널 | 6.222623 | 0.09 % |
| 단일 `batch=112` 융합 | 6.220358 | 0.13 % |
| **TP4 `batch=112` 융합** | 6.223577 | **0.07 %** |
| **TP4 `batch=112` 기존 커널** | 6.240660 | **0.20 %** |

**배치 폭은 결과에 전혀 영향이 없다** — `fused=0` 에서 B=32 와 B=112 가
소수점 6자리까지 동일했고, `fused=1` 도 마찬가지였다. 차이는 전부 커널 선택에서 온다.

### 융합 커널이 기존보다 정확하다 (float64 대조)

배치 perplexity 에서 융합이 0.27 % 다른 값을 내서 커널을 직접 수치 비교했다
(`prefill_bench/test_attn_fused.cpp` — 두 함수가 `static` 이라 `.cpp` 를 통째로 include).

처음엔 두 커널 간 상대 L2 오차가 **9.8e-4** 였다. 재결합이면 1e-6 수준이어야 하므로
재결합이 아니다. 원인은 **`softmax_F32` 가 근사 벡터 지수 `expf_neon` 을 쓰는데
융합 커널은 libm `expf` 를 쓰고 있던 것**이었다. 융합 쪽도 `expf_neon` 으로 맞췄다
(정확도 일치 + 원소별 스칼라 `expf` 호출 제거).

그래도 7.5e-4 가 남는다. 근사 지수와 온라인 소프트맥스를 섞으면
`exp~(a)·exp~(b) ≠ exp~(a+b)` 이므로 두 커널은 **원리적으로** 다른 값을 낸다.
어느 쪽이 맞는지는 서로 비교해서 알 수 없어 float64 기준해를 만들어 댔다.

| 커널 | float64 대비 상대 L2 오차 |
|---|---|
| 기존 배치 커널 | 9.789e-4 |
| **융합 커널** | **9.311e-4** |

**융합이 오히려 더 정확하다.** 둘 다 ~1e-3 인 것은 `expf_neon` 의 근사 오차 바닥이지
타일링이나 온라인 소프트맥스 때문이 아니다.

> 결론: TP4 의 prefill 배치 경로는 두 커널 모두 단일 노드와 **0.2 % 안에서 일치**하고,
> 그 편차는 이미 존재하던 `expf_neon` 근사 바닥과 같은 수준이다. 무손실로 간주한다.

## 4.10. SP 축은 원래 깨져 있었다 (사전 결함)

Ring CP(7-4)를 SP 토폴로지 위에 올렸는데 출력이 `!!!!` 로 깨졌다. 로짓 회수 경로를
의심해 한참 팠지만, **대조 실험이 원인을 다른 곳으로 돌렸다.**

`--cp-split` 을 끈 SP2 도 똑같이 `!` 만 생성한다. CP 가 꺼지면 `gCpSize=1` 이라
`cpRowWindow` 는 전체 범위를 돌려주고 allgather 도 원래 경로를 타므로 CP 코드는
비활성이다. 그래서 오늘 코드 변경 **이전** 리비전(`795cf5b`)을 worktree 로 빌드해
같은 실험을 돌렸다.

```
795cf5b 빌드, --sp-size 2, 워커 1대  ->  생성 결과: "!"
```

**SP 는 오늘 작업 이전부터 깨져 있었다.**

### 왜 지금까지 몰랐나

SP 는 **성능만 쟀고 정확성은 한 번도 확인하지 않았다**(SP2 43,620 / SP4 47,374 ms).
[§4.9](#49-다중-노드-정확성-검증-처음으로-수행) 의 검증은 TP4 만 대상이었다.
"SP 가 단일보다 느리다"를 통신 오버헤드로 해석했는데, 애초에 올바른 계산을
하고 있지 않았을 가능성이 크다. **그 수치들은 폐기해야 한다.**

### 설계에 미치는 영향

[Ring CP](09-design-ring-cp.md) 는 `spSize=N` 토폴로지 위에 서 있다.
그 축이 `tpSize=1`(전체 가중치 복제)과 KV 시퀀스 샤딩을 공짜로 주기 때문이었다
(§4.7 의 7-3 검증). **기반이 깨져 있으면 그 위에서 CP 를 디버깅해봐야 소용없다.**

### 원인 좁히기 — 네 가지를 배제했다

| 가설 | 실험 | 결과 |
|---|---|---|
| 프롬프트가 `--sp-prefill-threshold`(기본 256) 아래라서 | 447토큰으로 재실행 | **기각** — 그대로 `!` |
| KV 샤딩 / allgather 결함 | `DLLAMA_SP_NOSHARD=1` 로 샤딩 제거<br>(두 노드가 각자 전체 KV 사용) | **기각** — 그대로 `!` |
| `tpSize=1` 일 때 `SYNC_WITH_ROOT` 를 건너뛰어<br>워커가 임베딩 출력 `x` 를 못 받는 것 | `DLLAMA_KEEP_TP1_SYNCS=1` 로 sync 유지 | **기각** — 그대로 `!` |
| 오늘 작업의 회귀 | `795cf5b` worktree 빌드 | **기각** — 사전 결함 |

세 번째는 코드상 실재하는 결함이다 ([nn-network.cpp:1893](../src/nn/nn-network.cpp)):

```c
// With TP group size 1, root sync is typically a no-op broadcast path.
if (shouldSkipTp1NoopSyncs()) {
    if (declaredTpSize <= 1) continue;   // <- xPipe 브로드캐스트가 사라진다
}
```

SP 는 `tpSize=1` 이므로 워커가 `x` 를 영영 못 받는다. 실제로 워커의 xPipe 행을
찍어보면 `maxabs=0` 이었다. 다만 이것만 고쳐도 출력은 여전히 깨진다 —
**결함이 하나가 아니다.**

### 남은 결론

`DLLAMA_SP_NOSHARD=1` 에서는 두 노드가 서로 데이터를 주고받지 않고 각자 전체를
계산한다. 그런데도 root 의 출력이 틀린다. 즉 **문제는 SP 의미론이 아니라
`tpSize=1` + `nNodes=2` 구성 자체**다. 이 코드베이스의 다중 노드 경로는 TP 를
전제하고 있고, TP 가 아닌 2노드 구성은 검증된 적이 없다.

### 다음

CP 를 SP 축에 얹는 것을 포기하고 **별도 축**으로 만든다
(`NnParallelTopology` 에 cpSize 추가 + 필요한 sync 를 명시적으로 정의).
비용은 크지만, 검증된 적 없는 경로 위에 쌓지 않는다는 이점이 있다.
`DLLAMA_SP_NOSHARD` 는 진단용으로 남겨둔다.

> **교훈**: 새 기능을 기존 축 위에 올릴 때, 그 축이 **정확성 기준으로** 검증된 적이
> 있는지 먼저 확인한다. 성능 수치가 있다는 것은 동작한다는 뜻이 아니다.

전 노드 동일: Raspberry Pi 5 / Cortex-A76 4코어 / aarch64. **메모리만 이종**.

| 그룹 | 노드 |
|---|---|
| 16 GB × 4 | root(.105) + .113 + .166 + .191 |
| 8 GB × 5 | .103 / .94 / .104 / .54 / .96 |

`env.sh` 에서 16 GB 를 목록 앞에 배치해 **4노드 실험이 자동으로 전부 16 GB** 가 되게 했다.

> ⚠️ **Tailscale 주소(100.x)를 실험에 쓰지 말 것.** WireGuard 오버레이라 암호화
> 오버헤드와 DERP 릴레이 경유 가능성이 있어 통신 측정이 오염된다. 접속 불가 시

## 5.5. 실행 절차 (다중 노드는 반드시 이 순서로)

```bash
cd /home/ubuntu/prefill-opt

# 0) 빌드
make dllama

# 1) 워커에 배포 — root/worker 바이너리가 다르면 재현 불가능한 실패가 난다
bash prefill_bench/redeploy_workers.sh

# 2) 워커 기동 — md5 대조 + 포트 해제 대기 + LISTEN 확인을 강제한다
bash prefill_bench/start_workers.sh 3 165.194.19.113 165.194.19.166 165.194.19.191

# 3) 측정 — 가드 5종이 들어 있다
bash prefill_bench/run_one.sh ./dllama <tag> prompts_gen/prompt_512.txt <out_dir> \
     --auto-pp 0 --pp-size 1 --sp-size 1 --workers 165.194.19.113:9998
```

`run_one.sh` 의 가드:

| # | 가드 | 막는 사고 |
|---|---|---|
| 1 | 실행 파일 이름(comm)으로 중복 dllama 탐지 | 8B 모델 2개 동시 로드 → OOM |
| 2 | 가용 메모리 ≥ 8 GB 확인 | 빌드/추론 경합 |
| 3 | 프롬프트 길이에서 `--max-seq-len` 자동 산정 | KV 캐시 과할당 (8192 이면 KV 만 2.1 GB) |
| 4 | 로그 크기 상한 200 MB 감시 | 종료 경로 무한 출력 → 디스크 소진 |
| 5 | 실패 시 rc 표시 (137/143 = OOM/kill) | 실패를 성공으로 오독 |

> 가드 1은 커맨드라인(`pgrep -f`)이 아니라 실행 파일 이름으로 판정한다.
> 커맨드라인으로 하면 이 스크립트를 감싼 셸까지 오탐한다(실제로 겪음).

## 6. 운영 교훈

`prefill_bench/run_one.sh` 에 가드로 고정했다. **다중 노드 실험은 반드시 이 스크립트로 돌릴 것.**

| 사고 | 원인 | 가드 |
|---|---|---|
| OOM #1 | 백그라운드 실행이 죽은 줄 알고 두 번째를 띄움 → 8B 모델 2개 동시 로드 | `pgrep -f "dllama[^ ]* +(inference\|worker)"` — 이름 변형까지 탐지 |
| OOM #2 | 추론 중에 빌드를 동시 실행 | 시작 전 가용 메모리 ≥ 8 GB 확인 |
| OOM #3 | KV 캐시가 실제 프롬프트가 아니라 `--max-seq-len` 전체로 할당됨 (8B/8192 이면 KV 만 2.1 GB) | 프롬프트 길이에서 `--max-seq-len` 자동 산정 |
| **디스크 19.5 GB 소진** | 종료 시 트래픽 요약이 무한 출력 (아래 §7) | 로그 200 MB 상한 감시 + 코드 측 출력 횟수 제한 |
| 좀비 프로세스 | 이전 세션의 `dllama inference` 가 살아남아 자원 점유 | 위 중복 실행 가드가 탐지 |

### 진단할 때의 규칙 (이번에 크게 데임)

1. **한 번에 하나만 바꾼다.** 바이너리·프롬프트 길이·repack 유무를 동시에 바꿔
   원인 추적이 세 바퀴 돌았다.
2. **바이너리 신원을 매번 확인한다.** 빌드보다 먼저 복사한 stale 바이너리를 실행해
   "고쳤는데 왜 그대로지"를 반복했다. root/worker `md5sum` 대조를 실행 전에 찍을 것.
3. **로그는 크기부터 본다.** `grep` 으로만 확인해 5.5 GB 로그를 놓쳤다.

## 7. 알려진 기존 버그 (distributed-llama 원본)

### 종료 시 트래픽 요약 무한 출력

정상 추론이 끝난 뒤 종료 경로에서:

```
📦 [NET_TRAFFIC] root<->worker[1] socket=0 tx_total=648B ...   ← 정상
📦 [NET_TRAFFIC] invalid socket=1 for root<->worker[2] (nSockets=1)
📦 [NET_TRAFFIC] invalid socket=2 for root<->worker[3] (nSockets=1)
...                                                            무한 증가
```

호출부(`app.cpp:1963`, `app.cpp:2126`)는 둘 다 `i < network->nSockets` 로 경계가
잡혀 있는데 인덱스가 무한 증가했다. **원인 미확정**(종료 시점의 객체 수명 문제로 추정).

한 번의 실행에서 로그가 14 GB, 다른 실행에서 5.5 GB 까지 자랐다.
**추론 결과 자체는 정상**이므로 측정값은 유효하다.

대응: `printSocketTrafficSummary` 의 invalid 분기 출력을 4회로 제한하고,
`run_one.sh` 에서 로그 크기를 감시한다. 근본 원인은 다중 노드 작업이 안정된 뒤 추적할 것.
