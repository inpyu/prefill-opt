## 2. 스케일링 곡선 (최종, 균형 분할)

각 N 마다 스테이지 프로파일(n=28 중앙값)을 재고 서브블록 최적 배정을 적용했다.
게이트 전부 통과 (N=2/4/8 편차 0.7 % 이내).

| 노드 | 배정 (서브블록) | prefill | 배수 | 효율 | 모델 예측 | η_balance | tok/s |
|---|---|---|---|---|---|---|---|
| 1 | — | 29,454 | 1.00× | — | — | 100 % | 15.2 |
| 2 | `34,30` | 19,245 | 1.53× | 77 % | 1.93× | 79 % | 23.3 |
| 4 | `21,17,13,13` | 11,709 | 2.52× | 63 % | 3.61× | 70 % | 38.3 |

노드를 늘릴수록 **단조적으로 빨라진다.**

| N | 균등 | 균형 | 개선 |
|---|---|---|---|
| 8 | 7,446 | 6,347 | **1.17×** |

서브레이어 분할이 §4.16 의 입자도 제약을 풀어 N=8 에서도 균형화가 가능해졌다.

### 노드 이종성 (레이어당 시간, N=8 기준)

| 노드 | ms/레이어 | root 대비 |
|---|---|---|
| root (.105) | 28.3 | 1.00× |
| .103 (8 GB) | 32.6 | 1.15× |
| .94 (8 GB) | 32.7 | 1.16× |
| .104 (8 GB) | 33.4 | 1.18× |
| .54 (8 GB) | 35.0 | 1.24× |
| .113 (16 GB) | 35.0 | 1.24× |
| .191 (16 GB) | 37.1 | 1.31× |

**8 GB 노드가 16 GB 노드보다 빠르다.** 메모리 용량은 속도와 무관하다.
가장 느린 노드가 가장 빠른 노드의 1.6배 — 균등 분할이 이만큼 손해를 본다.

## 3. 예측 모델

```
속도향상(N) = M·N / (M + N − 1),   M = S / B_min
```

`M` 은 마이크로배치 수, `B_min` 은 GEMM 타일 효율이 유지되는 최소 청크 폭
(Pi5 실측 **16**). 버블만 고려한 상한이다.

**따라오는 결과 두 가지:**

- `N → ∞` 에서 속도향상 상한은 `M = S/B_min` 이다. S=448 이면 28배.
  **프롬프트 길이가 유효 노드 수의 상한을 정한다.**
- 실측/예측 비 `η_balance` 가 SBC 고유 손실이며, N 과 함께 100 → 59 % 로 떨어진다.

## 4. η_balance 의 정체 (분해 완료)

| 원인 | 성질 | 대응 | 신규성 |
|---|---|---|---|
| 하드웨어 개체차 (`.166` 이 40 % 느림) | 정적 | 측정 기반 불균등 분할 | 없음 (PipeEdge) |
| 마지막 스테이지 상수 (final norm + lm_head, 35 ms) | 정적·구조적 | 분할 시 상수 보정 | 없음 |
| **레이어 입자도** | **구조적 한계** | **서브레이어 분할 (미구현)** | **여기** |

**입자도가 핵심 제약이다.**

| | 스테이지당 레이어 | 레이어 1개 / 목표 스테이지 시간 | 균형화 |
|---|---|---|---|
| N=4 | 8 | 11 % | 성공 (2.52 → 2.81×) |
| N=8 | 4 | 22 % | **실패** (7,165 → 7,360) |
| N=16 | 2 | ~44 % | 사실상 불가 |

N=8 에서는 느린 노드를 3레이어로 줄이면 다른 노드가 5레이어가 되어 **새 최대**가
된다. 이론 이득 12 % 가 세션 편차 10 % 에 묻힌다.

## 5. 하드웨어 한계 대비 위치

| | 달성 GFLOPS | 피크 대비 |
|---|---|---|
| 단일 노드 | 208 | **68 %** |
| PP8 | 784 | 32 % (8노드 합산 대비) |

Pi5 이론 피크 307 GOPS(A76 4코어 @2.4 GHz, NEON SDOT).

> **단일 노드는 이미 피크의 68 % 다.** 커널을 더 다듬어도 최대 1.5배이고,
> **정확한 연산으로는 몇십 배가 불가능하다.** 8노드 이론 상한이 6.4× 다.

## 6. 부수 관찰

- **8 GB 노드가 16 GB 노드보다 빠르다** (120~124 vs 132~170 ms).
  메모리 용량은 속도와 무관하다. 이종 클러스터에서 "메모리 큰 노드 = 좋은 노드"가 아니다.
- **최적 청크 폭은 16~32** 이고 이는 GEMM 타일 구조에서 온다. 8 이면 2배 손해,
  448 이면 attention 이 커진다. 이 구간이 `M` 을 통해 스케일링 상한을 정한다.
- **분산 통신은 병목이 아니었다.** 실제 전송 시간은 언제나 1초 미만이었고,
  `syncWait` 이 80 % 였던 것은 전부 다른 노드가 무언가에 막혀 있었기 때문이다.

## 7. 시도했으나 채택하지 않은 것

| 방향 | 결과 |
|---|---|
| Ring CP (토큰 축 분산) | 보류 — 통신량이 PP 의 8배(168 vs 21 MB) |
| TP (텐서 병렬) | 보류 — 통신이 매 레이어 임계경로, N 이 커져도 안 줄어듦. 게다가 코드가 깨져 있었음 |
| SP (시퀀스 병렬) | 사용 불가 — 단일 요청용 축이 아님 (P/D 분리용) |
| 임베딩 양자화 | 불필요 — 워커는 임베딩이 없어 8 GB 로 충분 |
| 토큰 가지치기 | 실패 — 1.08배 얻으려고 품질 42 % 손실 |


## 8. 서브레이어 분할 — 구현 성공, 균형화는 실패 (2026-08-11)

### 구현은 됐다

레이어를 `att`/`ff` 두 서브블록으로 쪼개 PP 경계를 레이어 중간에 놓을 수 있게 했다.
기존 브리지(`MERGE_ADD(zqPipe→x)` → `CAST(x→xPipe)`)가 att 뒤에서도 같은 의미라
경계 메커니즘은 새로 만들 필요가 없었다.

게이트 전부 통과:

| 구성 | 편차 |
|---|---|
| 단일 노드 | 0.000 % (회귀 없음) |
| PP4 균등 / 레이어 `9,9,7,7` | 0.707 % / 0.289 % (이전과 동일) |
| 서브블록 `16,16,16,16` | 0.707 % (레이어 `8,8,8,8` 과 동일) |
| **서브블록 `17,17,15,15`** | 0.487 % (레이어를 가로질러 자름) |
| PP8 서브블록 `9,8,6,8,9,9,9,6` | 0.326 % |

### 그러나 균형화는 실패했다

| 구성 | prefill | 균등 대비 |
|---|---|---|
| **PP8 균등** | **8,081** | **최고** |
| PP8 서브블록 `9,8,6,8,9,9,9,6` | 8,454 | +4.6 % |
| PP8 레이어 `5,4,3,4,5,4,4,3` | 9,519 | +18 % |

**균등 분할이 가장 빠르다.** 레이어 단위든 서브블록 단위든 균형화가 오히려 나쁘다.

### 원인 — **측정 표본이 1개였다** (초선형성은 착시)

처음에는 "스테이지 시간이 레이어 수에 비선형이라 정적 분할이 원리적으로 불가능하다"고
결론지었다. **틀렸다.** 근거였던 값이 노드당 마이크로배치 **1개** 표본이었다.

표본을 28개로 늘려 중앙값을 쓰자:

| 기계 | 표본 1개 기준 | **표본 28개 기준** |
|---|---|---|
| .113 | −10 % (선형 이하) | **−0.6 %** |
| .166 | +9 % (초선형) | **−6.4 %** |
| .191 | **+28 %** (강한 초선형) | **+5.2 %** |

**스테이지 시간은 레이어 수에 ±6 % 안에서 선형이다.** 비용 모델은 틀리지 않았고
**입력 숫자가 틀렸다.**

> 이것은 잘못된 측정이 **논문에 유리한 결론**을 지지한 사례다.
> "비용 모델이 원리적으로 비선형 → 온라인 재분할이 필수 → PipeEdge 와 차별화"는
> 그럴듯했지만 근거가 표본 1개였다. **유리한 결과일수록 측정을 먼저 의심한다.**

### 신뢰할 수 있는 값으로 다시 하니 — 성공

8스테이지 전부를 n=28 중앙값으로 재측정하고 서브블록 최적 배정을 계산했다
(att 24 % / ff 76 % 가중, rank7 의 lm_head 상수 분리).

```
레이어당: root 45.3 / .113 35.8 / .166 46.4 / .191 38.7
         .103 31.9 / .94 33.4 / .104 33.2 / .54 35.8
최적: 6,8,7,8,9,9,9,8   (예측 max 185.4 → 158.3 ms, 1.17×)
```

| 구성 | prefill | 개선 |
|---|---|---|
| PP8 균등 | 7,446 | — |
| **PP8 균형 `6,8,7,8,9,9,9,8`** | **6,347** | **1.17×** |

**예측과 정확히 일치한다.** 게이트 통과(편차 0.885 %).

### 정리 — 균형화는 된다, 단 입력이 신뢰할 수 있어야 한다

앞선 두 번의 실패(레이어 단위 `5,4,3,4,5,4,4,3`, 서브블록 `9,8,6,8,9,9,9,6`)는
모두 **표본 1개 프로파일**로 배정을 고른 것이었다. 환경의 성질이 아니라 측정 품질
문제였다.

따라서 [10-design-prune-pipeline.md](10-design-prune-pipeline.md) 의
"비선형성 때문에 온라인 재분할이 필수"라는 논지는 **철회한다.**
정적 분할로 충분하며, 필요한 것은 **신뢰할 수 있는 스테이지 프로파일을 얻는 절차**다:

- 노드당 최소 20~30 마이크로배치 표본
- 중앙값 사용 (평균은 파이프라인 fill/drain 의 긴 꼬리에 오염된다)
- att/ff 비중(24 / 76 %)을 반영한 서브블록 가중
- 마지막 스테이지의 lm_head 상수 분리

### 주의 — 이 세션의 단일 노드 값은 오염됐다

측정 중 root 에서 `node` 프로세스가 CPU 97.7 % 를 점유했다. 단일 노드는 4코어를
모두 쓰므로 직격당해 46,415 ms 로 나왔다(평소 ~30,000). PP8 은 root 가 1/8 만
담당해 13 % 만 느려졌다.

**따라서 이 세션의 "단일 대비 배수"는 부풀려진 값이라 보고하지 않는다.**
PP8 구성끼리의 비교는 오염이 양쪽에 동일하게 걸리므로 유효하다.
root 프로파일(45.3 ms/레이어)도 오염된 값이므로, 부하가 사라지면 재측정이 필요하다.


## 9. 프롬프트 길이 스윕 — 모델 반증과 원인 (2026-08-11)

패딩 적용 후 PP8(균형 배정 `9,8,6,8,9,9,9,6`)로 길이를 바꿔가며 측정했다.

| S | 단일 | PP8 | 실측 배수 | 모델 상한 | 실측/모델 |
|---|---|---|---|---|---|
| 112 | 5,449 | 6,614 | **0.82×** | 4.00× | 21 % |
| 224 | 11,968 | 2,902 | 4.12× | 5.33× | 77 % |
| 512 | 28,415 | 5,363 | 5.30× | 6.56× | 81 % |
| 2048 | 142,867 | 60,952 | **2.34×** | 7.59× | **31 %** |

**모델은 "길수록 좋아진다"고 예측했으나 2048 에서 급락한다.** 반증이다.

### 원인 — 청크 크기 휴리스틱

`resolvePrefillChunkBatchSize` 가 청크를 **세 번** 나눈다:

```c
autoChunk = nBatches / ppSize;                    // 256/8 = 32
if (ppSize >= 4) autoChunk /= 2;                  // -> 16
pressure = nPrefillTokens / prefillChunkThreshold; // 2048/256 = 8
if (pressure >= 8)  autoChunk /= 2;                // -> 8    <- 여기
if (pressure >= 16) autoChunk /= 4;
```

**프롬프트가 길수록 청크를 줄인다.** 그런데 [§4.7](06-baseline-status.md) 실측은
정반대다 — `B=8` 은 토큰당 2배 손해인 최악 구간이다.

S=2048 에서 `--prefill-chunk-size` 로 우회하면:

| chunk | prefill | 배수 |
|---|---|---|
| 휴리스틱 (8) | 61,915 | 2.31× |
| 16 | 35,936 | 3.98× |
| **32** | **33,506** | **4.26×** |

**청크 크기 하나로 1.85배가 갈린다.**

### S=112 는 다른 이유다

`M = 7 < N = 8` 이라 파이프라인이 채워지지 않는다. 모델도 4.00× 를 예측하지만
실제로는 0.82× 로 **단일보다 느리다**. 짧은 프롬프트에서는 노드를 늘리면 손해다.

이것은 모델의 **정성적 예측이 맞는 방향**이다 — `M`이 `N`에 못 미치면 파이프라인이
성립하지 않는다. 다만 정량적으로는 크게 빗나간다(21 %).

### 정리 — 처방

```
유효 노드 수 상한:  N <= M = S / B_min
청크 크기:          B_min (=16~32) 을 유지. 길이에 따라 줄이지 말 것
```

현재 코드의 휴리스틱은 이 처방과 반대로 작동한다. 긴 프롬프트일수록 손해가 커진다.
