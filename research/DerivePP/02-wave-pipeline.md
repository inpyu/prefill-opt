# 02. Wave-Pipelined Microbatch PP — 핵심 엔진

**이 하나가 4.14~4.51× 를 만들었다.** 나머지는 그 위의 보정이다.

## 2.1 문제 다시 보기

레이어를 8노드에 나누면 경계마다 활성값을 넘겨야 한다. 순차 실행이면:

```
Stage 0:  C ──▶ D ──────────────────────────────────
Stage 1:       ......... C ──▶ D ───────────────────
Stage 2:                  ......... C ──▶ D ────────
                          ↑ 놀고 있다
```

전송 `D` 가 그대로 총시간에 더해진다. 100 Mb 구간에서 한 번 건널 때 18 ms 이고,
마이크로배치가 151개면 2.4 s 다.

## 2.2 해법 — 프롬프트를 마이크로배치로 쪼개 파도처럼 흘린다

프롬프트를 `B` 토큰짜리 마이크로배치로 나눠, 스테이지에 연속으로 밀어 넣는다.

```
Stage 0:  MB0 → MB1 → MB2 → MB3
Stage 1:        MB0 → MB1 → MB2 → MB3
Stage 2:              MB0 → MB1 → MB2 → MB3
Stage 3:                    MB0 → MB1 → MB2 → MB3
```

**스테이지 1이 MB0 을 계산하는 동안, 스테이지 0은 이미 MB1 을 계산한다.**
그리고 MB0 의 활성값 전송은 그 계산들과 **겹친다.**

느린 링크를 건너는 전송이 다른 스테이지의 계산 뒤로 숨는다. 이것이 전부다.

## 2.3 형식화 — 완료시각 재귀

두 완료시각을 둔다.

- `F_{k,j}` : 스테이지 `k` 가 마이크로배치 `j` 의 **계산**을 끝낸 시각
- `E_{k,j}` : 스테이지 `k` 가 `j` 의 **전송**까지 끝낸 시각

```
E_{k,j} = max( F_{k,j},   E_{k,j−1} ) + D_k(j)
F_{k,j} = max( E_{k−1,j}, F_{k,j−1} ) + C_{k,j}        (k > 0)
F_{k,−1} = 0,  E_{k,−1} = 0
```

`E_{k,j−1}` 항이 **링크 직렬화**다 — 같은 링크로 앞 마이크로배치를 아직 보내는
중이면 기다려야 한다. 통신이 충분히 짧아 이를 무시할 수 있으면

```
F_{k,j} = max( F_{k−1,j} + D_{k−1}(j),  F_{k,j−1} ) + C_{k,j}
```

로 줄어든다. 이 재귀는 [05](05-sharedpack.md) 의 이득 분해에도 그대로 쓴다.

## 2.4 구현에서 중요했던 것

### 중간 청크의 로짓을 보내지 않는다

처음엔 마지막 스테이지가 매 마이크로배치의 로짓을 root 로 보냈다. 그러자
**마지막 스테이지의 send 가 막혔다**(실측 5,667 ms).

```
마이크로배치당 로짓 = B × vocab × 4 = 16 × 128,256 × 4 = 8.2 MB
28개면 230 MB
```

root 는 마이크로배치를 밀어 넣느라 이걸 즉시 읽지 않는다. 소켓 버퍼가 차고
send 가 블록된다. 파이프라인 처리량은 `1/max(스테이지)` 이므로 전체가 끌린다.

**prefill 이 실제로 필요로 하는 로짓은 프롬프트 마지막 토큰의 것 하나뿐이다.**
디코드가 마지막 실제 토큰부터 시작하기 때문이다. 그래서:

- 중간 청크는 로짓을 아예 보내지 않는다 (`isLastPrefillChunk`)
- 마지막 청크도 **마지막 행만** 보낸다
- `lm_head` 도 prefill 동안 마지막 행만 계산한다 (`lmHeadRowRange`)

### root 가 기다리지 않는다

`forwardPrefillNoWait()` — root 는 자기 스테이지를 계산하고 활성값을 보낸 뒤
**로짓을 기다리지 않고** 다음 마이크로배치로 넘어간다. 드레인은 마지막에 한 번.

## 2.5 효과

| Prompt | Wave-PP 엔진 | 마이크로배치 선택 | 최종 |
|---|---|---|---|
| S=447 | **4.14×** | 1.132× | **4.68×** |
| S=1789 | **4.51×** | 1.013× | **4.57×** |

로컬 llama.cpp 대비다. 곱셈 분해는 `T_llama/T_B16 = (T_llama/T_B32) × (T_B32/T_B16)`.

그리고 **공식 distributed-llama 가 붕괴한 바로 그 구성**(8 GB 군을 포함해
100 Mb 업링크를 건너는 배치)에서:

```
확장 폭이 오히려 커진다:   3.82×  →  6.64×
```

자기 단일 노드 대비 8노드에서 6.64×, **효율 83%** 다.
링크가 10배 비대칭인 조건에서 나온 값이다.

## 2.6 한계와 열린 지점

- **`N` 축은 아직 A/B 를 하지 않았다.** 확장 곡선의 `N` 은 노드 구성과 교락돼
  있다 — `N≤4` 는 16 GB 군만 쓰고 `N=8` 은 8 GB 군을 포함한다.
  따라서 순수 `N` 효과가 아니라 **배치 계획 `(N, π)`** 비교로 표기해야 한다.
- 완료시각 모델의 **절대 예측은 길이에 따라 무너진다**(§7.14). 형식은 서 있으나
  예측기로는 쓰지 않는다. 쓰는 것은 **계획 쌍 비교**다 → [04](04-axiscert.md)
- wave 경로는 비-wave 경로와 **수치가 다르다.** 활성값을 q80 로 전송하기 때문이며
  SharedPack 이전부터 있던 성질이다. 정확성 비교는 반드시 **같은 wave 조건 안에서**
  해야 한다 (`research/19` §8.2).
