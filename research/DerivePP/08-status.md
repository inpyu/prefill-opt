## 8.2 진행 중 — 일반성 스윕

**48회 조합.** `prompt {447, 1789, 7212} × B {16, 32} × threads {1, 4}`, N=8 wave on.
조합마다 `A,B,B,A` 4회를 **연달아** 돌려 같은 세션 안에서만 비율을 만든다.

첫 조합 결과:

```
s447 B16 t4    A gm 6,523.5 → B gm 4,400.9    R = 1.4823
               syncWait 2,595 → 1,232
               non-wait residual 3,928 → 3,169  (1.240×)
```

**B=16 이 B=32(1.426×)보다 이득이 크다.** 배치가 작을수록 pack 중복 비중이 커진다는
예측과 방향이 맞는다. 다만 아직 1조합이라 확정이 아니다.

harness `prefill_bench/generality.sh`, artifact `artifacts/generality/`.

## 8.3 다음 작업 — 우선순위

| # | 작업 | 왜 이 순서인가 |

### 1번의 설계

`research/16` 의 completion recurrence 로 counterfactual 을 네 번 계산한다.

```
F_{k,j} = max( F_{k−1,j} + D_{k−1}(j),  F_{k,j−1} ) + C_{k,j}
```

| # | C (stage compute) | D (link) | 묻는 것 |
|---|---|---|---|
| 1 | BASE | BASE | 재현 기준선 |
| 2 | **영향받은 matmul 만** SP | BASE | 그 projection 들의 개선율이 N=1 평균보다 컸는가 |
| 3 | 모든 stage compute SP | BASE | 링크 고정해도 1.426× 가 나오는가 |
| 4 | SP | SP | 실측과 일치하는가 (모델 타당성) |

**3번이 1.426× 를 재현하지 못하면, TTFT 개선의 일부는 SharedPack 으로 귀속할 수
없다.** 그 가능성을 열어둔다.

## 8.5 절대 하지 말 것

```
4.57×  ×  1.436×  =  6.56×        ← 이 곱셈을 하지 않는다
```

베이스라인·세션·조건이 다르다. 최종 시스템 대 llama.cpp 는 **동일 조건에서
다시 재야 한다.** 그 전까지 두 수치는 각각 별도로만 보고한다.

그리고 다음 표현들도 쓰지 않는다.

```
"pipeline amplification"                        ← 관측이지 설명이 아니다
"스테이지가 빨라져 bubble 이 줄었다"              ← 슬롯 수·비율이 준 게 아니다
"연산 1.20× + syncWait 1.77× 이득"               ← 이중 계산
"다른 엣지 가속은 정확도를 희생하지만 우리는 아니다"  ← 근거 없음
```
