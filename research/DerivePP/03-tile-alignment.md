# 03. 타일 정렬 스케줄링 — 계단 비용과 파이프라인 누적

wave 파이프라인이 서고 나서 **마이크로배치 크기 `B` 를 얼마로 할 것인가**가
남는다. 이게 단순한 튜닝이 아니었다.

## 3.1 문제 — 비용 함수가 계단이다

Q4_0 repack GEMM(`ggml_gemm_q4_0_4x4_q8_0`)은 **4행 단위**로 돈다.
나머지 1~3행은 훨씬 느린 gemv 로 처리된다. llama.cpp 계열의 표준 구조다.

실측:

```
c(15) = 327 ms
c(16) = 148 ms      ← 토큰이 하나 더 많은데 2.2배 빠르다
```

단일 실행이면 한 번 손해보고 끝이다. **파이프라인에서는 다르다.**

## 3.2 왜 파이프라인에서 치명적인가

초과분을 `e` 라 하면 스테이지 `k` 의 완료시각은

```
스테이지 k 완료 = (m + k − 1)·c + k·e
```

앞 스테이지의 지연 위에 자기 초과분이 **더해지고 회복되지 않는다.**
즉 손실이 `N·e` 로 **스테이지 수만큼 누적**된다.

실측으로 세 번 확인했다. 나머지 청크를 **마지막에 두든, 1번에 두든, 중앙에 두든**
손실이 `1,100~1,400 ms` 로 동일했다.

> **안전한 위치가 없다.** 재배치로는 풀리지 않는다.

## 3.3 해법 — 비정렬 자체를 없앤다

`S=447` 은 `3 × 149` 라서 16 근처 어떤 `B` 로도 나누어떨어지지 않는다.
그래서 **위치를 패딩**해 모든 마이크로배치를 `B` 배수로 만든다.

올림 단위는 **청크 크기가 아니라 GEMM 타일 행 수(4)** 다.

```
schedTotal = ceil(realTotal / 4) × 4
```

청크 크기로 올리면 짧은 프롬프트에서 크게 낭비된다(13토큰 → 32위치).
`batchSize % 4 == 0` 이면 절벽이 없으므로 4로 충분하다.

```
비용   토큰 ≤ B−1 개 (S=447 에서 1개, 0.2%)
이득   N·e ≈ 20%
```

패딩 위치는 마지막 실제 토큰을 반복해 채운다. **prefill 의 로짓은 쓰이지 않고**
(디코드가 마지막 실제 토큰부터 시작한다), 패딩 위치의 KV 는 디코드 첫 스텝이
덮어쓴다. 그래서 정확성에 영향이 없다.

## 3.4 `B` 선택의 효과

| Prompt | 마이크로배치 선택 이득 |
|---|---|
| S=447 | **1.132×** |
| S=1789 | **1.140×** (anchor 9회, J2 의 1.136× 와 독립 재현) |

`S=1789` 에서 한때 **1.013×** 로 보였던 적이 있다. 그것은 **세션 간 비교의
인공물**이었다. 같은 세션 안에서 교차 앵커로 다시 재니 1.140× 가 나왔다.

> 이 사건이 [07-measurement.md](07-measurement.md) 의 "같은 세션 안에서만 비율을
> 만든다" 규칙을 만든 계기다.

## 3.5 `B` 는 `S` 의 단조 함수가 아니다

직관적으로는 프롬프트가 길수록 배치를 키우는 게 맞아 보인다. **틀렸다.**

```
최적 B:   S=512 → 16,   S=2048 → 32,   S=7212 → 16
```

단조가 아니다. 그래서 `B ∝ S` 도 `B ∝ √S` 도 **기각했다**
→ [06-rejected.md](06-rejected.md)

대신 캘리브레이션한 격자에서 고른다.

```
ℬ_cal = {4, 8, 12, 16, 24, 32, 48, 64, 96, 128}
```

`B_min = 16` 이 Pi 5 의 성능 knee 다.
