# 03. `B` — Wave Pipeline 의 실행 파라미터

> **위치.** `B` 는 최적화 "축" 이 아니라 **Wave Pipeline 의 실행 파라미터**다.

## 3.1 상충 관계

wave 실행 시간은 대략 이렇게 쓸 수 있다.

```
T_wave(S, N, B)  ≈  ( ceil(S/B) + N − 1 ) · c(B)
```

- `ceil(S/B)` : 마이크로배치 수
- `N − 1` : 파이프라인 채우는 데 드는 스테이지 수 (bubble)
- `c(B)` : 마이크로배치 하나의 스테이지 계산 시간

여기서 상충이 바로 보인다.

```
B 가 크면   →  마이크로배치 수가 줄어 bubble 비중(N−1)이 커진다
B 가 작으면 →  c(B)/B 가 나빠진다. SDOT/GEMM 효율이 떨어진다
```

## 3.2 `c(B)` 는 매끄럽지 않고 계단이다

Q4_0 repack GEMM 은 **4행 단위**로 돌고 나머지 1~3행은 훨씬 느린 gemv 로 간다.
llama.cpp 계열의 표준 구조다.

```
c(15) = 327 ms
c(16) = 148 ms      ← 토큰이 하나 더 많은데 2.2배 빠르다
```

단일 실행이면 한 번 손해보고 끝이다. **파이프라인에서는 누적된다.**
초과분을 `e` 라 하면

```
스테이지 k 완료 = (m + k − 1)·c + k·e
```

앞 스테이지의 지연 위에 자기 초과분이 더해지고 **회복되지 않는다.**

실측으로 세 번 확인했다 — 나머지 청크를 **마지막에 두든, 1번에 두든, 중앙에 두든**
손실이 `1,100~1,400 ms` 로 동일했다. **안전한 위치가 없다.**

## 3.3 해법 — 타일 정렬 패딩

비정렬 자체를 없앤다. 올림 단위는 **청크 크기가 아니라 GEMM 타일 행 수(4)** 다.

```
schedTotal = ceil(realTotal / 4) × 4
```

청크 크기로 올리면 짧은 프롬프트에서 크게 낭비된다(13토큰 → 32위치).
`batchSize % 4 == 0` 이면 절벽이 없으므로 4로 충분하다.

```
비용   토큰 ≤ B−1 개 (S=447 에서 1개, 0.2%)
이득   N·e ≈ 20%
```

패딩 위치는 마지막 실제 토큰을 반복해 채운다. **prefill 의 로짓은 쓰이지 않고**
(디코드가 마지막 실제 토큰부터 시작한다), 패딩 위치의 KV 는 디코드 첫 스텝이
덮어쓴다. 정확성에 영향이 없다.

## 3.4 `B` 를 어떻게 고르는가

**해석식으로 예측하지 않는다.** `c(B)` 가 계단이라 닫힌 형태가 없다.
소수의 후보를 **캘리브레이션으로 고른다.**

```
ℬ_cal = {4, 8, 12, 16, 24, 32, 48, 64, 96, 128}
```

`B_min = 16` 이 Pi 5 의 성능 knee 다.

### `B` 는 `S` 의 단조 함수가 아니다

```
최적 B:   S=512 → 16,   S=2048 → 32,   S=7212 → 16
```

`B ∝ S` 도 `B ∝ √S` 도 성립하지 않는다. 그래서 두 규칙 모두 쓰지 않는다.
