# 07. 설계 공간 — 왜 TP/CP/core split/복잡한 partition 이 아닌가

논문 본문에는 이 절이 **짧게** 들어간다. 최종 시스템이 왜 지금의 형태인지
설명하는 데 필요한 만큼만이다. 상세 근거는 `research/16` §12 에 있다.

---

## 7.1 최종 시스템의 구성

```
병렬화        pipeline parallel 만 사용    (PP=8, SP=1, TP=1)
레이어 분할   균등                          (8,8,8,8,8,8,8,8 서브블록 = 4레이어씩)
마이크로배치  캘리브레이션 격자에서 선택     (B=16 또는 32)
활성값 전송   q80                           (1.06 B/원소)
```

단순하다. **그게 요점이다.** 저속 링크에서는 통신을 늘리는 어떤 병렬화도
곧바로 손해로 돌아온다.

---

## 7.2 왜 Tensor Parallel 이 아닌가 — 통신 회계

TP 는 레이어 **안**을 쪼개므로 매 레이어마다 all-reduce/all-gather 가 필요하다.
PP 는 레이어 **경계**에서만 활성값을 한 번 넘긴다.

```
PP  활성값 1회 전송 / 레이어 경계.  B=48, d=4096 → 209 kB
TP  집합 통신 1회 이상 / 레이어.    32 레이어 전부에서 발생
```

우리 링크에서 209 kB 한 번을 건너는 비용:

```
1 GbE 경계:  0.083 + 209/115.7 = 1.9 ms
100 Mb 경계: 0.126 + 209/11.7  = 18.0 ms
```

**현재 스테이지 순서는 100 Mb 업링크를 정확히 1회만 횡단한다.**

```
실측 유효 전송시간 16.1 ms × M=151  ≈  2.4 s
(모델식 18.0 ms 를 쓰면 ≈ 2.7 s. 두 값을 섞지 않는다)
```

그 실험(`S_real=1789`, `B=48`, `N=8`)의 전체 prefill 시간을 분모로 하면 **약 1.3%** 다.

TP 를 쓰면 이 횡단이 레이어마다 발생한다. 저속 구간에서 감당할 수 없다.
그리고 TP 의 집합 통신은 **계산 뒤로 숨기기도 어렵다** — 모든 참가자가
동기화 지점에 도달해야 하기 때문이다. Wave Pipeline 의 전제 자체가 무너진다.

---

## 7.3 왜 stage 내부를 더 쪼개지 않는가 — 두 대안, 두 근거

**core split 과 context-parallel island 은 서로 다른 근거로 닫힌다.**
하나의 보조정리로 둘을 함께 닫을 수 없다.

### 7.3.1 core split — 직접 측정으로 기각

스테이지 안에서 코어를 나눠 두 작업을 동시에 돌리는 방식이다.
직접 재보니 **느려졌다.**

```
261.4 ms  →  270.2 ms        G = 0.967×
```

해석식이 아니라 측정 결과다. 이 축은 여기서 닫힌다.

### 7.3.2 context-parallel island — 조건부 상한 + 프로토콜 비용

두 physical stage 를 하나의 logical stage 로 합쳐 그 안에서 토큰을 나누는 방식이다.
**아래 조건이 모두 성립할 때만** 다음 상한이 유도된다.

| 조건 |
|---|
| physical node 수와 총 연산 용량이 고정 |
| 두 physical stage 를 하나의 logical stage 로 합침 |
| 병렬화가 stage service time 자체를 줄이지 **않음** |
| 얻는 것은 logical stage 수가 `N → N−1` 로 줄어드는 효과뿐 |
| 통신과 간섭 비용은 0 으로 낙관 |

이때

```
T_before = (M + N − 1)·c
T_after  ≥ (M + N − 2)·c
```

이므로

```
speedup  ≤  (M + N − 1) / (M + N − 2)
상대 개선 ≤  1 / (M + N − 2)
```

`S=1789`, `B=32`, `N=8` 이면 `M=56` 이므로 상대 개선 상한이 `1/62 ≈ 1.6%` 다.
**낙관적 상한이 이미 1.6%** 인데 여기에 Ethernet 프로토콜 비용이 더해지므로 닫힌다.

> **적용 범위 주의.** 이 상한은 **모든 intra-stage 병렬화의 상한이 아니다.**
> CP 가 attention 의 service time 자체를 줄이거나 core split 이 커널 효율을
> 바꾸는 경우에는 위 조건 중 세 번째가 깨지므로 **그대로 적용할 수 없다.**
> 그래서 core split 은 §7.3.1 의 직접 측정으로 따로 닫았다.

## 7.4 왜 복잡한 레이어 분할이 아닌가 — 측정으로 껐다

**att/ff 서브블록 분할** (32 레이어 → 64 서브블록)은 분할 입자도를 두 배로 만들어
스테이지 균형이 좋아질 것으로 기대됐다. 그런데 end-to-end A/B 에서 **비활성**이다.

```
S=1789   비활성
S=7212   0.986 / 1.000     (깨끗한 재측정 J4-R)
```

"긴 프롬프트에서는 살아난다" 는 직관도 틀렸다. **교차점 양쪽 모두에서 죽어 있다.**

**구조적 이유.** 8 GB / 16 GB 군이 **같은 CPU** 라 노드 성능 이종성이 작다.
차이는 RAM 용량이고 그건 계산 속도가 아니다. 균등 분할이 이미 거의 최적이다.

같은 이유로 **operator/topology-aware placement `π`** 도 철회했다 —
근거였던 순위 역전이 재현되지 않았다 (Kendall τ: −0.29 → +0.111).

---

## 7.5 요약

| 대안 | 왜 아닌가 | 근거 유형 |
|---|---|---|
| Tensor Parallel | 레이어마다 집합 통신. 저속 구간에서 감당 불가. 계산 뒤로 숨기기도 어려움 | 통신 회계 |
| core split | 직접 측정 `G = 0.967×` — 느려진다 | end-to-end 측정 |
| context-parallel island | 조건부 상한 `1/(M+N−2)` ≈ 1.6% + 프로토콜 비용 | 조건부 상한 |
| att/ff 서브블록 분할 | 두 길이 모두에서 비활성 | end-to-end A/B |
| placement 공동 최적화 | 근거가 재현되지 않음. 노드 이종성이 애초에 작음 | 재현 실패 |

**결론.** 저속·비대칭 링크에서는 **통신을 최소로 두고 그것마저 계산 뒤로 숨기는**
구조가 이긴다. 그것이 Wave Pipeline 이고, 남는 낭비는 노드 **안**에 있었다.
그것이 SharedPack 이다.
