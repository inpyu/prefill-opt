# 01. 문제 — 왜 이 개발을 했는가

## 1.1 하드웨어가 준 제약

라즈베리파이 5 여덟 대다. **16 GB 4대 + 8 GB 4대**, 전부 같은 CPU(4코어)다.

```
16 GB 군   105 / 113 / 166 / 191    ─┐
                                     ├─ 메인 스위치 ── 업링크 100 Mb ──┐
8 GB 군    103 / 94 / 104 / 54     ─┘                                 │
```

링크를 `D(x) = α + x/β` 로 적합해 실측했다(`prefill_bench/bench_link.cpp`,
64 B~4 MB 왕복).

| 경로 | α (ms) | β (MB/s) |
|---|---|---|
| 16 GB 군 내부 | 0.083~0.085 | **115.7~117.0** |
| 8 GB 군 내부 | 0.084~0.087 | **115.5~116.9** |
| **군 간** | 0.126 | **11.7** |

**RAM 이 아니라 토폴로지 문제다.** 모든 노드가 `1000Mb/full` 로 협상돼 있고
8 GB 노드끼리도 115.6 MB/s 가 나온다. 메인 스위치와 하위 스위치를 잇는
**업링크가 100 Mb** 인 것이 원인이고, RAM 용량과의 상관은 배치의 부산물이다.

즉 **링크가 10배 비대칭**이다. 이것이 이 연구의 출발 조건이다.

> `iperf` 같은 대용량 스트리밍으로는 `α` 를 잡을 수 없고, ssh 왕복은 프로토콜
> 처리 시간이 섞여 무효다. 전용 echo 서버/클라이언트가 필요했다.

## 1.2 왜 TTFT(prefill)인가

LLM 추론은 두 단계다.

```
prefill   프롬프트 전체를 한 번에 처리해 KV 캐시를 만든다.  계산 집약(GEMM)
decode    토큰을 하나씩 만든다.                              메모리 대역 집약(GEMV)
```

**첫 토큰까지의 지연(TTFT)은 prefill 이 결정한다.** 그리고 prefill 은 배치
차원이 있어 GEMM 으로 돌아가므로, decode 와 달리 **계산을 나눌 여지가 크다.**
엣지에서 대화형 응답성을 좌우하는 것도 TTFT 다.

decode 는 이미 메모리 대역에 묶여 있어 노드를 늘려도 얻는 것이 적다.
그래서 **prefill 에 집중했다.**

## 1.3 기존 공개 구현이 왜 실패하는가

같은 하드웨어·모델·양자화·스레드 수·프롬프트에서 재보니 **분산이 오히려 손해**였다.

| 시스템 | 노드 | 로컬 CPU 대비 |
|---|---|---|
| llama.cpp RPC | N=2 | 최대 **0.41×** |
| 공식 distributed-llama | N=4 | 최대 **0.44×** |

원인을 추측이 아니라 **소스로 확인**했다.

- **llama.cpp RPC** — 비동기 pipeline 경로가 소스에 없다.
  `set/get/cpy_tensor_async` 계열이 구현되지 않아 매 경계에서 블로킹 왕복이 생긴다.
  통신이 계산 뒤로 숨지 못하므로 노드를 늘릴수록 왕복 횟수만 는다.
- **공식 distributed-llama** — 100 Mb 업링크를 건너는 순간 붕괴한다.
  활성값을 매 레이어 경계에서 전량 주고받는 구조라 대역이 그대로 벽이 된다.

**이것이 개발의 직접적 동기다.** "분산하면 빨라진다" 가 이 환경에서는 성립하지
않았고, 성립시키려면 **통신을 계산 뒤로 숨기는 구조**가 필요했다.

## 1.4 왜 어려운가 — 노드 사이의 두 벽

### 벽 1. 통신이 계산과 겹치지 않는다

레이어를 노드에 나누면(pipeline parallel) 경계마다 활성값을 넘겨야 한다.
순차 실행이면 `계산 → 전송 → 계산 → 전송` 이라 전송 시간이 그대로 더해진다.
100 Mb 구간에서는 이게 치명적이다.

```
B=48, d=4096 → 209 kB
  1 GbE 경계:  0.083 + 209/115.7 = 1.9 ms
  100 Mb 경계: 0.126 + 209/11.7  = 18.0 ms      ← 9.5배
```

### 벽 2. 커널 비용이 계단이다

Q4_0 repack GEMM 은 4행 단위로 돌고 나머지는 느린 gemv 로 처리한다.
그래서 배치 크기에 대한 비용이 **매끄럽지 않고 계단**이다.

```
c(15) = 327 ms  >  c(16) = 148 ms      토큰이 더 적은데 2.2배 느리다
```

파이프라인에서는 이 초과분이 **스테이지 수만큼 누적**된다. 회복되지 않는다.

## 1.5 벽 3 — 노드 안에서도 CPU 가 논다

위 두 벽은 **노드 사이** 문제다. 그런데 노드 **안**에도 같은 성격의 낭비가 있다.

Q4_0 repack GEMM 은 스레드를 **출력 열**로 나눈다. 그런데 모든 스레드가
**배치 전체의 activation** 을 필요로 한다. executor 는 op 경계에서만 동기화하고
op 내부 배리어가 없다. 그래서 **각 스레드가 activation 전체를 자기 스크래치에
중복 변환한다.**

```
스레드 0:  activation 전체 → 자기 packed copy → 자기 output column
스레드 1:  activation 전체 → 자기 packed copy → 자기 output column
스레드 2:  ...
스레드 3:  ...
```

pack 연산량 자체는 전체의 **0.30%** 에 불과하다. 문제는 **4개의 독립 cache
footprint** 가 생겨 4스레드 확장이 무너지는 것이다.

| 스레드 수 | duplicate vs shared |
|---|---|
| 1~3 | 1.00~1.03× (차이 없음) |
| **4** | **1.68×** |

## 1.6 두 계층은 같은 병이다

```
노드 사이:  데이터를 넘길 때마다 기다린다        → 통신이 계산과 안 겹친다
노드 안:    소비자마다 데이터를 다시 준비한다     → cache 를 중복 점유한다
```

공통 원리로 묶인다.

> **데이터를 소비자마다 반복 준비하지 않고, 적절한 계층에서 한 번 materialize 한 뒤
> 파이프라인으로 전달하거나 공유한다.**

## 1.8 스스로에게 건 제약

측정과 일반성을 지키기 위해 처음부터 금지한 것들이다.

| 금지 | 이유 |
|---|---|
| 커널 수정에 의존하는 설계 | 일반성이 떨어진다. 다른 플랫폼으로 안 옮겨간다 |
| 양자화 변경 | 정확도를 대가로 지불한다. 공정 비교가 깨진다 |
| 모델 재로드 기반 재분할 | 측정에 로드 시간이 섞인다 |
| 런타임 레이어 마이그레이션 | KV 일관성이 깨진다 |
| 온도 기반 접근 | 재현되지 않는다 |
| Tailscale(100.x) 사용 | WireGuard 오버레이가 통신 측정을 오염시킨다. **공인/LAN IP 만** |
