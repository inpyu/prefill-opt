# 설계: 균형 인지 2D 타일링 prefill (Ring CP)

**이것이 제안 알고리즘의 최종 형태다.** [07](07-design-block-parallel.md) 의 블록 병렬(근사)은
정확도 검증에서 기각됐고, 그 과정에서 얻은 측정이 이 설계의 근거가 된다.

---

## 1. 통합 원리: 병렬성과 산술 강도는 상충한다

노드 하나에 **토큰 B개**와 **가중치의 f 비율**을 할당한다고 하면:

$$
\text{연산}=\frac{B f C_{\text{layer}}}{P},\qquad
\text{메모리}=\frac{f W_{\text{layer}}}{BW},\qquad
\textbf{산술 강도}=\frac{B\,C}{W}
$$

**산술 강도는 `B` 에만 의존하고 `f` 와 무관하다.** 여기서 두 분할 축의 성격이 갈린다.

| | 토큰 축 (CP) | 텐서 축 (TP) |
|---|---|---|
| 노드당 토큰 `B` | **S/N** ← 강도 하락 | S ← 강도 유지 |
| 노드당 가중치 `f` | 1 (전체 복제) | 1/N |
| 통신 | ring KV — **attention(7.5 %)에만** | 레이어당 all-reduce ×2 |

> **토큰 축은 통신이 싸지만 산술 강도를 희생하고, 텐서 축은 강도를 지키지만 통신이 비싸다.**

이 하나의 상충이 지금까지 관측한 모든 현상을 설명한다.

| 관측 | 이 틀에서의 해석 |
|---|---|
| 블록 ≥ 32토큰 제약 | `B` 가 강도 임계 밑으로 내려감 |
| 청크 32 → FFN 가중치 44 GB 재스트리밍 | `B` 가 작아 강도가 낮음 (같은 문제) |
| TP2 가 1.13× 에 그침 | 강도는 지켰으나 배리어 64회 |
| PP 실패 (0.95×) | 두 축 어디에도 속하지 않음 — 깊이는 순차 |
| 블록 병렬 근사 실패 | `B` 를 줄이려다 **문맥까지** 잘라버림 (§2) |

### 알고리즘 = 인수분해 문제

prefill 작업을 (토큰 × 가중치) 2차원 격자로 보고, 노드 수를
$N = N_{tok}\times N_{ten}$ 으로 인수분해한다.

$$
T(N_{tok},N_{ten})=\underbrace{\max\!\Big(\tfrac{BfC}{P},\ \tfrac{fW}{BW}\Big)L}_{\text{연산·메모리}}
+\underbrace{2LN_{ten}\tau}_{\text{TP 배리어}}
+\underbrace{\text{ring}(N_{tok})}_{\text{FFN 뒤에 은닉}}
$$

`B = S/N_tok`, `f = 1/N_ten`. 두 상수는 **이 클러스터에서 직접 측정**했다.

| 상수 | 값 | 출처 |
|---|---|---|
| 기계 균형 | 11~14 FLOP/byte | 110 GFLOPS ÷ 8~10 GB/s |
| 배리어 τ | **16.3 ms** | TP2 syncWait 14,611 ms ÷ 896회 |

| S | N | 최적 인수분해 | 이유 |
|---|---|---|---|
| 447 | 4 | **(4, 1)** 순수 토큰 축 | B=112 ≥ 32, 통신 거의 0 |
| 447 | 28 | (14, 2) | B=32 하한, 남는 2배는 텐서 축 |
| 112 | 8 | (3, 2~3) | 짧아서 토큰 축 여지가 적음 |

**기존 연구는 분할 축을 고정하고 최적화한다** — Ring Attention 은 토큰 축, Megatron 은
텐서 축, Galaxy 는 정적 하이브리드다. 전부 GPU 전제라 대역폭이 넉넉해 **산술 강도가
문제되지 않고 통신 비용만 본다.** 우리 주장은 하나다:

> 대역폭이 희소한 CPU 클러스터에서는 **분할 자체가 산술 강도를 깎는다.**
> 따라서 최적 분할은 "통신 최소화"가 아니라 **"강도 유지와 통신의 균형"** 이며,
> 그 균형점은 측정된 두 상수로 결정된다.

## 2. 왜 근사(블록 병렬)를 버렸는가 — 실측

[07](07-design-block-parallel.md) 의 블록 독립 인코딩을 단일 노드에서
**attention 마스크만 바꿔** 검증했다 (분산 코드 없이 정확도만 측정).

**검산 통과**: `blockSize = 4096`(마스크 무효)일 때 baseline 과 생성 토큰 md5 동일.

| 구성 | 생성 텍스트 (53토큰) |
|---|---|
| baseline | `clock frequency unevenly across nodes, producing stragglers that collective operations cannot hide...` |
| 블록 112 | `That one may be the only way to do not have to do not have to. To do not have to...` |
| 블록 112 + anchor 32 | `that cache. The key in addition to the cache. The key in addition to the cache...` |
| 블록 56 | `the key. The key to the key to the key to the key to...` |
| 블록 56 + anchor 32 | `the cost of the system. The system is the system. The system is...` |

**전부 반복 루프에 빠졌다. anchor 로도 회복되지 않는다.**

### 원인: 블록 크기가 절대적으로 부족하다

| | Star Attention | 우리 |
|---|---|---|
| 프롬프트 | 128 K | **447 토큰** |
| 블록 크기 | 16~32 K | **56~112 토큰** |
| 블록당 문맥 | 문단 수십 개 | **문장 2~3개** |

128 K 를 8블록으로 쪼개면 블록당 16 K 로 충분한 문맥이 남지만,
447토큰을 4블록으로 쪼개면 **문장 두어 개**다. 그 안에서만 attention 하면 맥락이 없다.

> 07 초안에서 "블록 수가 적어 오히려 유리하다"고 썼던 것은 **틀렸다.**
> 블록 *수*가 아니라 블록 *크기*가 문제이며, 짧은 프롬프트 체제에서
> 블록 독립 인코딩은 성립하지 않는다.

**이 부정 결과가 exact 를 택한 근거가 된다.** 근사를 검토했고 왜 안 되는지 실측으로 보였다.

## 3. Ring CP — 구조

```
S=447, N=4  →  블록 112 토큰
노드 0: 0..111    노드 1: 112..223    노드 2: 224..335    노드 3: 336..446
```

레이어 하나에서 각 노드가 하는 일:

| 단계 | 통신 | 비중 |
|---|---|---|
| ① 자기 토큰의 Q,K,V 계산 | 없음 | (projection 15 %) |
| ② attention — 자기 쿼리 × 모든 이전 K,V | **여기만** | 7.5 % |
| ③ 자기 토큰의 FFN | 없음 | 76 % |

**①③ 이 87.9 % 이고 통신이 0이다.**

### causal 이라 "ring" 이 아니라 "앞으로만 전달"

```
노드 0 : 자기 것만          → 수신 0회
노드 1 : 블록 0             → 1회
노드 2 : 블록 0,1           → 2회
노드 3 : 블록 0,1,2         → 3회
```

총 전송 `N(N−1)/2 = 6`회. 양방향 ring 의 절반이다.

### online softmax 가 필요 없다

Ring Attention 논문들은 블록별 부분 attention 을 online softmax 로 합친다.
**우리는 그럴 필요가 없다** — dllama 의 KV 버퍼가 이미 전체 `seqLen` 으로 잡혀 있다
(`sliceKvCache` → `size2D(F_32, seqLen, kvDim0)`).

```
노드 2 의 KV 버퍼
┌─────────┬─────────┬─────────┬ ─ ─ ─ ┐
│ 블록 0  │ 블록 1  │ 블록 2  │ 미사용 │
│ 수신    │ 수신    │ 자기것  │        │
└─────────┴─────────┴─────────┴ ─ ─ ─ ┘

→ 기존 causal attention 을 [0, 336) 범위로 그대로 실행
```

받은 KV 를 제자리에 써 넣고 **기존 커널을 그대로** 쓴다.
**수학적으로 단일 노드와 완전히 동일**하므로 검증이 byte-for-byte 비교로 끝난다.

> 대가: 노드 N−1 이 전체 KV 를 보유(메모리 절감 없음).
> S=447 에서 KV 는 117 MB 라 무관하다. 긴 프롬프트에서 문제되면 그때 online softmax 로 전환.

## 4. 핵심 설계: 통신을 FFN 뒤에 숨긴다

```
KV 블록 = 112 × 1024 × 2 × 4B = 918 KB
레이어당 노드 평균 수신 ≈ 1.4 MB  →  1GbE 에서 12.3 ms
```

| 레이어당 (N=4) | 시간 |
|---|---|
| **FFN 연산** | **202 ms** |
| ring KV 전송 | **12.3 ms** |

**16배 여유.** FFN 은 토큰 간 의존이 없어 통신과 완전히 겹친다.

> GPU 연구는 통신을 **attention 연산** 뒤에 숨기려다 대역폭에 막힌다
> ([Ring Attention](https://arxiv.org/abs/2310.01889),
> [Tree Attention](https://arxiv.org/pdf/2408.04093),
> [Long-Context Attention Benchmark](https://arxiv.org/pdf/2510.17896)).
> **CPU 는 FFN 이 76 % 라 숨길 곳이 넉넉하다.** 우리 체제에서만 성립하는 스케줄링이다.

### 스케줄

```
레이어 l:
  1. Q,K,V 계산
  2. 자기 KV 블록을 뒤쪽 노드로 비동기 송신     ← 여기서 발사
  3. attention (이미 받은 블록들로)
  4. FFN                                      ← 이 동안 전송이 완료됨
  5. 레이어 l+1 로
```

## 5. 부하 불균형 — zigzag

causal 이라 뒤쪽 노드가 더 계산한다(노드 3 이 노드 0 의 4배).
토큰을 2N 조각으로 쪼개 노드 i 에게 **조각 i 와 조각 (2N−1−i)** 를 준다.

```
조각:  0  1  2  3  4  5  6  7      (각 56토큰)
노드0: ■              ■
노드1:    ■        ■
노드2:       ■  ■
노드3:          ■■
```

앞 조각은 가볍고 뒤는 무거워 짝지으면 균등해진다.

> **이종 노드에서는 이 불균형을 역이용**한다 — 빠른 노드에 뒤쪽 조각을 몰아준다.
> 8 GB/16 GB 혼합 클러스터에서 유용하다.

## 6. 예상 성능

```
T(N) = GEMM/N + attention/N + 노출된 통신

N=4:  32,298/4 + 2,770/4 + ~0  =  8,768 ms  →  4.19×
N=8:  32,298/8 + 2,770/8 + ~0  =  4,384 ms  →  8.38×
```

**exact 인데 근사(3.58×, 품질 붕괴)보다 빠르다.**

한계는 `B ≥ 32` 이므로 `N ≤ S/32` (S=447 → 14).
그 이상은 §1 의 하이브리드 2D 로 넘어간다. **S 가 커지면 상한도 커진다** —
TTFT 가 실제로 문제인 긴 프롬프트에서 가장 잘 확장된다.

## 7. 구현 계획

| # | 변경 | 규모 | 비고 |
|---|---|---|---|
| 1 | `nBatches` = 블록 크기 (32 → B) | 중간 | 그래프 버퍼가 이걸로 잡힌다. **블록 크기 = 청크 크기 = nBatches 가 하나로 통합** |
| 2 | **가중치를 전 노드에 복제** | **가장 큼** | 현재 `loadRowMatmulSlices` 가 슬라이스 전송. 6.32 GB × (N−1) |
| 3 | 노드별 토큰 구간 배정 | 작음 | `controlPacket` 에 blockStart/blockLen |
| 4 | `SYNC_KV_FORWARD` — KV 를 뒤쪽 노드로 | 중간 | 기존 `SYNC_SP_KV`(allgather) 를 참고해 단방향으로 |
| 5 | FFN 뒤 은닉 비동기 스케줄 | 중간 | 송신 발사 후 FFN, 다음 레이어 전에 완료 확인 |
| 6 | zigzag 배정 | 작음 | 3번의 확장 |

**2번이 관건.** [발견 #3](03-attention-batching.md) 의 임베딩 양자화(6.32 → 4.34 GB)를
먼저 하면 전송·로딩이 30 % 빨라진다.

### 순서

```
7-1. 측정 신뢰도 확보 (반복 + 중앙값 + 온도 로깅)   ✔ 완료
7-2. nBatches 를 블록 크기로 (단일 노드에서 먼저 검증)  ✔ 완료 — 단, 결과가 설계를 바꿨다
7-2b. 온라인 소프트맥스 융합                        ← 순서 변경으로 앞당김
7-3. 가중치 복제 배포
7-4. 토큰 구간 배정 + KV 앞으로 전달 (zigzag 없이 균등 분할)
7-5. FFN 뒤 은닉 스케줄
7-6. zigzag
```

### 순서를 바꾼 이유 (7-2 의 실측 결과)

7-2 를 단일 노드에서 검증한 결과, 이 설계의 전제 하나가 **기각**됐다
([06 §4.7](06-baseline-status.md) 전문).

- "블록을 키우면 FFN 가중치 재스트리밍이 줄어 빨라진다" → **아니다.**
  청크를 14 → 4 개로 줄여 재스트리밍을 44.4 → 12.7 GB 로 낮췄는데
  FFN 은 23,721 → 22,702 ms, 1 초뿐이다. GEMM 은 이미 32행에서 compute-bound 다.
- 대신 **attention 이 폭발한다**(B=32 에서 2,548 → B=448 에서 43,838 ms).
  점수 행렬 `att` 가 `(B × nHeads × seqLen × 4B)` 로 실체화되어 L3 2 MB 를 벗어나기 때문이다.

즉 **`B` 에는 캐시 천장이 있다.**

```
B_max ≈ L3 / (nHeads · seqLen · 4)
```

seqLen 704 에서 ≈23, **4096 이면 ≈4**. 프롬프트가 길수록 천장이 낮아지는데,
그건 정확히 CP 가 필요한 영역이다. 이 상태로 7-3(가중치 복제)부터 진행하면
**노드를 늘려도 노드당 블록을 키울 수 없어** 이 설계 전체가 무의미해진다.

따라서 `att` 를 실체화하지 않는 **온라인 소프트맥스 융합을 7-3 앞으로 옮긴다.**
이것은 "attention 을 2~3배 빠르게 하는 선택지"가 아니라 **`B` 를 키우기 위한 전제 조건**이다.

> 융합 커널은 키를 `TILE`(=128) 개씩 끊어 처리하며 running max/sum 을 유지한다.
> 점수 스크래치가 `seqLen` 이 아니라 `TILE` 에 비례하므로 위 천장이 사라진다.
> 구현은 `multiheadAttFused_F32` (`nn-cpu-ops.cpp`), 스위치는 `--attn-fused 0/1`.
> 부동소수점 연산 순서가 달라 bit-exact 하지 않으므로, 검증은 greedy 출력 토큰
> 일치로 한다 — **33 토큰 완전 일치 확인**.

## 8. 검증

**exact 방식의 큰 장점은 정답이 명확하다는 것이다.**

| 검사 | 기준 |
|---|---|
| N=1 실행 | 단일 노드와 **byte-for-byte 동일** |
| **N=4 실행** | 단일 노드와 **byte-for-byte 동일** (exact 이므로) |
| 통신 은닉 | `syncWait + syncXfer` ≪ FFN 시간 |
| 스케일링 | N=1/2/4/8 에서 `T ∝ 1/N` 인가 |

깊이 분해와 블록 병렬에서 검산 지점 덕분에 잘못된 결론을 두 번 피했다.
여기서도 같은 원칙을 적용한다.

### 측정 신뢰도 (선행 과제)

같은 설정 5회 실행의 편차가 크다.

```
51.2 / 33.0 / 32.0 / 31.6 / 34.3 초   (chunk 스윕, 전부 동일 설정)
```

첫 실행이 60 % 튀었다. 열 상태로 보인다.
**4.19× 를 주장하려면 편차보다 큰 차이여야 하는데 지금 편차가 ±30 % 다.**
`run_one.sh` 에 반복 측정 + 중앙값 + 온도 로깅을 넣는 것이 7-1 이다.
