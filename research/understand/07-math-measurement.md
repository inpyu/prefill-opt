# 1부. 품질을 어떻게 재는가

## 1-1. 정보량 — 왜 `−log p` 인가

확률 `p` 인 사건이 일어났을 때 "얼마나 놀라운가"를 재고 싶다. 요구 조건은 둘이다.

```
① p 가 클수록 덜 놀랍다              →  감소 함수
② 독립 사건 두 개의 놀라움은 더해진다  →  I(p·q) = I(p) + I(q)
```

②를 만족하는 함수는 로그뿐이다(곱을 합으로 바꾸는 유일한 연속 함수).
①을 만족하려면 부호가 음수여야 한다.

```
I(p) = −log p
```

| `p` | `−ln p` | 해석 |
|---|---|---|
| 1.0 | 0 | 확실했다. 정보 없음 |
| 0.5 | 0.69 | 동전 하나 |
| 0.01 | 4.6 | 매우 놀랍다 |
| → 0 | → ∞ | 불가능하다고 본 일이 일어났다 |

**단위**: 밑이 `e` 면 **nat**, 2 면 **bit**. 이 문서는 nat 을 쓴다.

## 1-2. cross-entropy

언어 모델은 각 위치에서 다음 토큰의 분포 `q(· | x_<i)` 를 낸다.
실제로 온 토큰은 `x_i` 하나다. 그 하나에 대한 놀라움을 전 위치에서 평균한다.

```
CE = (1/n) Σ_{i=1}^{n} ( − ln q(x_i | x_<i) )
```

**읽는 법**: "모델이 정답 토큰에 평균적으로 얼마나 낮은 확률을 줬는가."

`CE` 는 학습의 손실 함수 그 자체다. 즉 **perplexity 는 손실을 사람이 읽기 좋게
바꾼 것일 뿐**이고, 새로운 정보는 없다.

## 1-3. perplexity — 왜 지수를 씌우나

```
PPL = exp(CE) = exp( −(1/n) Σ ln q(x_i | x_<i) )
```

**의미를 보려면 균등분포를 넣어 본다.** 모델이 `V` 개 토큰에 균등하게 `1/V` 를 준다면:

```
CE  = −ln(1/V) = ln V
PPL = exp(ln V) = V
```

> **PPL = "모델이 실질적으로 몇 개 중에 하나를 고르고 있는가"** (실효 분기 계수).
>
> - PPL = 1 : 항상 정확히 맞힌다
> - PPL = 10 : 매번 10개 중 하나를 고르는 정도의 불확실성
> - PPL = `V` (=128,256) : 아무것도 모른다

지수를 씌우는 이유는 **로그 스케일의 손실을 "개수"라는 직관적 단위로 되돌리기 위해서**다.

**범위**:

```
1  ≤  PPL  ≤  V = 128,256          (nat 으로는 0 ≤ CE ≤ 11.76)
```

## 1-4. perplexity 를 읽는 법

여기가 실무에서 자주 틀리는 지점이다. **PPL 은 비율로, CE 는 차로 읽어야 한다.**

```
PPL_2 / PPL_1 = exp(CE_2 − CE_1)
```

즉 **PPL 의 비율은 CE 차이의 지수**다. 이 프로젝트의 실제 값으로 확인한다.

| 사건 | PPL | CE (nat) | 해석 |
|---|---|---|---|
| 기준 (S=448, 꼬리 48) | 1.633 | 0.490 | 거의 확신 |
| `layer 8, keep 0.9` | 2.32 | 0.842 | **+0.35 nat** |
| `layer 8, keep 0.5` | 26.38 | 3.273 | +2.78 nat |
| `layer 4, keep 0.5` | 142.96 | 4.963 | +4.47 nat |

> **"+41.8 %" 라는 표기가 오해를 부른다.** 실제로는 **0.35 nat** 이 늘었고,
> 이는 "정답 토큰의 확률이 평균 `e^{-0.35} = 0.70` 배가 됐다"는 뜻이다.
> 기준 PPL 이 1.633 처럼 낮으면 작은 절대 변화도 큰 백분율로 보인다.
>
> **비교 가능한 단위는 CE 차(nat)다.** 다른 프롬프트·다른 평가 길이에서 잰
> PPL 백분율을 직접 비교하면 안 된다.

## 1-5. 지표가 조용히 무효가 되는 경우

[13-methodology §1](../13-methodology.md) 이 기록한 사고다.

```
keep = 0.9  →  perplexity  38  →  18,570   (486배)
그런데 생성 텍스트는 기준과 완전히 동일했다
```

**nat 으로 환산하면 무슨 일이 났는지 보인다.**

```
ln 38     = 3.64 nat
ln 18,570 = 9.83 nat        차이 6.19 nat
균등분포  = 11.76 nat
```

6.19 nat 은 **모델이 사실상 아무것도 모르는 상태에 가까워진 것**이다.
10 % 를 자른 결과일 수 없다. **값의 크기 자체가 지표를 의심할 근거였다.**

**원인**: 배치 perplexity 는 `logitsPipe` 의 **행 `i` 를 토큰 `i` 로** 대조한다.
그런데 압축(compaction)을 하면 살아남은 행이 앞으로 당겨져서
**행 `i` 가 더 이상 토큰 `i` 가 아니다.**

```
압축 전 : 행 0,1,2,3,4,…  ↔  토큰 0,1,2,3,4,…
압축 후 : 행 0,1,2,…      ↔  토큰 0,2,5,…      ← 대응이 깨졌다
```

지표는 **엉뚱한 토큰의 확률을 읽고 있었다.** 코드는 에러 없이 돌고, 숫자도 나온다.

> **이것이 construct validity(구성 타당도) 문제다** — 지표가 재려던 것을
> 실제로 재고 있는가. 코드가 도는 것과 지표가 유효한 것은 다르다.
>
> **규칙: 측정 대상의 자료 구조가 바뀌면, 지표의 전제도 다시 검증한다.**
> 이 지표를 믿었다면 "가지치기가 품질을 파괴한다"고 결론 내리고
> 방향 자체를 버렸을 것이다.

**대안 `--ppl-eval-tail N`**: 앞부분은 배치 prefill(가지치기 적용)로 처리하고,
마지막 `N` 토큰만 `batchSize=1` 로 하나씩 평가한다.
행↔토큰 대응 문제가 원리적으로 없고, **TTFT 목적 가지치기가 실제로 해치는 것
(이후 예측 능력)을 직접 잰다.**

### 지표를 고를 때의 일반 원칙

| 성질 | 왜 필요한가 |
|---|---|
| **연속적** | 통과/실패가 아니라 곡선을 그려야 트레이드오프가 보인다 |
| **전제가 명시적** | 무엇이 무엇과 대응하는지 적혀 있어야 깨진 걸 알아챈다 |
| **범위를 안다** | 나온 값이 물리적으로 가능한지 판정할 수 있다 (위의 11.76 nat) |
| **생성과 교차 확인 가능** | 지표와 실제 출력이 어긋나면 지표를 의심한다 |

argmax 일치(앞 8토큰)는 **이산적**이라 부동소수점 재결합에 취약하다.
그래서 [13-methodology §1](../13-methodology.md) 의 게이트가
"고유 토큰 3종 + 앞 8토큰 + PPL 편차" **세 층**으로 되어 있다 —
각 층이 다른 종류의 고장을 잡는다.

# 2부. 근사 오차

## 2-1. 상대 오차와 프로베니우스 노름

```
rel.err = ‖ Y − Ŷ ‖_F / ‖ Y ‖_F
```

`‖A‖_F = √(Σ_{ij} A_ij²)` — 모든 원소의 제곱합의 제곱근.

**왜 나누나.** 절대 오차는 스케일에 휘둘린다. 값이 1000 단위인 텐서에서 오차 10 은
1 % 지만, 0.1 단위면 재앙이다.

**왜 `rel.err = 1.0` 이 의미 있는 기준선인가.**
`Ŷ = 0` (아무것도 예측 안 함)을 넣어 보면:

```
rel.err = ‖Y − 0‖ / ‖Y‖ = 1.0
```

> **`rel.err = 1.0` 은 "0을 예측하는 것과 같다"는 뜻이다.**
> 그보다 크면 **예측이 오히려 해롭다.** 이 기준선이 있어야 숫자를 읽을 수 있다.

| rel.err | 해석 |
|---|---|
| 0.01 | 1 % — 대개 무해 |
| 0.10 | 경계선 |
| 0.30 | 구조는 남았으나 신뢰 어려움 |
| **1.00** | **0 예측과 동등 — 완전 실패** |

## 2-2. 어떤 변환이 오차를 보존하는가

근사를 파이프라인 중간에 넣을 때 결정적인 질문이다.

**직교 변환(회전, 반사)은 노름을 보존한다.**

```
R 이 직교행렬 (RᵀR = I) 이면
‖Rz‖² = (Rz)ᵀ(Rz) = zᵀRᵀRz = zᵀz = ‖z‖²
```

따라서 `z = k − k̂` 를 넣으면

```
‖R k − R k̂‖ = ‖k − k̂‖              ← 오차가 그대로다
```

> **RoPE 는 직교 변환이다**([05-math-attention §2-3](05-math-attention.md#2-3-rope-유도-요구에서-함수를-역산한다)).
> 그래서 **회전 전에서 잰 상대 오차가 회전 후에도 그대로 성립한다.**
> 이것이 "근사의 타깃은 회전 전 `K = W_kφ(x)` 여야 한다"의 두 번째 근거다.

**반대로 보존하지 않는 것들:**

| 변환 | 오차에 하는 일 |
|---|---|
| 직교 (RoPE, 순열) | **보존** |
| 대각 스케일링 `diag(d)` | 성분별로 `d_j` 배 — 큰 `d_j` 방향의 오차가 증폭 |
| 일반 행렬 `A` | 최대 `σ_max(A)` 배 증폭 (조건수 문제) |
| softmax | 비선형. 포화 영역에서는 오차를 죽이고, 경계에서는 증폭 |

**따라오는 실무 규칙**: 근사는 **뒤에 직교 변환만 남는 지점**에 넣는 것이 가장 안전하다.
그 지점 이후로는 오차 분석이 그대로 유효하다.

# 3부. 성능을 어떻게 재는가

## 3-1. 하드웨어 피크 성능 유도

"우리가 하드웨어의 몇 %를 쓰고 있는가"를 알려면 분모가 필요하다.

**Raspberry Pi 5 — Cortex-A76 4코어 @ 2.4 GHz, NEON.**

핵심은 `SDOT` 명령어 하나가 몇 번의 곱셈-누산(MAC)을 하는가다.

```
vdotq_s32(int32x4_t acc, int8x16_t a, int8x16_t b)

  128비트 레지스터  =  int8 16개
  4개씩 묶어 4쌍의 내적을 계산해 int32 4개에 누산

  ⟹  4 lane × 4 곱셈 = 16 MAC = 32 연산(곱 16 + 합 16)
```

코어당 사이클당 SDOT 1개를 발행한다고 보면:

```
피크 = 4 코어 × 2.4×10⁹ Hz × 32 연산/사이클
     = 307.2 GOPS
```

[11-results §5](../11-results.md) 의 **307 GOPS** 가 이 값이다.

### ⚠ 04-concepts §4-4 의 수치 오류

[04-concepts §4-4](04-concepts.md#4-4-simd-와-내적-명령어) 는
"`vdotq_s32` 하나가 **32 MAC = 64 FLOP**" 이라고 적었다. **2배 크다.**
128비트에는 int8 이 16개뿐이므로 MAC 은 16개다.

64 FLOP 을 쓰면 피크가 614 GOPS 가 되어 11-results 의 307 과 모순되고,
달성률이 68 % 가 아니라 34 % 로 나온다. **307 이 정본이다.**
(→ [README §4](README.md#4-원본-문서-간-알려진-불일치) 에 등재)

## 3-2. 달성 GFLOPS 와 그 의미

**분자 — prefill 이 실제로 한 연산량.**
[04-concepts §1-8](04-concepts.md#1-8-로짓과-lm_head) 의 레이어당 0.436 GFLOP/token 을 쓰면:

```
연산량 = 32 레이어 × 0.436 GFLOP/token × 448 token = 6.25 TFLOP
```

(lm_head 는 prefill 에서 마지막 행만 계산하므로 무시할 수준이다.)

**달성치:**

| 구성 | 시간 | GFLOPS | 피크 대비 |
|---|---|---|---|
| 단일 노드 | 30,110 ms | `6.25e12/30.11` = **208** | **68 %** (÷307) |
| PP8 | 7,973 ms | `6.25e12/7.973` = **784** | 32 % (÷2,458) |

> **단일 노드가 이미 피크의 68 % 라는 사실이 이 연구의 방향을 결정했다.**
> 커널을 더 다듬어도 남은 여지는 최대 1.5배다.
> **"정확한 연산으로 몇십 배"는 하드웨어가 허용하지 않는다.**
> 그래서 남은 선택지가 ① 노드를 늘리거나 ② 연산 자체를 줄이는 것(근사)뿐이다.
>
> 이 계산을 안 해 보면 "커널을 더 최적화하자"에 몇 주를 쓸 수 있다.
> **피크 대비 달성률은 최적화를 언제 멈출지 알려주는 숫자다.**

## 3-3. 속도향상 보고의 함정

같은 시스템에서 세 개의 서로 다른 "배수"가 나온다.

```
원본 distributed-llama (222 s)  →  PP8 (7.2 s)   =  31×
본 연구 단일 (30.1 s)           →  PP8 (7.2 s)   =  4.4×
llama.cpp 단일 (27.7 s)         →  PP8 (7.2 s)   =  3.5×
```

**전부 사실이지만 재는 것이 다르다.**

| 배수 | 기준선 | 무엇을 주장하나 |
|---|---|---|
| 31× | 원본 dllama | 구현 결함 수정 + 분산의 **합** |
| **4.4×** | 본 연구 단일 | **분산이 기여한 것** ← 이 연구의 본체 |
| 3.5× | llama.cpp 단일 | **외부 기준선** 대비 — 유일하게 반박 불가능한 수치 |

> **논문에 쓸 수 있는 것은 세 번째다.** 자기 단일 노드를 기준으로 하면
> "단일 노드를 일부러 느리게 두지 않았나"라는 반론에 답할 수 없다.
> **외부에서 널리 쓰이는 구현을 기준선으로 삼아야 방어된다.**
>
> [11-results §1](../11-results.md) 이 세 배수를 **모두** 병기한 것이 옳은 형태다.
> 하나만 고르면 어느 쪽으로든 오해를 만든다.

### 배수는 같은 세션 안에서만 비교한다

```
같은 구성(PP8)의 두 세션 :  7,973 ms  vs  7,165 ms      (10 % 차이)
```

`30,110 / 7,973 = 3.78×` 인데 `30,110 / 7,165 = 4.20×` 다.
**분자와 분모를 다른 세션에서 가져오면 배수가 11 % 움직인다.**

> **규칙: 배수를 계산할 때 분자와 분모는 반드시 같은 세션에서 잰 값이어야 한다.**
> [README §4](README.md#4-원본-문서-간-알려진-불일치) 가 "07 §1 표와 06 §2 표의
> 숫자를 섞어 비율을 계산하지 말 것"이라고 적은 것이 같은 이야기다.

# 4부. 실험 설계

## 4-1. 왜 평균이 아니라 중앙값인가

[13-methodology §3](../13-methodology.md) 의 실측 5회:

```
49,992   34,077   34,824   34,418   32,414        (ms)
```

| 통계량 | 값 |
|---|---|
| 평균 (5회) | 37,145 |
| **중앙값 (5회)** | **34,418** |
| 평균 (rep1 제외) | 33,933 |

**평균은 이상치 하나에 3,200 ms(9 %) 끌려간다.** 중앙값은 거의 움직이지 않는다.

**이유는 정의에서 바로 나온다.**

```
평균   : 모든 값이 1/n 의 가중치로 결과에 들어간다   →  큰 값 하나가 크게 민다
중앙값 : 순서만 쓴다                                →  극단값의 크기와 무관
```

성능 측정의 잡음은 **한쪽으로만 치우친다** — 무언가 방해하면 느려지지,
빨라지는 일은 없다. 즉 분포가 **오른쪽 꼬리를 갖는다.**
이런 분포에서 평균은 체계적으로 과대평가된다. **중앙값이 옳은 선택이다.**

### 흩어짐은 어떻게 보고하나

이 프로젝트는 `(최대 − 최소) / 중앙값` 을 "편차"로 쓴다.

```
5회 전부      : (49,992 − 32,414) / 34,418 = 51 %
rep1 제외     : (34,824 − 32,414) / 34,077 =  7 %
```

**rep1 을 버리면 51 % → 7 %.** 이 하나로 "첫 실행은 다른 모집단"임이 드러난다.

**왜 열이 아니라 콜드 스타트인가.** 열 문제라면 **뒤로 갈수록** 느려져야 한다.
실제로는 rep1 만 느리고 rep2~5 는 평평하다. 시작 온도도 rep1 이 오히려 낮았다.
따라서 원인은 페이지 캐시·mmap 폴트·CPU 주파수 상승 같은 **1회성 초기화**다.

> **워밍업 제외는 데이터를 버리는 것이 아니라, 다른 모집단을 분리하는 것이다.**
> 근거(단조 감소가 아님 + 온도 무관)를 함께 기록해야 정당화된다.

## 4-2. 순서 효과와 교차 실행

**사고**: 융합 attention 을 순차 비교(A 먼저, B 나중)했더니 "1.3 % 손해"가 나왔다.

**의심의 근거**: 커널과 **무관해야 할** 항목까지 같이 늘었다.

```
gemm  +558 ms
ffn   +517 ms        ← 융합 attention 은 이 둘을 건드리지 않는다
```

**이것이 결정적 증거다.** 처치가 영향을 줄 수 없는 항목이 움직였다면,
움직인 것은 처치가 아니라 **시간 자체(드리프트)** 다.
열 축적, 페이지 캐시 상태, 백그라운드 프로세스가 후보다.

**해법 — 교차 실행(A/B interleaving).**

```
순차  :  A A A A  B B B B      ← 시간과 처치가 섞여 있다 (교란)
교차  :  A B A B A B A B      ← 시간 효과가 두 처치에 균등하게 분배된다
```

이것은 실험계획법의 **블록 설계(blocking)** 다.
"시간"을 블록으로 두고 각 블록 안에서 두 처치를 모두 실행한다.
드리프트가 있어도 **같은 블록 안의 비교는 유효하다.**

교차 4라운드 결과: **4/4 라운드 모두 융합이 빨랐다.**

> **`run_one.sh` 의 워밍업·반복 중앙값은 한 설정 *안의* 편차만 잡는다.**
> 설정 *사이의* 순서 효과는 못 막는다. **다른 층위의 잡음이다.**

## 4-3. "4/4 라운드"는 얼마나 강한 증거인가

부호 검정(sign test)으로 정량화한다.

귀무가설: 두 구성이 동일하다 → 각 라운드에서 어느 쪽이 빠를 확률은 1/2.

```
P(4/4 모두 한쪽) = (1/2)⁴ = 1/16 = 6.25 %        (단측)
                  양측이면 12.5 %
```

> **4라운드는 "우연이 아닐 가능성이 높다"까지만 말한다.** 관례적 기준(5 %)에
> 아슬아슬하게 못 미친다. **5라운드면 3.1 %** 가 되어 기준을 넘는다.
>
> 부호 검정은 **크기를 안 쓰고 방향만 쓰므로** 강건하지만 그만큼 검정력이 약하다.
> 효과가 작을수록 라운드를 늘려야 한다. 라운드 수를 정할 때
> **"몇 라운드면 우연을 배제할 수 있나"를 먼저 계산하는 것이 옳다.**

## 4-4. 잡음이 검출 가능한 효과의 크기를 정한다

이 프로젝트의 세션 간 편차는 **약 10 %** 다. 그러면:

```
검출하려는 효과 < 잡음      →  단일 비교로는 판정 불가
```

[06-math-pipeline §7](06-math-pipeline.md#7-입자도--왜-n8-에서-균형화가-실패하는가) 에서
N=8 균형화의 **이론 이득이 12 %** 였다. 잡음 10 % 와 같은 자릿수다.

> **N=8 균형화가 "실패"한 것이 아니라, 이 측정 설정으로는 판정할 수 없었던 것에 가깝다.**
> 12-findings #14 는 7,165 → 7,360(악화)을 보고했는데, 이 역시 잡음 범위 안이다.
>
> **결론을 내리려면 둘 중 하나가 필요했다:**
> ① 교차 실행 + 라운드 수를 늘려 잡음을 평균으로 줄이거나,
> ② **총 시간이 아니라 스테이지별 도착 시각**을 재서 `ρ` 를 직접 관측하거나.
>
> ②가 근본적이다. 총 시간은 여러 효과의 합이라 신호 대 잡음비가 나쁘다.
> **원인에 가까운 양을 직접 재면 잡음이 훨씬 작다.**
> [13-methodology §6](../13-methodology.md) 의 노드별 계측이 이것이고,
> 실제로 그 계측이 마지막 스테이지 5,667 ms 를 **한 번에** 드러냈다.

**일반 원칙:**

```
잡음 σ, 라운드 R 회의 평균을 쓰면  →  실효 잡음 σ/√R
효과 크기 e 를 검출하려면          →  R ≳ (σ/e)²
```

σ=10 %, e=12 % → `R ≈ 0.7` (1라운드로 충분해 보임)이지만, 이는 잡음이 독립일 때다.
세션 내 상관이 있으면(드리프트) 훨씬 많이 필요하다. **그래서 교차 실행이 먼저다.**

## 4-5. 게이트는 분류기다

정확성 게이트는 "정상 구성"과 "깨진 구성"을 가르는 **이진 분류기**다.
따라서 두 종류의 오류가 있다.

| | 실제 정상 | 실제 깨짐 |
|---|---|---|
| 게이트 통과 | ✔ | **거짓 음성** — 깨진 걸 재고 있다 |
| 게이트 탈락 | **거짓 양성** — 멀쩡한 걸 버린다 | ✔ |

**이 프로젝트에서 둘 다 일어났다.**

**거짓 양성 (게이트가 틀림)**

```
임계값 0.5 %  →  정상 구성인 TP2 가 0.740 % 로 탈락
```

> **게이트가 정상 구성을 떨어뜨리면 게이트가 틀린 것이다.**
> 임계값은 **알려진 정상 구성들의 분포**로 보정해야 한다.
> 이론적 이상치(0)가 아니라 **관측된 정상 범위**가 기준이다.

**지표의 분산이 표본 수에 의존한다**

```
13토큰 프롬프트  →  TP4 편차 5.35 %  (예측 12개만 평균)
128토큰 프롬프트 →  TP4 편차 0.707 % (안정)
```

`n` 개를 평균하면 표준오차가 `1/√n` 로 준다. `12 → 128` 이면 `√(128/12) = 3.3` 배 안정.
실측은 5.35 → 0.707 로 7.6배 개선인데, 이는 짧은 프롬프트에서 개별 항의
분산 자체도 컸기 때문이다.

> **게이트의 임계값과 표본 수는 함께 정해야 한다.**
> 표본이 적으면 어떤 임계값도 안정적이지 않다.

**거짓 음성이 더 위험하다.** [13-methodology §1](../13-methodology.md) 이 기록한 4건 중
3번(불균등 분할에서 가중치가 엉뚱한 노드로)은 게이트가 없었다면
**"빨라졌다"고 보고됐을 것이다.** 깨진 구성은 대개 **더 빠르다** —
계산을 덜 하기 때문이다.

> **성능 최적화에서 거짓 음성은 체계적으로 유리한 방향으로 틀린다.**
> 그래서 **성능을 재기 전에 정확성을 게이트로 통과**시키는 순서가 강제되어야 한다.
