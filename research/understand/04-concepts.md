# 1부. 트랜스포머가 무엇을 계산하는가

## 1-1. 토큰과 임베딩

**토큰**은 텍스트를 자른 조각이다. 단어보다 작을 수도 클 수도 있다
("prefill" → `pre` + `fill` 처럼). 모델은 글자가 아니라 **토큰 ID(정수)** 를 받는다.

모델이 정수를 직접 계산할 수는 없으니, ID 를 벡터로 바꾼다.
**임베딩**은 그냥 **큰 표에서 행 하나를 꺼내는 것**이다.

```
임베딩 표 : vocab × h  =  128256 × 4096   (Llama-3-8B)
토큰 ID 5  →  표의 5번 행  →  길이 4096 벡터
```

**핵심**: 임베딩은 곱셈이 아니라 **복사(lookup)** 다. 연산량이 0에 가깝다.
그런데 표 자체는 크다 — 128256 × 4096 × 4B = **2.1 GB** (F32일 때).
즉 **연산에는 안 잡히는데 메모리는 많이 먹는 항목**이다.

← 이어짐: [양자화](#4-1-양자화가-하는-일) (이 표를 4비트로 줄이면 1.8 GB 가 빈다)

## 1-2. residual stream

토큰 하나가 모델을 통과하는 동안, 그 토큰을 대표하는 **벡터 하나**가 계속 갱신된다.
이 벡터의 흐름을 **residual stream** 이라 한다.

```
x_0     = 임베딩(토큰)
x_{l+1} = x_l + Attn_l(x_l) + FFN_l(x_l)
x_32    → 로짓
```

**왜 `+` 인가 (residual connection).**
레이어가 `x` 를 통째로 바꾸는 게 아니라 **얼마나 바꿀지(delta)만 계산해서 더한다.**
깊은 신경망에서 학습이 되게 하는 표준 장치이고, 추론 관점에서는 다른 의미가 있다:

> **`x_l` 은 레이어를 지나며 조금씩만 변한다.** 인접 레이어의 `x` 는 서로 닮아 있다.

이 성질이 나중에 "레이어 k 의 `x_k` 만 보고 위쪽 레이어의 값을 추측할 수 있는가"라는
질문의 근거가 된다.

**그리고 여기에 근본적인 제약이 있다.** `x_{l+1}` 을 알려면 `x_l` 이 있어야 한다.
레이어 32개는 **반드시 순서대로** 계산된다.

```
토큰 방향 : 서로 독립  →  병렬 가능
깊이 방향 : 순차       →  병렬 불가
```

**이 비대칭이 이 프로젝트의 모든 문제의 뿌리다.**

← 이어짐: [선형 사상](#7-1-선형-사상), [PP](#5-3-pp-파이프라인-병렬)

## 1-3. Attention

**해결하려는 문제**: 토큰 하나의 의미는 **다른 토큰들에 의존한다.**
"그것은 무겁다"에서 "그것"이 뭔지는 앞 문장을 봐야 안다.
그러니 각 토큰이 **다른 토큰들의 정보를 가져오는 장치**가 필요하다.

**구조 — 도서관 비유가 정확하다.**

| 이름 | 역할 | 비유 |
|---|---|---|
| **Q** (query) | 내가 찾는 것 | 검색어 |
| **K** (key) | 각 토큰이 내건 간판 | 책 제목 |
| **V** (value) | 각 토큰이 실제로 주는 내용 | 책 본문 |

토큰 i 가 하는 일:

```
1. 내 검색어 q_i 와 모든 간판 k_j 의 유사도를 잰다
       s_ij = q_i · k_j / √d          (내적, √d 로 스케일)

2. 유사도를 확률로 바꾼다
       a_ij = softmax_j(s_ij)          (다 더하면 1)

3. 그 확률로 내용을 가중 평균한다
       out_i = Σ_j a_ij · v_j
```

**Q, K, V 는 어디서 오나.** 전부 같은 `x` 에서 행렬 곱으로 만든다.

```
q_i = W_q · x_i        K, V 도 마찬가지
```

**즉 "K 를 만든다"는 것은 행렬 곱 한 번이 전부다.** 이 단순함이 나중에 중요해진다.

**멀티헤드**: 위 과정을 32개의 독립된 "관점"으로 나눠서 한다.
`h=4096` 을 32개 헤드 × `headDim=128` 로 쪼개, 각 헤드가 자기 128차원 안에서만 위 계산을 한다.
헤드끼리는 완전히 독립이다 → **헤드 축은 병렬화하기 쉽다.**

**비용의 성질** — 이것이 attention 의 특징이다:

```
토큰 S개가 서로를 다 본다  →  S × S 쌍  →  O(S²)
```

다른 모든 연산이 O(S) 인데 **attention 만 O(S²)** 다. S 가 커질수록 비중이 오른다.

← 이어짐: [KV 캐시](#2-2-kv-캐시), [attention 의 산술 강도](#3-5-attention-의-산술-강도)

→ **더 깊이**: [05-math-attention 1부](05-math-attention.md#1부-attention) — Q·K 를 왜 **분리**해야
하는지(대칭성 논증), `√d` 가 `Var[q·k] = d` 에서 나오는 유도, `d_head` 가 점수 함수의
**랭크 상한**이라는 관점, GQA 의 수식적 의미.

## 1-4. causal mask

언어 모델은 **다음 토큰을 예측**한다. 그러니 토큰 i 가 자기 뒤의 토큰을 보면 안 된다
(답을 미리 보는 것).

**mask** 는 `j > i` 인 유사도를 `-∞` 로 만드는 것이다. softmax 를 거치면 `e^{-∞} = 0` 이라
그 토큰의 가중치가 정확히 0이 된다.

```
        j=0   j=1   j=2   j=3
i=0   [ ✓  ,  -∞ ,  -∞ ,  -∞ ]
i=1   [ ✓  ,  ✓  ,  -∞ ,  -∞ ]
i=2   [ ✓  ,  ✓  ,  ✓  ,  -∞ ]
i=3   [ ✓  ,  ✓  ,  ✓  ,  ✓  ]
```

**두 가지 귀결**:

1. 실제 연산량은 `S²` 가 아니라 **`S²/2`** 다 (삼각형).
2. **토큰 i 의 계산은 자기보다 앞의 토큰에만 의존한다.**
   → 뒤 토큰이 추가돼도 앞 토큰의 K, V 는 **변하지 않는다.**

2번이 KV 캐시가 성립하는 이유다.

## 1-5. FFN 와 SwiGLU

Attention 이 "토큰끼리 정보를 섞는" 장치라면, **FFN 은 각 토큰이 혼자 하는 처리**다.
토큰 간 상호작용이 전혀 없다. 그냥 벡터 하나를 넣고 벡터 하나를 받는다.

**기본형**: 넓혔다가 좁힌다.

```
4096 → 14336 → 4096
```

중간에서 3.5배로 넓히는 이유는 표현력이다 (넓은 공간에서 비선형을 먹인 뒤 되돌린다).

**SwiGLU** 는 이걸 게이트 구조로 바꾼 변형이다. 행렬이 **3개**다.

```
FFN(x) = w2( silu(w1·x) ⊙ w3·x )

  w1 : 4096 → 14336    "값"
  w3 : 4096 → 14336    "게이트"  ← 어느 성분을 통과시킬지
  w2 : 14336 → 4096    되돌리기
  ⊙  : 원소별 곱
```

`silu(w1·x)` 가 게이트 역할을 하고 `w3·x` 와 원소별로 곱해진다.
성분마다 "얼마나 통과시킬지"를 데이터에 따라 조절하는 셈이다.

**비용**: 행렬 3개 × (4096×14336) 이라 **레이어 연산의 80.7 %** 를 차지한다.
attention 이 화제의 중심이지만, **짧은 프롬프트에서 실제 시간을 먹는 건 FFN 이다.**

**중요한 성질**: FFN 은 **토큰 간 의존이 0** 이다.
토큰을 아무렇게나 나눠 다른 기계에서 계산해도 결과가 같다.
(attention 은 그럴 수 없다 — 서로를 봐야 하니까)

## 1-6. 정규화 (LayerNorm 과 RMSNorm)

**문제**: 레이어를 지나며 벡터의 크기가 점점 커지거나 작아지면 수치가 불안정해진다.
그래서 각 레이어 입구에서 **크기를 표준화**한다.

**LayerNorm** (고전형): 평균을 빼고 표준편차로 나눈다.

```
y = (x − mean(x)) / std(x) · γ + β
```

**RMSNorm** (Llama 계열): **평균 빼기를 생략**하고 크기만 맞춘다.

```
rms(x) = √( (1/n) Σ x_i² )
y      = x / rms(x) · γ
```

**왜 생략해도 되나.** 실험적으로 성능 차이가 거의 없는데 연산은 줄어든다
(평균 계산, 뺄셈, 그리고 β 파라미터가 사라짐).

**계산 구조.** `rms(x)` 는 벡터 전체를 훑어야 나오는 **스칼라 하나**다.
그래서 구현에서 두 단계로 쪼개진다 — 먼저 역제곱근을 구하고(리덕션), 그 다음 곱한다(원소별).

**이 프로젝트에서 `φ(·)` 라고 쓰는 것이 RMSNorm 이다.**
Q/K/V 를 만드는 행렬 곱의 실제 입력은 `x` 가 아니라 **`φ(x)`** 이기 때문에,
수식을 정확히 쓰려면 `K = W_k · φ(x)` 여야 한다.

## 1-7. 위치 인코딩과 RoPE

**문제**: Attention 식을 보면 **토큰의 순서 정보가 전혀 없다.**
`Σ_j a_ij v_j` 는 j 의 순서를 바꿔도 같은 값이다. "개가 사람을 물었다"와
"사람이 개를 물었다"를 구분할 수 없다.

**해결 방향 두 가지:**

| 방식 | 방법 | 한계 |
|---|---|---|
| 절대 위치 (고전) | 위치 t 마다 다른 벡터를 **더한다** | 학습 때 안 본 위치로 확장이 어렵다 |
| **RoPE** (상대) | q, k 를 위치에 따라 **회전시킨다** | — |

**RoPE 의 아이디어.** 벡터를 2차원씩 짝지어, 위치 t 에 비례하는 각도로 회전시킨다.

```
위치 t 의 회전 각도 : θ_t = t · ω     (ω 는 차원마다 다른 주파수)

q̃_i = R(i·ω) · q_i
k̃_j = R(j·ω) · k_j
```

**왜 이게 좋은가 — 회전의 성질 때문이다.** 두 회전 벡터의 내적은:

```
q̃_i · k̃_j  =  (R(iω) q_i) · (R(jω) k_j)
            =  q_i · R((j−i)ω) k_j        ← 회전행렬의 성질
```

> **결과가 절대 위치 i, j 가 아니라 상대 거리 `j − i` 에만 의존한다.**

"3칸 앞 토큰"이라는 관계가 문장 어디에 있든 똑같이 표현된다. 이것이 RoPE 가 이긴 이유다.

**추론 관점의 귀결 — 이게 실무에서 중요하다:**

1. **캐시에 저장되는 K 는 이미 회전된 값이다.** 그래서 같은 문장을 다른 위치에
   재사용하려면 회전을 되돌렸다가 다시 걸어야 한다.
2. **"위치와 무관한 값"이 필요하면 회전 이전 값을 써야 한다.**
   회전 전 `K = W_k·φ(x)` 는 순수하게 내용만의 함수다.

← 이어짐: [선형 사상](#7-1-선형-사상), [블록 로컬 attention](#6-1-블록-로컬-attention)

→ **더 깊이**: [05-math-attention 2부](05-math-attention.md#2부-rope) —
`Attn(PX) = P·Attn(X)` 증명(위치 인코딩이 없으면 트랜스포머가 **집합 함수**다),
`⟨f(q,m),f(k,n)⟩ = g(q,k,m−n)` 요구에서 회전을 **역산**하는 과정,
왜 주파수가 여럿이어야 하는지(aliasing), 왜 V 에는 걸지 않는지,
그리고 interleaved / half-split **페어링 불일치**라는 조용한 버그.

## 1-8. 로짓과 lm_head

마지막 레이어를 나온 벡터 `x_32` (길이 4096)를 **어휘 크기로 사영**해
각 토큰의 점수를 낸다.

```
로짓 = W_lm · x_32      W_lm : 128256 × 4096
```

이 128256개 점수에 softmax 를 걸면 다음 토큰의 확률 분포가 된다.

**비용이 크다.** `2 × 4096 × 128256 ≈ 1.05 GFLOP/token` — **레이어 하나(0.436 GFLOP)의 2.4배**다.
행렬 자체도 크다(Q4_0 으로도 295 MB).

**핵심 관찰**: 프롬프트를 읽는 동안에는 **로짓이 필요 없다.**
필요한 건 마지막 토큰 하나의 로짓뿐이다. 나머지 위치의 lm_head 계산은 전부 버려진다.

← 이어짐: [TTFT](#2-5-ttft)

# 2부. KV 캐시는 왜 생겼는가

## 2-1. 중복 계산 문제

토큰을 하나씩 생성한다고 하자. 캐시가 없으면 매 스텝마다 무슨 일이 일어나나:

```
스텝 1 : "안녕"                  → 토큰 2개의 K,V 계산
스텝 2 : "안녕 하세"             → 토큰 3개의 K,V 계산   (2개는 이미 했던 것)
스텝 3 : "안녕 하세 요"          → 토큰 4개의 K,V 계산   (3개는 이미 했던 것)
```

**S 토큰을 생성하면 총 `1+2+3+...+S = O(S²)` 번의 K,V 계산**을 한다.

그런데 [causal mask](#1-4-causal-mask) 에서 봤듯, **토큰 j 의 `k_j`, `v_j` 는
뒤에 뭐가 오든 변하지 않는다.** 앞 토큰만 보고 만들어지니까.

> **같은 값을 매번 다시 만들고 있다. 저장해 두면 된다.**

---

## 2-2. KV 캐시

한 번 계산한 `k_j`, `v_j` 를 **저장해 두고 재사용**하는 것.

```
캐시 없음 : 스텝마다 K,V 를 j=0..t 전부 계산     O(S²) 계산
캐시 있음 : 스텝마다 K,V 를 1개만 계산해 덧붙임   O(S)  계산
```

**저장 구조.** 레이어마다 따로 있어야 한다 (레이어 l 의 attention 은 레이어 l 의 K,V 를 본다).

```
KV 캐시 = [레이어 L개] × [토큰 S개] × (K 벡터 + V 벡터)
```

**크기 유도** (Llama-3-8B, F32):

```
토큰 1개·레이어 1개 : K(1024) + V(1024) = 2048 개 × 4B  =    8 KB
토큰 1개 (32 레이어) : 8 KB × 32                        =  256 KB
2048 토큰            : 256 KB × 2048                    =  512 MB
```

**여기서 두 가지가 따라온다:**

1. **메모리를 많이 쓴다.** 모델 가중치(4.5 GB)에 더해 프롬프트 길이에 비례하는 메모리가 든다.
   → 이 때문에 PagedAttention 같은 "KV 를 1급 자원으로 관리하는" 시스템이 생겼다.
2. **decode 마다 이 전부를 읽어야 한다.** 토큰 하나 만들자고 512 MB 를 훑는다.
   → [메모리 대역폭 문제](#2-3-prefill-과-decode-가-갈리는-지점)

**정밀도 선택.** 캐시를 F16 으로 저장하면 크기와 읽기 트래픽이 **정확히 절반**이 된다.
정확도 손실은 거의 없다고 알려져 있어 대부분의 엔진이 F16 을 기본으로 쓴다.

← 이어짐: [산술 강도](#3-2-산술-강도), [CP/SP](#5-4-cpsp-시퀀스-병렬)

→ **더 깊이**: [05-math-attention 3부](05-math-attention.md#3부-kv-캐시) —
"미래 스텝이 다시 읽는가"라는 **단일 기준**으로 Q 가 탈락하는 과정,
왜 **회전 후**의 K 를 저장하는지와 그 대가(캐시가 위치에 고정되어 접두사 공유만 가능),
크기 공식에 `h` 가 아니라 `n_kv` 가 들어가는 이유,
그리고 **근사의 타깃은 회전 전 `K = W_kφ(x)` 여야 한다**는 세 가지 근거.

## 2-3. prefill 과 decode 가 갈리는 지점

캐시를 도입하면 추론이 **성격이 다른 두 국면**으로 갈라진다.

```
prefill : 프롬프트 S 토큰을 한 번에 넣어 캐시를 채운다
decode  : 토큰 1개씩 만들며 캐시에 한 줄씩 덧붙인다
```

**왜 성격이 다른가 — 가중치를 몇 번 쓰느냐다.**

가중치를 메모리에서 읽는 것은 어느 쪽이든 **한 번**이다. 차이는 그 읽은 가중치로
몇 토큰분을 계산하느냐다.

```
prefill : 가중치 1회 읽기  →  S 토큰 계산    (S = 447 이면 447배 재사용)
decode  : 가중치 1회 읽기  →  1 토큰 계산    (재사용 0)
```

decode 는 **읽는 시간이 곧 전부**다. 4.5 GB 를 8 GB/s 로 읽으면 0.56초.
연산 유닛은 그동안 거의 논다.

| | prefill | decode |
|---|---|---|
| 행렬 연산 형태 | 행렬 × 행렬 (**GEMM**) | 행렬 × 벡터 (**GEMV**) |
| 병목 | 연산 | **메모리 대역폭** |
| 개선 방향 | 연산 효율, 병렬화 | 가중치 크기 줄이기, 양자화 |

> **같은 모델, 같은 하드웨어인데 최적화 방법이 정반대다.**
> 이 때문에 "prefill 과 decode 를 아예 다른 기계에 배치하자"(P/D disaggregation)는
> 시스템 설계까지 나왔다.

**주의**: "prefill 은 compute-bound" 는 **배치가 충분할 때만** 참이다.
프롬프트를 32토큰 미만 청크로 자르면 prefill 도 memory-bound 가 된다.
→ [GEMM 의 산술 강도](#3-4-gemm-의-산술-강도가-배치-크기인-이유)

---

## 2-4. MHA → MQA → GQA

KV 캐시가 크다는 문제를 **구조로** 푸는 방향.

**MHA (Multi-Head Attention)** — 원형. 헤드 32개가 각자 자기 K, V 를 갖는다.

```
KV 차원 = 32 헤드 × 128 = 4096   (= hidden 전체)
```

**MQA (Multi-Query Attention)** — 극단. **KV 헤드를 1개만** 두고 32개 쿼리 헤드가 전부 공유.

```
KV 차원 = 1 × 128 = 128          (32배 절약)
```

캐시가 32배 작아지지만 표현력이 떨어져 품질이 내려간다.

**GQA (Grouped-Query Attention)** — 중간. KV 헤드를 8개 두고 4개씩 묶어 공유한다.

```
쿼리 헤드 32개  →  4개씩 8그룹
KV   헤드  8개  →  그룹당 1개

kvMul = 32 / 8 = 4        "쿼리 헤드 4개가 KV 헤드 1개를 공유"
KV 차원 = 8 × 128 = 1024   (4배 절약)
```

품질은 MHA 에 가깝고 캐시는 1/4. 그래서 요즘 모델의 표준이 됐다.

**분산 관점의 부수 효과 — 이게 크다.**
노드 간에 KV 를 주고받아야 할 때, 보낼 데이터가 4096 이 아니라 **1024** 다.
**GQA 는 시퀀스 축 분산(CP)의 통신량을 4배 줄여 준다.**

**구현 관점의 함정.** 커널이 **쿼리 헤드 단위로** 루프를 돌면,
같은 KV 헤드를 `kvMul`(=4)번 반복해서 읽게 된다.
GQA 의 이득을 얻으려면 **KV 헤드 단위로 묶어서** 처리해야 한다.

---

## 2-5. TTFT

**TTFT (Time To First Token)** = 프롬프트를 넣고 첫 글자가 나올 때까지의 시간.

```
TTFT = prefill 전체 + decode 첫 스텝 1회
```

decode 한 스텝은 짧으므로 **사실상 prefill 시간이다.**

**TTFT 시점에 만들어져야 하는 것은 정확히 두 개다:**

```
1. 모든 토큰 × 모든 레이어의 KV 캐시
2. 마지막 토큰 1개의 로짓
```

**이 명제가 강력한 이유.** 토큰 `0..S-2` 의 상위 레이어 residual stream 은
**오직 그 레이어의 KV 를 만들기 위해서만** 존재한다. 다른 용도가 없다.

여기서 세 갈래의 최적화가 갈라져 나온다:

| 관찰 | 최적화 |
|---|---|
| 로짓은 마지막 1개만 필요 | prefill 에서 lm_head 건너뛰기 |
| 상위 레이어 계산의 목적은 KV 뿐 | KV 를 **더 싸게** 만들 수 있으면 그 계산을 건너뛴다 |
| 토큰끼리는 독립 | 토큰을 나눠 여러 기계에서 동시에 |

← 이어짐: [7부 선형대수](#7부-계산을-건너뛰기--선형대수), [5부 분산](#5부-여러-대로-나누기)

# 3부. 왜 빠르지 않은가 — 하드웨어

## 3-1. 메모리 계층

CPU 는 **계산은 빠른데 데이터를 가져오는 게 느리다.** 그래서 계층을 둔다.

```
레지스터   ~1 cycle       수십 개
L1 캐시    ~4 cycles      64 KB
L2 캐시    ~15 cycles     512 KB ~ 2 MB
DRAM      ~200 cycles     GB 단위      ← 여기가 절벽
```

**DRAM 접근은 연산보다 두 자릿수 느리다.**
따라서 성능 문제는 대개 "연산이 느리다"가 아니라 **"데이터가 제때 안 온다"** 이다.

**대역폭이라는 관점.** 지연(latency)보다 실무에서 중요한 건 **초당 몇 바이트를 옮기는가**다.

```
Raspberry Pi 5 : 약 8~10 GB/s
서버용 CPU     : 100~200 GB/s
GPU (HBM)      : 1000~3000 GB/s
```

> **SBC 는 연산 대비 메모리 대역폭이 특히 부족하다.**
> GPU 에서 통하는 최적화가 SBC 에서 안 통하는 이유의 대부분이 여기서 나온다.

---

## 3-2. 산술 강도

"이 연산이 연산 병목인가, 메모리 병목인가"를 판정하는 **단 하나의 숫자**.

```
산술 강도 (arithmetic intensity) = 총 연산량 / 총 메모리 접근량   [FLOP / byte]
```

**직관**: "메모리에서 1바이트 가져올 때마다 몇 번 계산하는가."

- 값이 크다 = 한 번 가져와 오래 쓴다 = 메모리가 여유롭다 → **compute-bound**
- 값이 작다 = 가져오자마자 버린다 = 메모리가 못 따라온다 → **memory-bound**

**예시로 감 잡기:**

```
벡터 덧셈 c = a + b
  연산 : n번
  메모리: 3n개 × 4B = 12n byte
  강도 : n / 12n = 0.083 FLOP/byte     ← 극도로 memory-bound

행렬 곱 (n×n)
  연산 : 2n³
  메모리: 3n² × 4B
  강도 : 2n³ / 12n² = n/6              ← n 이 크면 compute-bound
```

**행렬 곱이 GPU 시대의 주인공이 된 이유가 이것이다.** 강도가 크기에 비례해 올라간다.

---

## 3-3. roofline 과 machine balance

산술 강도가 **얼마 이상이면** compute-bound 인가? 그 경계는 기계마다 다르다.

**machine balance** = 그 기계의 연산 능력 ÷ 메모리 대역폭.

```
Raspberry Pi 5 :  110 GFLOPS  ÷   9 GB/s   ≈  12 FLOP/byte
서버 CPU       : 2000 GFLOPS  ÷ 150 GB/s   ≈  13
A100 GPU       :  312 TFLOPS  ÷ 2.0 TB/s   ≈ 156
```

> 재미있는 점: **CPU 들은 balance 가 10대로 비슷하고, GPU 는 100대로 훨씬 높다.**
> GPU 는 연산이 워낙 빨라서 "데이터를 재사용하지 않으면 굶는" 기계다.

**roofline 모델**은 이걸 그림으로 만든 것이다.

```
성능
 ↑
 │        ┌─────────────  ← 연산 한계 (평평한 지붕)
 │      ╱
 │    ╱                   ← 대역폭 한계 (비스듬한 지붕)
 │  ╱
 └────┼──────────────→  산술 강도
    balance
```

내 커널의 산술 강도를 x축에 찍으면, **그 지점의 지붕 높이가 낼 수 있는 최대 성능**이다.
지붕에 못 미치면 다른 문제(캐시 미스, 명령어 낭비 등)가 있는 것이다.

**왜 이 개념이 이 프로젝트에서 중요한가.**
machine balance 는 **하드웨어의 성질을 숫자 하나로 요약**한다.
"Pi 에서만 되는 이야기"가 아니라 "balance 가 12 인 기계에서 성립하는 규칙"으로 쓰면
다른 하드웨어로 옮길 수 있는 주장이 된다.

---

## 3-4. GEMM 의 산술 강도가 배치 크기인 이유

이 유도가 "청크는 32 이상"이라는 규칙의 전부다.

**상황**: 가중치 행렬 `W` (d × k) 에 토큰 B개를 곱한다.

```
연산량   = 2 · B · d · k                    (곱셈+덧셈)
메모리   ≈ d · k · (가중치 1바이트 크기)     ← 가중치가 압도적
```

활성화(B·k)와 출력(B·d)도 읽고 쓰지만, 보통 `B ≪ d, k` 라 가중치가 지배한다.

```
산술 강도 = 2·B·d·k / (d·k·s)  =  2B / s        (s = 가중치 바이트/원소)
```

**즉 강도는 B 에만 비례한다.** d, k 는 약분되어 사라진다.

| 가중치 정밀도 | s | 강도 |
|---|---|---|
| F32 | 4 | B/2 |
| F16 | 2 | B |
| **Q4_0** | ~0.56 | **~3.5 B** |

> **양자화는 메모리를 아끼는 동시에 산술 강도를 올린다.**
> 같은 배치에서 더 compute-bound 가 된다는 뜻이다.

**Pi5 (balance ≈ 12) 에 대입:**

```
Q4_0 : 3.5B ≥ 12  →  B ≥ 3.4
F32  : B/2  ≥ 12  →  B ≥ 24
```

이론상 3~4면 충분해 보이는데 **실측 포화점은 32** 다. 격차의 이유는
활성화 트래픽, 캐시 블로킹 효율, 명령어 오버헤드 등 모델이 무시한 항들이다.
**그래서 이론값이 아니라 실측 포화점을 쓴다.**

**결론적 규칙:**

> **배치(청크) 32 미만에서는 prefill 도 memory-bound 다.**
> 그리고 32 를 넘으면 더 키워도 연산 효율 이득이 없다.
> → 청크 크기는 **연산이 아니라 통신·파이프라인 관점에서 정하면 된다.**

---

## 3-5. attention 의 산술 강도

Attention 은 GEMM 과 성질이 다르다. **재사용할 "가중치"가 없기 때문이다.**

```
Attention 의 입력  : Q (내 토큰들), K/V (캐시)
GEMM 의 입력      : 활성화, W (모든 토큰이 공유)
```

`K`, `V` 는 **토큰마다 다른 데이터**다. 여러 토큰이 공유하는 건 맞지만,
"몇 개의 쿼리 토큰이 같은 KV 를 함께 쓰느냐"에 따라 재사용률이 정해진다.

**쿼리 토큰 T개를 묶어(타일) 처리하면:**

```
KV 읽기  : S × kvDim × 2 × 4B          (T개가 공유)
연산     : 2 × T × S × headDim × 2      (QK^T 와 AV)

강도 ≈ T / 2  FLOP/byte     (F32 KV 기준)
```

**balance 12 에 도달하려면 `T ≈ 24`.** GEMM 의 32 와 비슷한 자리다.

**여기서 나오는 실무적 함정** — 이게 실제로 큰 성능 차이를 만든다:

decode 는 쿼리가 1개라 `T=1` 이고, 강도가 0.5 밖에 안 된다. **어쩔 수 없이 memory-bound.**
그런데 **prefill 이 decode 용 커널(T=1)을 반복 호출하면**, 배치가 있는데도 T=1 로 돌게 된다.

```
KV 캐시를 (배치 크기)번 반복해서 읽는다
→ 트래픽이 배치 배로 늘어난다
→ 잘못 만들면 attention 이 전체 시간의 절반 이상을 먹는다
```

**교훈**: "attention 이 병목이다"라는 측정 결과는 **커널이 제대로 배치화됐는지 확인한 뒤**에만
믿을 수 있다. 아니면 구현 문제를 알고리즘 문제로 오진한다.

---

## 3-6. 타일링

**목적**: 데이터를 한 번 가져와서 **최대한 오래 쓰기**. 산술 강도를 인위적으로 올린다.

**단순 행렬 곱의 문제:**

```
for i, j:
    C[i][j] = Σ_k A[i][k] · B[k][j]
```

안쪽 루프가 `B` 의 열 전체를 훑는다. `B` 가 캐시보다 크면 **매번 DRAM 까지 간다.**

**타일링**: 캐시에 들어가는 작은 블록으로 쪼개, 그 블록을 다 쓰고 넘어간다.

```
for ii, jj, kk (블록 단위):
    A[ii][kk], B[kk][jj] 를 캐시로 가져온다
    그 안에서 가능한 모든 곱셈을 끝낸다     ← 여기서 재사용
```

블록 크기 T 일 때, 한 번 가져온 데이터로 T배 더 계산한다 → **강도가 T배**.

**FlashAttention 은 이 아이디어를 attention 에 적용한 것이다.**
차이는 계층이다 — GPU 에서는 HBM↔SRAM, CPU 에서는 DRAM↔L2.
**계층 이름이 다를 뿐 논법은 같다.**

---

## 3-7. online softmax

타일링을 attention 에 적용하려 하면 **softmax 가 걸림돌**이 된다.

```
softmax(s)_j = e^{s_j} / Σ_j e^{s_j}
                          └─ 분모가 전체 합
```

**분모를 알려면 모든 값을 봐야 한다.** 그러니 타일 하나만 보고는 결과를 확정할 수 없다.
게다가 `e^{s}` 는 s 가 크면 오버플로하므로, 실무에서는 최대값을 빼고 계산한다
(이것도 전체를 봐야 안다).

**online softmax 는 "지금까지 본 것 기준"으로 계산해 두고, 새 값이 오면 보정한다.**

상태 두 개를 들고 다닌다:

```
m : 지금까지 본 최대값
d : 지금까지의 분모 (m 기준으로 계산된 것)
```

새 블록에서 최대값 `m'` 를 만나면:

```
m_new = max(m, m')
d_new = d · e^{m − m_new}  +  d' · e^{m' − m_new}
        └─ 기존 분모를 새 기준으로 환산
```

`e^{m − m_new}` 를 곱하는 것이 **"기준점 변경"** 이다.
지수 함수라서 기준을 바꾸는 게 곱셈 한 번으로 끝난다 — 이게 이 트릭이 성립하는 이유다.

출력도 같은 방식으로 보정하며 누적한다. **결과는 한 번에 계산한 것과 정확히 같다.**

**두 가지 이득:**

1. **중간 버퍼를 안 만들어도 된다.** `S × S` 크기의 attention 행렬을 메모리에 쓰지 않는다.
2. **[LSE merge](#6-3-lse-merge--부분-attention-을-정확히-합치는-법) 의 수학적 기반이 된다.**
   블록 단위로 쪼개 계산하고 합칠 수 있다는 것은, **다른 기계에서 계산해 합쳐도 된다**는 뜻이다.

# 4부. 숫자를 줄이기 — 양자화

## 4-1. 양자화가 하는 일

모델 가중치는 원래 32비트 실수(F32)다. 이걸 **더 적은 비트로 표현**하는 것이 양자화.

**왜 하나.** 두 가지 다 이득이다:

```
메모리   : 8B 모델이 32 GB → 4.5 GB    (담을 수 있게 됨)
대역폭   : 읽는 바이트가 1/7           (decode 가 그만큼 빨라짐)
```

**왜 되나.** 신경망 가중치는 **정밀도에 관대하다.** 값 하나가 조금 틀려도
수천 개를 더하는 과정에서 오차가 상쇄된다.

**기본 형태 (선형 양자화):**

```
저장 : q = round( x / scale )        정수
복원 : x̂ = q · scale                 근사값
```

`scale` 은 "정수 1칸이 실수로 얼마인가"다. 값의 범위에 맞춰 정한다.

---

## 4-2. 블록 양자화

**단순한 방법의 문제**: 텐서 전체에 `scale` 하나를 쓰면, 큰 값 하나 때문에
scale 이 커지고 **작은 값들이 전부 0으로 뭉개진다.**

```
값들: [0.01, 0.02, 0.015, ..., 8.0]
scale 이 8.0 에 맞춰지면 → 0.01 은 4비트로 표현 불가
```

**블록 양자화**: 값을 32개씩 묶고, **블록마다 자기 scale** 을 둔다.

```
블록 = 값 32개 + 그 블록만의 scale 1개
```

각 블록 안에서는 값의 범위가 비슷하므로 scale 이 잘 맞는다.
**저장 오버헤드는 32개당 scale 하나이므로 미미하다.**

---

## 4-3. Q4_0 과 Q8_0

`Q<비트>_<변형>` 표기다. `_0` 은 대칭형(offset 없음).

**Q4_0** — 가중치용:

```
블록 = 값 32개 (각 4비트) + fp16 scale 1개
     = 16 byte  +  2 byte  =  18 byte / 32값
     = 4.5 bit/값
```

4비트는 부호 없는 정수 0~15 로 저장하고, **복원할 때 8을 빼서** −8~+7 로 만든다.
이 8을 **zero-point** 라 한다.

```
x̂ = (q − 8) · scale
```

**Q8_0** — 활성화용:

```
블록 = 값 32개 (각 8비트) + fp16 scale = 34 byte / 32값
```

**왜 가중치는 4비트, 활성화는 8비트인가.**

| | 크기 | 정밀도 요구 |
|---|---|---|
| 가중치 | 크다 (GB 단위, **읽기 트래픽 지배**) | 관대 (학습으로 굳어진 값) |
| 활성화 | 작다 (배치×hidden) | 민감 (입력마다 분포가 달라짐) |

**줄여야 할 것은 가중치이고, 지켜야 할 것은 활성화다.** 그래서 비대칭으로 간다.

**연산은 정수로 한다.** Q4_0 가중치 × Q8_0 활성화를 int8 정수 연산으로 처리하고
마지막에 두 scale 을 곱해 실수로 되돌린다. 이게 다음 항목으로 이어진다.

---

## 4-4. SIMD 와 내적 명령어

**SIMD** (Single Instruction Multiple Data): 명령어 하나로 여러 데이터를 동시에 처리.
ARM 의 NEON 은 128비트 레지스터를 쓴다.

```
128비트에 담기는 것:
  float32 4개
  int8   16개      ← 정수가 4배 이득
```

**정수 연산이 유리한 첫 번째 이유가 이것이다** — 같은 레지스터에 4배 많이 들어간다.

**dotprod (SDOT)** — ARMv8.2 의 특수 명령어:

```
일반적으로 내적을 하려면 : 곱하기 → 넓히기 → 더하기 (여러 명령어)
SDOT 는 한 명령어로     : int8 4개씩의 내적을 계산해 int32 에 누적
```

`vdotq_s32` 하나가 **int8 16개 × 16개를 처리해 int32 4개를 만든다**
— 4 lane × 4 곱셈 = **16 MAC = 32 연산**.

> **정정 (2026-08-11).** 이 줄은 원래 "32 MAC = 64 FLOP"이라고 적혀 있었다. **2배 크다.**
> 128비트에는 int8 이 16개뿐이므로 MAC 은 16개다.
> 64 FLOP 을 쓰면 피크가 614 GOPS 가 되어 [11-results §5](../11-results.md) 의
> **307 GOPS** 와 모순되고, 단일 노드 달성률이 68 % 가 아니라 34 % 로 나온다.
> 유도는 [07-math-measurement §3-1](07-math-measurement.md#3-1-하드웨어-피크-성능-유도) 에 있다.

**이 명령어가 있느냐 없느냐가 3~4배 차이를 낸다.**
그런데 컴파일러가 이 명령어를 쓰려면 **CPU 기능 플래그가 켜져 있어야** 한다
(`__ARM_FEATURE_DOTPROD`). 빌드 플래그 하나로 조용히 꺼질 수 있고,
꺼져도 **결과는 맞게 나오므로 (느린 폴백 경로로 돌아서)** 눈치채기 어렵다.

> **교훈**: 저수준 커널은 "돌아간다"와 "제대로 돌아간다"가 다르다.
> 성능이 이상하면 **어느 경로로 실행되는지 먼저 확인**해야 한다.

---

## 4-5. 메모리 레이아웃과 repack

같은 데이터라도 **메모리에 놓인 순서**에 따라 속도가 달라진다.

**문제 1 — 언팩 비용.** 4비트 두 개가 1바이트에 붙어 있다.
계산하려면 매번 풀어야 한다:

```
load → and(하위 4비트) → shift(상위 4비트) → sub(zero-point 8 빼기)
```

이 언팩이 **명령어의 절반 이상**을 먹을 수 있다. 실제 계산(dotprod)은 몇 개뿐인데.

**문제 2 — 흩어진 접근.** 출력 행 4개를 동시에 계산하고 싶은데,
행이 메모리에 멀리 떨어져 있으면 로드를 4번 해야 한다.

**repack (재배치)** 은 **로드 시점에 한 번** 데이터를 재배열해 두는 것이다.
추론 중에 매번 하던 일을 미리 해 둔다.

| 기법 | 원리 |
|---|---|
| **zero-point 사전 흡수** | 저장할 때 XOR 로 −8 을 미리 적용 → 런타임 뺄셈 제거 |
| **출력 행 인터리브** | 4개 행을 번갈아 배치 → 로드 1회가 4행을 커버 |
| **scale 연속 배치** | 4개 scale 을 붙여 놔 벡터 명령어로 한 번에 곱함 |

**핵심 통찰**: **로드는 한 번이고 추론은 수천 번이다.**
로드 시점의 비용은 아무리 커도 상관없다. 런타임에서 명령어 하나 줄이는 게 낫다.

**추가 이득**: 재배치가 **크기를 바꾸지 않게** 설계하면(같은 바이트 수),
같은 메모리 위치에서 제자리(in-place)로 할 수 있어 추가 메모리가 0이다.

# 5부. 여러 대로 나누기

## 5-1. 나눌 수 있는 축은 네 개다

한 번의 forward 계산은 **3차원 격자**로 볼 수 있다.

```
축 1 : 토큰   (S개)      — 프롬프트의 각 위치
축 2 : 레이어 (L개)      — 깊이
축 3 : 폭     (h, 헤드)  — 각 레이어 안의 차원
```

**어느 축으로 자르느냐가 분산 전략이다.**

| 자르는 축 | 이름 | 노드가 맡는 것 |
|---|---|---|
| 폭 | **TP** (Tensor Parallel) | 모든 토큰 × 모든 레이어 × **일부 차원** |
| 레이어 | **PP** (Pipeline Parallel) | 모든 토큰 × **일부 레이어** × 모든 차원 |
| 토큰 | **CP/SP** (Context/Sequence Parallel) | **일부 토큰** × 모든 레이어 × 모든 차원 |
| 토큰 (근사) | 블록 병렬 | CP 인데 블록 간 참조를 생략 |

**각 축의 성질을 결정하는 것은 "그 축을 자르면 무엇이 깨지는가"다.**

```
폭   을 자르면 → 행렬 곱의 부분합이 흩어진다  → 매번 합쳐야 함 (통신 잦음)
레이어를 자르면 → 순서 의존이 그대로 남는다     → 기다림이 구조적
토큰 을 자르면 → attention 만 서로를 봐야 한다  → 통신이 적음
```

세 번째가 가장 유리해 보인다. 그런데 왜 다들 TP 를 쓰나?
**모델이 노드 하나에 안 들어갈 때는 선택지가 없기 때문이다** — TP/PP 는 가중치를 나누지만
CP 는 모든 노드가 가중치 전체를 복제해야 한다.

---

## 5-2. TP (텐서 병렬)

**아이디어**: 행렬 곱 `y = W·x` 에서 **W 를 열로 잘라** 각 노드가 일부 열만 계산한다.

```
W = [W_1 | W_2]      노드 1이 W_1, 노드 2가 W_2

노드 1 : y_1 = W_1·x
노드 2 : y_2 = W_2·x
결과   : y = [y_1 ; y_2]     이어 붙이면 끝  ← 통신 없음!
```

**여기까지는 통신이 필요 없다.** 문제는 다음 층이다.

다음 층이 `z = U·y` 라면, `U` 를 행으로 자르면:

```
노드 1 : z_1 = U_1·y_1      (부분합)
노드 2 : z_2 = U_2·y_2      (부분합)
z = z_1 + z_2               ← 더해야 완성. 여기서 통신
```

**즉 "열 분할 → 행 분할" 쌍이 끝날 때마다 한 번씩 합친다.**
트랜스포머 레이어에는 그런 쌍이 두 개 있다 — attention 블록과 FFN 블록.

> **레이어당 2회의 all-reduce.** 32레이어면 forward 한 번에 **64회**다.

**성질:**

| | |
|---|---|
| 장점 | 가중치가 나뉜다. 연산이 정확히 1/N 로 나뉜다. 부하가 균등하다 |
| 단점 | **동기가 매우 잦다.** 레이어마다 전원이 모여야 한다 |
| 통신량 | 합칠 데이터가 `배치 × 토큰 × hidden` — **prefill 에서는 토큰 수만큼 크다** |

**prefill 과 decode 의 결정적 차이**:

```
decode  : 토큰 1개  →  all-reduce 크기 = 2·h        (작다)
prefill : 토큰 S개  →  all-reduce 크기 = 2·S·h      (S배 크다)
```

**TP 는 decode 를 위해 설계된 구조다.** prefill 에 그대로 쓰면 통신량이 S배로 뛴다.

---

## 5-3. PP (파이프라인 병렬)

**아이디어**: 레이어를 나눠 맡는다. 노드 1이 0~7층, 노드 2가 8~15층, ...

```
노드1 → 노드2 → 노드3 → 노드4
```

**통신이 적다.** 경계에서 활성화 벡터 하나만 다음 노드로 넘긴다(P2P).
all-reduce 가 아니라 **일방향 전달**이라 전원이 모일 필요도 없다.

**그런데 문제가 있다 — 버블.**

```
시간 →
노드1 : [청크1][청크2][청크3]
노드2 :       [청크1][청크2][청크3]
노드3 :             [청크1][청크2][청크3]
노드4 :                   [청크1][청크2][청크3]
        └──────┘                    └──────┘
         앞이 빔                      뒤가 빔
```

**입력을 하나만 넣으면 한 번에 노드 하나만 일한다.** N배 느려지는 셈이다.

**해결책 — 청크를 여러 개 흘려보낸다** (chunked prefill / wave pipelining).
노드 1이 청크 2를 처리하는 동안 노드 2가 청크 1을 처리한다.
청크가 많을수록 버블 비율이 준다.

**그래도 남는 것:**

1. **채우고 비우는 구간은 없앨 수 없다.** 청크가 무한히 많지 않은 한.
2. **의존이 구조적이다.** 청크는 반드시 1→2→3→4 **순서대로** 지나야 한다.
   중간 노드가 하나 느리면 뒤가 전부 밀린다.
3. 프롬프트가 짧으면 청크 수가 적어 버블 비율이 크다.

> **통신 최적화로는 PP 의 대기를 못 줄인다.** 대기의 원인이 전송이 아니라 **순서 의존**이라서다.
> 이것이 TP 와 PP 의 근본적 차이다.

### 버블은 정량화된다 (추가 2026-08-11)

위 서술은 정성적이다. 실제로는 닫힌 식이 나온다. 마이크로배치 `M` 개, 스테이지 `N` 개,
스테이지당 시간 `t` 일 때:

```
T_N   = (M + N − 1) · t
속도향상 = M·N / (M + N − 1)
```

**두 극한이 이 축의 성질을 전부 말해 준다.**

```
M → ∞ :  속도향상 → N       이상적
N → ∞ :  속도향상 → M       ← 상한이 M 이다
```

> **`M = S / B_min` 이므로 프롬프트 길이가 유효 노드 수의 상한을 정한다.**
> S=448, B_min=16 이면 **28배가 절대 상한**이고, 노드를 더 붙여도 넘지 못한다.

유도, 불균형 계수 `ρ` 의 도입, 효율의 분해(`η = η_bubble × η_balance`),
그리고 **레이어 입자도가 왜 N=8 에서 균형화를 무의미하게 만드는지**는
[06-math-pipeline](06-math-pipeline.md) 에 있다.

### 그리고 실제로는 PP 가 이겼다

이 절의 서술만 읽으면 PP 가 가장 나쁜 축처럼 보인다. 실측 결과는 반대였다.

| 축 | 결과 |
|---|---|
| TP | 코드가 깨져 있었고, 애초에 **실행된 적이 없다** ([12-findings #9](../12-findings.md)) |
| SP | 단일 요청용 축이 아님 (P/D 분리용). 사용 불가 |
| CP (Ring) | exact 이지만 통신량이 PP 의 8배(168 vs 21 MB) → 보류 |
| **PP** | **4.39×** — 이 코드베이스에서 동작하는 유일한 축 |

**이유는 [06-math-pipeline §10](06-math-pipeline.md#10-통합-원리-병렬성과-산술-강도는-상충한다) 의
표 하나로 설명된다.** PP 는 노드당 토큰 수 `B` 를 건드리지 않으므로
**산술 강도를 깎지 않는 유일한 축**이고, 배리어도 쓰지 않는다.
그 대가인 버블만이 `M` 을 키워 완화할 수 있는 종류였다.

> 대역폭이 희소한 SBC 에서는 **"무엇을 잃는가"보다 "잃은 것을 되돌릴 수단이 있는가"가
> 축 선택을 결정한다.**

## 5-4. CP/SP (시퀀스 병렬)

**아이디어**: 토큰을 나눈다. 노드 1이 토큰 0~111, 노드 2가 112~223, ...

**대부분의 연산은 이걸로 끝난다.** FFN 도 projection 도 정규화도
**토큰 간 의존이 전혀 없으므로** 각자 자기 토큰만 하면 된다. 통신 0.

**문제는 attention 하나뿐이다.** 토큰 i 는 자기 앞의 **모든** 토큰의 K, V 를 봐야 한다.
그런데 앞 토큰들은 다른 노드에 있다.

**해결 1 — ring (pass-KV).** KV 를 원형으로 돌린다.

```
1라운드 : 각 노드가 자기 KV 로 부분 attention 계산
2라운드 : KV 를 이웃에게 넘김 → 받은 KV 로 부분 attention 추가
...
N라운드 후 : 모두가 모든 KV 를 한 번씩 봤다
```

부분 결과들은 [LSE merge](#6-3-lse-merge--부분-attention-을-정확히-합치는-법) 로 합친다.
**결과는 exact 하다.**

**핵심 장점 — 전송과 연산이 겹친다.** 다음 KV 를 받는 동안 지금 KV 로 계산할 수 있다.
그리고 이웃하고만 통신하므로 **전원이 모이는 배리어가 아니다.**

**해결 2 — pass-Q.** 반대로 쿼리를 돌린다. 쿼리가 KV 보다 작을 때 유리하다.

**GQA 와의 궁합.** 돌려야 할 KV 가 `kvDim`(1024)이지 `h`(4096)가 아니다.
**GQA 가 CP 를 4배 싸게 만든다.**

**대가**: 각 노드가 **가중치 전체를 복제**해야 한다. 모델이 노드 메모리에 들어가야만 쓸 수 있다.

**decode 로의 인계.** prefill 후 KV 가 토큰 구간별로 흩어져 있다.
decode 도 같은 축으로 하면 **옮길 필요가 없다** — 각 노드가 자기 구간에 대해
부분 attention 을 하고 LSE 로 합치면 된다. 교환량은 무시할 수준이다.

> **분산 축을 고르는 것은 "KV 가 어디에 어떤 모양으로 남을지"를 고르는 것이다.**
> prefill 축과 decode 축이 다르면 KV 를 재배치해야 하고, 그 비용이 TTFT 이득을 먹는다.

---

## 5-5. 집합 통신 (collective)

여러 노드가 데이터를 주고받는 **표준 패턴**들. 이름이 곧 동작이다.

| 이름 | 동작 | 전원 참여? |
|---|---|---|
| **broadcast** | 한 노드의 데이터를 전원에게 | 예 |
| **reduce** | 전원의 데이터를 합쳐 한 노드에게 | 예 |
| **all-reduce** | 전원의 데이터를 합쳐 **전원에게** | 예 |
| **allgather** | 각자의 조각을 모아 전원이 전체를 가짐 | 예 |
| **reduce-scatter** | 합친 뒤 조각내어 하나씩 나눠 가짐 | 예 |
| **P2P** | 한 노드 → 한 노드 | 아니오 |
| **ring** | 이웃에게만 순환 전달 (P2P 의 연쇄) | 아니오 |

**핵심 구분은 "전원이 모여야 하는가"다.**

```
all-reduce, allgather : 전원이 도착해야 진행  →  암묵적 배리어
P2P, ring             : 둘만 맞으면 진행      →  배리어 아님
```

**all-reduce = reduce-scatter + allgather.** 링 알고리즘으로 구현하면
각 노드가 `2(N−1)/N × 데이터` 만큼 보내면 된다 — 데이터 양은 최적이다.
**그런데 지연은 홉 수만큼 쌓인다.** 데이터가 작으면 전송 시간보다 **왕복 지연이 지배**한다.

---

## 5-6. 배리어와 straggler

**배리어**: 모든 노드가 도착할 때까지 기다리는 지점.

**비용의 성질이 특이하다:**

```
배리어 1회 비용 = (가장 느린 노드의 도착 시각) − (가장 빠른 노드의 도착 시각)
                + 통신 자체의 지연
```

**즉 평균이 아니라 최대값에 맞춰진다.**

**straggler (낙오자)** = 그 가장 느린 노드. 원인은 다양하다:

- 열 스로틀링 (SBC 에서 흔하다)
- OS 스케줄링 jitter
- 하드웨어 성능 차이 (이종 클러스터)
- **구버전 바이너리** (측정에서 가장 흔한 사고)

**왜 배리어가 무서운가 — 누적된다.**

```
배리어 1회에 평균 15 ms 손실
× 레이어당 2회 × 32레이어 × 청크 14개  =  896회
= 13초
```

**개별 지연은 작은데 횟수가 많아서 지배적이 된다.**

> **여기서 실무적으로 중요한 결론이 나온다.**
> 통신 최적화라 하면 보통 "보내는 바이트를 줄이자"를 떠올린다.
> 그런데 대기가 전송보다 훨씬 크면, **바이트를 반으로 줄여도 거의 안 빨라진다.**
> 줄여야 하는 것은 **배리어 횟수**다.
>
> 그리고 이 둘 중 뭐가 문제인지는 **재 봐야 안다.** 그래서 계측을
> "전송에 쓴 시간"과 "기다린 시간"으로 나누는 것이 중요하다.

**대기 방식도 성능에 영향을 준다.**

| 방식 | 반응 속도 | CPU 점유 |
|---|---|---|
| sleep(1ms) | 느림 (타이머 해상도에 묶임) | 없음 |
| spin (바쁜 대기) | 즉시 | **코어 하나를 통째로** |
| **poll/epoll** | 즉시 (커널이 깨움) | 없음 |

코어가 4개뿐인 기계에서 spin 은 연산 코어를 뺏어 **오히려 손해**다.
`poll` 이 두 마리 토끼를 잡는다.

## 5-7. 지연 대 대역폭

네트워크 성능은 숫자 하나가 아니다.

```
전송 시간 = 지연(latency) + 데이터 크기 / 대역폭(bandwidth)
```

| | 1 GbE | 의미 |
|---|---|---|
| 대역폭 | ~125 MB/s | 큰 데이터에서 지배 |
| RTT | ~0.2 ms + 스택 오버헤드 | 작은 데이터에서 지배 |

**교차점**: 1 GbE 에서 0.2 ms 동안 보낼 수 있는 양은 약 25 KB.

```
25 KB 보다 작은 메시지  →  지연이 지배 (크기를 줄여도 소용없다)
25 KB 보다 큰 메시지    →  대역폭이 지배
```

**분산 추론에서 왜 중요한가:**

```
decode  의 all-reduce : 2 × 4096 × 4B = 32 KB    ← 지연 지배 구간
prefill 의 all-reduce : 32 KB × 배치 32 = 1 MB   ← 대역폭 지배 구간
```

**같은 시스템인데 국면에 따라 병목이 다르다.**
decode 최적화(메시지를 압축)가 prefill 에서는 별 효과가 없고, 그 반대도 마찬가지다.

# 6부. 근사로 나누기

## 6-1. 블록 로컬 attention

**출발 질문**: attention 의 통신을 아예 **0** 으로 만들 수 없을까?

CP 는 KV 를 돌려야 한다. 그 교환을 **생략하면** 통신이 0이 된다.

```
프롬프트를 N 블록으로 나눈다
각 노드는 자기 블록 안에서만 attention 을 한다
블록 간 참조는 없다
```

**이건 근사다.** 원래 봐야 할 토큰을 안 보니까.

**얼마나 나쁜가.** 완화 요인이 하나 있다.

> **attention 은 대개 국소적이다.** 가까운 토큰에 큰 가중치가 몰리는 경향이 있다.
> **블록이 충분히 크면** 중요한 참조는 대부분 블록 안에 있다.

---

### ⚠ 정정 (2026-08-11) — 이 절의 원래 판단은 실측으로 반증됐다

원래 여기에는 두 번째 완화 요인으로 이렇게 적혀 있었다:

> ~~**블록 수가 적을수록 손실이 작다.** 2블록이면 경계가 1개, 64블록이면 63개다.~~
> ~~**역설적으로, 초장문을 겨냥한 연구보다 짧은 프롬프트에서 이 근사가 더 안전하다.**~~

**틀렸다.** [09 §2](../09-design-ring-cp.md) 가 단일 노드에서 attention 마스크만 바꿔
정확도를 측정한 결과:

```
생성 텍스트가 전부 반복 루프에 빠졌고, anchor 를 붙여도 회복되지 않았다
```

**결정하는 것은 블록의 *수* 가 아니라 블록의 *크기* 다.**

```
Star Attention  : 128 K 를 16~32 K 블록으로  →  블록 하나가 문서 한 장
이 프로젝트     : 447 을 56~112 토큰 블록으로 →  블록 하나가 문장 두어 개
```

블록 안에 **문맥이 남아 있어야** "attention 이 국소적"이라는 완화가 작동한다.
문장 두 개짜리 블록에는 남을 문맥이 없다.

> **따라서 결론이 뒤집힌다: 짧은 프롬프트에서 이 근사는 더 위험하다.**
> 블록 수가 적은 것은 경계 수를 줄여 주지만, 그 이득이 블록 크기 부족을 상쇄하지 못한다.
>
> **이 부정 결과가 [09](../09-design-ring-cp.md) 가 근사를 버리고 exact 를 택한 근거다.**
> 그리고 exact 노선(Ring CP)도 결국 통신량 때문에 보류됐다
> ([11-results §7](../11-results.md)) — 실제로 채택된 축은 PP 하나다.

**일반화할 교훈**: 알고리즘이 같아도 **파라미터 영역(regime)이 다르면 판단이 뒤집힌다.**
초장문 전제로 설계된 기법을 짧은 프롬프트에 옮길 때는
"무엇이 이 기법을 성립하게 하는 양인가"를 먼저 찾아야 한다. 여기서는 **블록 크기**였다.
다음 절 [6-2 anchor](#6-2-anchor) 의 재계산 vs 브로드캐스트 판단도 같은 구조다.

---

**부수적 이득 — 연산량 자체가 준다.**

```
attention 연산 : O(S²)

통째로     : S²
N블록      : N × (S/N)² = S²/N
```

**블록으로 나누면 총 attention 연산이 N배 줄어든다.**
TP 나 PP 는 이 이득이 없다 (연산량은 그대로 두고 나눠 맡을 뿐).

---

## 6-2. anchor

**블록 로컬 attention 의 약점**: 첫 블록을 제외한 모든 블록이 **문서의 시작을 못 본다.**

문서 앞부분에는 대개 전역적으로 중요한 정보가 있다 (주제, 지시문, 시스템 프롬프트).
게다가 트랜스포머에는 **attention sink** 라는 현상이 있다 — 초반 토큰 몇 개가
"주의를 흘려보내는 배수구" 역할을 해서, 없으면 softmax 분포가 망가진다.

**anchor**: 프롬프트 맨 앞 A 토큰을 **모든 블록의 접두**로 붙인다.

```
블록 0 : [토큰 0..111]
블록 1 : [anchor] + [토큰 112..223]
블록 2 : [anchor] + [토큰 224..335]
블록 3 : [anchor] + [토큰 336..447]
```

**anchor 를 각 노드가 어떻게 얻는가 — 두 가지 방법이 있고, 이게 설계 선택이다.**

| 방법 | 하는 일 | 비용 |
|---|---|---|
| **재계산** | 각 노드가 anchor 토큰을 자기가 직접 계산 | 노드당 **연산 +A토큰분** |
| **브로드캐스트** | 한 노드가 계산해 anchor **KV 만** 전송 | 전송 + 동기 |

**언제 어느 쪽이 유리한가 — 이것은 체제에 따라 갈린다.**

```
재계산 비용        ∝  A × (노드당 레이어 연산)
브로드캐스트 비용   ∝  A × kvDim × L × (1/대역폭)  +  L × 배리어비용
```

**중요한 것은 A 가 전체에서 차지하는 비율이다:**

```
노드당 토큰 = S/N 일 때,  재계산 오버헤드 비율 = A / (S/N)

S=128K, N=8, A=1K   →  1K / 16K  =  6 %     ← 무시 가능
S=2K,   N=4, A=128  →  128 / 512 = 25 %     ← 무시 못 함
S=512,  N=4, A=128  →  128 / 128 = 100 %    ← 연산이 2배
```

> **호스트 하나가 블록을 여러 개 맡으면 anchor 를 한 번 계산해 재사용할 수 있다**
> (amortization). 초장문에서는 이게 성립해서 재계산이 싸다.
> **노드당 블록이 하나뿐이면 희석할 대상이 없어 비용이 그대로 남는다.**

이것이 "기존 설계의 전제가 다른 체제에서 깨진다"의 구체적인 형태다.
알고리즘은 같은데 **파라미터 영역이 다르면 최적 선택이 뒤집힌다.**

## 6-3. LSE merge — 부분 attention 을 정확히 합치는 법

**질문**: 노드 1이 토큰 0~99 에 대해, 노드 2가 100~199 에 대해 attention 을 계산했다.
이 둘을 합쳐 "0~199 전체에 대한 attention" 을 만들 수 있나?

**답: 정확히 가능하다.** 그리고 교환할 데이터는 극히 적다.

**왜 어려워 보이는가.** softmax 의 분모가 전체 합이라서다.

```
out = Σ_j e^{s_j} v_j / Σ_j e^{s_j}
```

부분만 계산하면 분모가 자기 구간 것뿐이다.

**해결 — 분자와 분모를 따로 들고 다닌다.**

노드 p 가 자기 구간 `J_p` 에 대해 두 개를 계산한다:

```
분자 :  n_p = Σ_{j∈J_p} e^{s_j} v_j
분모 :  d_p = Σ_{j∈J_p} e^{s_j}
```

**그러면 전체는 그냥 더하면 된다:**

```
out = (n_1 + n_2) / (d_1 + d_2)
```

`e^{s_j} v_j` 와 `e^{s_j}` 는 **다른 구간과 무관하게** 계산되므로, 합이 정확히 성립한다.

**수치 안정성 문제와 LSE.** 실제로는 `e^{s}` 가 오버플로한다. 그래서 각 노드가
자기 구간의 최대값 `m_p` 를 빼고 계산한다.

```
ñ_p = Σ e^{s_j − m_p} v_j
d̃_p = Σ e^{s_j − m_p}
```

기준점이 다르므로 그냥 더할 수 없다. **공통 기준으로 환산한 뒤 더한다:**

```
m = max(m_1, m_2)

n = ñ_1 · e^{m_1 − m}  +  ñ_2 · e^{m_2 − m}
d = d̃_1 · e^{m_1 − m}  +  d̃_2 · e^{m_2 − m}

out = n / d
```

`m_p` 와 `d̃_p` 를 합쳐 `log-sum-exp` 형태로 주고받으므로 **LSE merge** 라 부른다.
[online softmax](#3-7-online-softmax) 와 정확히 같은 트릭이다 — 하나는 노드 안, 하나는 노드 사이.

**교환량:**

```
노드당 · 레이어당 · 헤드당 :  부분 출력 (headDim개) + LSE 스칼라 1개
                          =  (headDim + 1) float
```

전체 KV(수백 MB)에 비하면 **사실상 공짜**다.

**의미:**

> **KV 를 한 곳에 모을 필요가 없다.** 흩어진 채로 두고, 필요할 때 부분 결과만 합치면 된다.
> 그리고 이 병합은 **근사가 아니라 exact 하다.**

이것이 CP 의 ring 도, 블록 병렬의 최종 merge 도, 토큰 축 decode 도 성립하게 하는
**공통 기반**이다.

# 7부. 계산을 건너뛰기 — 선형대수

**여기서 답하려는 질문**: KV 를 만드는 데 96 % 의 연산이 든다.
그 96 % 를 **안 하고** KV 를 얻을 수는 없나?

---

## 7-1. 선형 사상

**선형 사상**(linear map)은 **행렬 곱 하나로 표현되는 변환**이다.

```
y = A · x
```

**"선형"의 뜻** — 두 성질을 만족한다:

```
A(x + x') = Ax + Ax'          더한 걸 변환 = 변환한 걸 더함
A(c·x)    = c·(Ax)            상수배가 통과함
```

**왜 선형이 특별한가.**

1. **표현이 유일하고 작다.** 어떤 선형 사상이든 행렬 하나로 완전히 기술된다.
2. **최적 근사를 닫힌 형태로 구할 수 있다.** ([최소제곱](#7-2-최소제곱과-정규방정식))
3. **계산이 빠르다.** 행렬 곱은 하드웨어가 가장 잘하는 연산이다.

**이 프로젝트에서의 쓰임.** 트랜스포머 레이어를 보면 이미 이런 형태가 있다:

```
K_l = W_k · φ(x_l)         ← 레이어 l 의 K 는 x_l 의 선형 사상
```

여기서 질문이 나온다:

> `x_l` 대신 **더 아래 레이어의 `x_k`** 를 써서, 다른 행렬 `A_l` 로 같은 `K_l` 을
> 만들 수는 없을까?
>
> ```
> K_l ≈ A_l · φ(x_k)       (l > k)
> ```

**된다면 무슨 일이 일어나나.** 레이어 k+1 부터 31 까지의 attention 과 FFN 을
**전부 건너뛸 수 있다.** 게다가 그 레이어들이 **서로 독립**이 되므로
아무 노드에나 나눠 줘도 통신이 0이다.

**될 이유가 있나.** [residual stream](#1-2-residual-stream) 에서 봤듯
`x` 는 레이어를 지나며 조금씩만 변한다. 인접 레이어의 `x` 는 닮아 있다.
그렇다면 `x_k` 안에 `x_l` 의 정보가 상당 부분 남아 있을 것이다.

**될 보장은 없다.** 실제 관계가 비선형이면 오차가 남는다. **그래서 재 봐야 한다.**

---

## 7-2. 최소제곱과 정규방정식

`A_l` 을 어떻게 정하나?

**아이디어**: 실제 데이터를 모아서, **가장 잘 맞는 A** 를 찾는다.

모델을 한 번 돌리면서 관측을 모은다:

```
입력  X : 각 토큰의 φ(x_k)     (n개 토큰 × 4096)
정답  Y : 각 토큰의 실제 K_l    (n개 토큰 × 1024)
```

**목표**: `X·A` 가 `Y` 에 최대한 가깝도록 A 를 정한다.

```
A* = argmin_A  ‖ X·A − Y ‖²_F
```

`‖·‖_F` 는 프로베니우스 노름 — **모든 원소의 제곱을 다 더한 것**이다.
즉 "예측과 정답의 차이를 제곱해서 전부 더한 값"을 최소로 만든다.

**왜 제곱인가.** ① 부호가 상쇄되지 않는다 ② 미분이 깔끔하다 ③ 닫힌 해가 나온다.

**닫힌 해 유도.** 목적함수를 A 로 미분해서 0으로 놓는다.

```
f(A)  = ‖XA − Y‖²  = tr( (XA−Y)ᵀ(XA−Y) )
∂f/∂A = 2Xᵀ(XA − Y) = 0
      → XᵀX A = XᵀY               ← 정규방정식 (normal equation)
      → A = (XᵀX)⁻¹ XᵀY
```

**이것이 핵심이다:**

> **학습이 아니다. 연립방정식을 푸는 것이다.**
>
> - 경사하강도, 역전파도, 에폭도 없다
> - `XᵀX` (4096×4096) 를 만들고 한 번 푸는 게 전부
> - 몇 분이면 끝나고 **GPU 가 필요 없다**

**비교 — 왜 이게 실무적으로 큰 차이인가:**

| | distillation (증류 학습) | 최소제곱 적합 |
|---|---|---|
| 필요한 것 | GPU, 학습 데이터, 며칠 | CPU, 관측 몇천 개, 몇 분 |
| 결과 | 더 정확할 수 있음 | 선형 범위 안에서 최적 |
| 접근성 | 연구실 설비 필요 | **노트북에서도 됨** |

**필요한 관측 수.** 미지수가 `4096 × 1024` 개인데, 각 토큰이 방정식 1024개를 준다.
`XᵀX` 가 역행렬을 가지려면 **X 의 행이 최소 4096개** — 즉 **토큰 4096개 이상**이 필요하다.
부족하면 해가 유일하지 않고 [과적합](#8-2-과적합과-holdout)된다.

## 7-3. ridge (정칙화)

**문제**: `XᵀX` 가 **거의** 특이(singular)하면 역행렬이 폭발한다.

관측이 부족하거나, 입력 차원끼리 상관이 높으면 이런 일이 생긴다.
결과적으로 A 의 원소가 비정상적으로 커지고, **훈련 데이터엔 잘 맞는데
새 데이터엔 엉망**이 된다.

**해결**: 대각선에 작은 값을 더한다.

```
A = (XᵀX + λI)⁻¹ XᵀY
```

**두 가지 해석:**

1. **수치적**: `λI` 를 더하면 모든 고유값이 λ 만큼 커진다.
   0에 가까운 고유값이 사라져 역행렬이 안정된다.
2. **최적화적**: 원래 문제에 벌점을 붙인 것과 같다.

```
A* = argmin_A  ‖XA − Y‖²  +  λ‖A‖²
                              └─ A 가 커지면 벌점
```

**"데이터에 맞추되, 너무 극단적인 A 는 쓰지 마라."**

**λ 는 어떻게 정하나.** 데이터 스케일에 휘둘리지 않게 하려면
행렬의 크기에 **비례**하게 잡는 게 안전하다:

```
λ = ridge × trace(XᵀX) / 차원수
```

이러면 `ridge` 를 0.001 처럼 고정해도 데이터 규모가 바뀌어도 동작한다.

## 7-4. 랭크

**행렬의 랭크** = 그 행렬이 담고 있는 **실질적인 정보의 차원 수**.

**직관적 예시:**

```
A = [ 1  2  3 ]
    [ 2  4  6 ]        ← 2행 = 1행 × 2
    [ 3  6  9 ]        ← 3행 = 1행 × 3

3×3 행렬이지만 실제 정보는 [1 2 3] 하나뿐  →  랭크 1
```

**의미**: `4096 × 1024` 행렬이라도 실제로는 **256차원 정보만** 담고 있을 수 있다.
그렇다면 4.2 M 개의 숫자로 저장하는 건 낭비다.

**왜 신경망 가중치의 랭크가 낮을 수 있나.**
학습된 가중치는 대개 **소수의 지배적인 방향**을 갖는다.
많은 방향은 거의 쓰이지 않는다. 이것이 LoRA, 모델 압축 등 여러 기법의 공통 전제다.

---

## 7-5. SVD 와 에너지

랭크를 **실제로 찾아내는** 표준 도구.

**SVD (특이값 분해)**: 어떤 행렬이든 이렇게 쪼갤 수 있다.

```
A = U Σ Vᵀ

  V : 입력 쪽 "방향들"     (정규직교)
  U : 출력 쪽 "방향들"     (정규직교)
  Σ : 대각행렬, 각 방향의 "세기"
```

**읽는 법**: A 가 하는 일은 사실

```
1. 입력을 V 의 방향들로 분해하고
2. 각 방향을 σ_i 배 늘리거나 줄이고
3. U 의 방향들로 다시 조립한다
```

이것뿐이다. **모든 선형 사상이 이 세 단계로 환원된다.**

**특이값 σ_i 는 크기 순으로 정렬된다:**

```
σ₁ ≥ σ₂ ≥ σ₃ ≥ ... ≥ 0
```

**σ 가 작다 = 그 방향은 거의 아무것도 안 한다** → 버려도 된다.

**에너지 비율** — 얼마나 버려도 되는지의 척도:

```
에너지(r) = (σ₁² + ... + σ_r²) / (σ₁² + ... + σ_n²)
```

**해석**: "상위 r개 방향이 전체 정보의 몇 %를 담는가."

```
에너지(256) = 0.95   →  256차원만 남기고 버려도 5 % 만 잃는다
```

**왜 제곱인가.** 프로베니우스 노름이 특이값의 제곱합이기 때문이다.
즉 에너지 비율이 곧 **"근사 오차의 비율"** 과 직결된다.

**Eckart-Young 정리**: 랭크 r 로 근사할 때, **상위 r개 특이값만 남기는 것이 최적**이다.
다른 어떤 랭크-r 행렬도 이보다 잘할 수 없다. **그래서 SVD 를 쓴다.**

---

## 7-6. 저랭크 근사

랭크가 낮으면 **작은 행렬 두 개의 곱**으로 쪼갤 수 있다.

```
A (4096 × 1024)  ≈  P (4096 × r) · B (r × 1024)
```

**절약** (r = 256):

```
원래  : 4096 × 1024        = 4.19 M
분해  : 4096×256 + 256×1024 = 1.05 M + 0.26 M = 1.31 M

→ 3.2배 절약
```

**연산도 줄어든다.** `A·x` 를 한 번에 하는 대신 `P·(B·x)` 로 두 번 하면:

```
직접   : 4096 × 1024 = 4.19 M 곱셈
분해   : 1024×256 + 256×4096 = 1.31 M 곱셈
```

**언제 이득인가.**

```
r < (d × k) / (d + k)
```

`4096×1024` 의 경우 `r < 819` 면 이득이다. r=256 이면 충분히 이득.

**주의**: 저랭크 근사는 **오차를 만든다.** 버린 방향의 정보가 사라진다.
얼마나 잃는지는 [에너지 비율](#7-5-svd-와-에너지)이 말해 준다.

---

## 7-7. 공유 기저와 대각 스케일링

**상황**: 상위 16개 레이어 각각에 대해 `A_l` 이 필요하다.

저랭크로 줄여도 레이어마다 `P_l`(4096×256), `B_l`(256×1024) 두 개씩 필요하다.
16레이어 × K,V 면 여전히 32쌍이다.

**가설**: 상위 레이어들의 KV 는 **같은 부분공간에 산다.**

근거가 있다. [residual stream](#1-2-residual-stream) 은 레이어를 지나며 조금씩만 변하고,
"레이어 간 KV 가 서로 닮았다"는 것은 KV 공유·압축 연구들이 이미 이용하고 있는 성질이다.

**그렇다면 방향(기저)은 공유하고, 레이어별 차이는 세기만 다르게 하면 된다.**

```
A_l  ≈  U · diag(d_l) · V

  V     : 공유  (256 × 4096)   — 입력을 256차원으로 압축
  d_l   : 레이어별 (256개)      — 각 방향의 세기
  U     : 공유  (1024 × 256)   — 256차원을 K 로 복원
```

**SVD 와 비교하면 구조가 보인다:**

```
SVD    :  A_l = U_l  Σ_l  V_lᵀ      모두 레이어별
공유기저:  A_l = U    D_l   V        U, V 만 공유
```

**즉 "모든 레이어가 같은 U, V 를 쓰고 Σ 만 다르다"는 제약을 건 것이다.**

**진짜 이득은 파라미터 수가 아니라 계산 순서에 있다.**

```
[공유 없이]  레이어마다 : K_l = P_l · (B_l · φ(x_k))     ← 큰 행렬 2개씩 매번

[공유 기저]
  z   = V · φ(x_k)          ← 한 번만! 모든 레이어 공통
  K_l = U · (d_l ⊙ z)       ← 레이어마다: 원소곱 + 작은 곱
```

`⊙` 는 **원소별 곱**(element-wise product) — 벡터 두 개를 같은 자리끼리 곱하는 것.
`d_l ⊙ z` 는 256번의 곱셈이 전부다.

**절감 규모** (상위 16레이어, K+V):

| | 파라미터 | 읽어야 할 바이트 | 연산 |
|---|---|---|---|
| dense (제약 없음) | 134 M | 75 MB | 268 MFLOP/token |
| **공유 기저** | **1.58 M** | **0.9 MB** | **18.9 MFLOP/token** |
| 비율 | 85× | **83×** | 14× |

**왜 이 구조가 CPU 에서만 의미가 있나 — 여기가 핵심이다.**

```
GPU : 대역폭 2 TB/s  →  75 MB 읽기 = 0.04 ms   (무시 가능)
SBC : 대역폭 9 GB/s  →  75 MB 읽기 = 8 ms      (레이어 연산보다 크다)
```

> **GPU 에서는 dense 로도 충분하다.** 그래서 GPU 기반 연구들은 이 구조를 안 쓴다.
> **메모리 대역폭이 병목인 기계에서만 83× 절감이 결정적이 된다.**
>
> "같은 알고리즘이라도 하드웨어 체제가 다르면 최적 구조가 달라진다"의
> 또 하나의 구체적 사례다.

# 8부. 맞는지 어떻게 아는가

## 8-1. 상대 오차

근사가 얼마나 정확한지 재는 표준 척도.

```
rel.err = ‖ 정답 − 예측 ‖ / ‖ 정답 ‖
```

**왜 나누나 (상대화).** 절대 오차만 보면 스케일에 휘둘린다.
값이 원래 1000 단위인 텐서에서 오차 10은 작지만, 값이 0.1 단위면 재앙이다.

**읽는 법:**

```
0.00  완벽
0.01  1 % 어긋남 — 대개 무해
0.10  10 % — 경계선
0.30  구조는 남았지만 신뢰하기 어렵다
1.00  0을 예측하는 것과 같은 수준 (완전 실패)
```

`rel.err = 1.0` 의 의미가 중요하다. **"아무것도 예측 안 함"과 같다는 뜻**이다.
(`Ŷ = 0` 을 넣으면 `‖Y−0‖/‖Y‖ = 1` 이다.) 그보다 크면 예측이 오히려 해롭다.

→ **더 깊이**: [07-math-measurement 2부](07-math-measurement.md#2부-근사-오차) —
**어떤 변환이 오차를 보존하는가.** 직교 변환(RoPE)은 `‖R(k−k̂)‖ = ‖k−k̂‖` 로 보존하고,
대각 스케일링과 일반 행렬은 증폭한다. 따라서 **근사는 뒤에 직교 변환만 남는 지점에
넣는 것이 가장 안전하다** — 그 지점 이후로는 오차 분석이 그대로 유효하다.

## 8-2. 과적합과 holdout

**과적합(overfitting)**: 가진 데이터에는 완벽히 맞는데 **새 데이터에서는 엉망**인 상태.

**왜 생기나 — 자유도 문제다.**

```
미지수가 관측보다 많으면, 해가 무한히 많다
그중 하나를 고르면 "가진 데이터"는 완벽히 맞출 수 있다
하지만 그건 데이터의 잡음까지 외운 것이다
```

**우리 경우의 구체적 계산:**

```
A_l 의 미지수 : 4096 × 1024
토큰 1개가 주는 방정식 : 1024개
→ 필요한 토큰 : 최소 4096개

관측이 460 토큰이면?  →  방정식이 미지수보다 훨씬 적다  →  반드시 과적합
```

**어떻게 알아채나 — holdout.**

```
데이터를 나눈다:
  80 %  → 적합(fit)에 쓴다
  20 %  → 손대지 않고 남겨 둔다 (holdout)

적합이 끝난 뒤 holdout 에서 오차를 잰다
```

**판정:**

| 적합 오차 | holdout 오차 | 진단 |
|---|---|---|
| 낮음 | 낮음 | 좋다. 진짜로 일반화된다 |
| 낮음 | **높음** | **과적합.** 외운 것이다 |
| 높음 | 높음 | 모델이 부족하다 (선형으로는 안 되는 관계) |

> **적합 오차만 보고 "성공"이라고 하면 안 된다.**
> 미지수가 많은 모델은 적합 오차를 얼마든지 낮출 수 있다.
> **holdout 오차가 유일하게 의미 있는 숫자다.**

**일반화(generalization)**: 새 입력에서도 동작하는 성질.
우리 맥락에서는 "캘리브레이션에 쓴 문서 말고 **다른 문서**에서도 KV 예측이 맞는가"다.
그래서 holdout 은 **다른 토큰**이 아니라 가능하면 **다른 문서**로 잡는 게 더 엄격하다.

## 8-3. 근사 기법을 공정하게 비교하기

**문제**: 근사 기법은 **정확도를 팔아 속도를 산다.**
그러니 "우리가 2배 빠르다"는 주장은 그것만으로는 의미가 없다.
정확도를 얼마나 깎았는지 말하지 않으면 비교가 안 된다.

**exact 기법과 근사 기법:**

| | 예 | 성질 |
|---|---|---|
| **exact** | Ring CP, TP, PP | 결과가 원본과 **수학적으로 동일** |
| **근사** | 블록 로컬 attention | 결과가 다르다. 대신 훨씬 싸다 |

**matched-accuracy 비교**: 두 기법을 **같은 정확도 지점에 맞춰 놓고** 속도를 잰다.

```
근사 기법의 파라미터(블록 수, anchor 크기)를 조절해
exact 와 같은 정확도가 나오는 지점을 찾는다
→ 그 지점에서 속도를 비교한다
```

이래야 "정확도를 포기해서 빠른 것"과 "진짜로 효율적인 것"을 구분할 수 있다.

**파레토 프론티어**: 정확도-속도 평면에 여러 설정을 찍으면 곡선이 나온다.

```
정확도
  ↑
  │  ●exact
  │    ●
  │      ●        ← 이 곡선이 파레토 프론티어
  │        ●
  └──────────→ 속도
```

**좋은 기법 = 곡선 전체를 바깥으로 밀어내는 기법.**
한 점에서만 이기는 것은 파라미터를 잘 고른 것일 수 있다.

**정확도는 무엇으로 재나.**

| 척도 | 무엇을 보나 | 한계 |
|---|---|---|
| perplexity | 다음 토큰 예측 확률 | 실사용 품질과 항상 일치하진 않음 |
| needle-in-haystack | 긴 문서에 숨긴 문장을 찾는가 | 장거리 참조에 특화 |
| RULER / LongBench | 장문 태스크 종합 | 계산 비용이 큼 |

**블록 로컬 attention 은 특히 장거리 참조를 깨뜨리므로**
perplexity 만으로는 손실이 안 드러날 수 있다.
**needle 계열 테스트가 이 근사에는 필수적이다.**

> **실제로는 더 단순한 방식으로 드러났다.** [09 §2](../09-design-ring-cp.md) 에서
> 블록 독립 인코딩은 **생성 텍스트가 반복 루프에 빠지는** 형태로 실패했다.
> 지표를 정교하게 고르기 전에 **출력을 눈으로 보는 것**이 먼저다.

→ **더 깊이**: [07-math-measurement](07-math-measurement.md) —
perplexity 를 `−log p` 부터 유도하고(**PPL = 실효 분기 계수**),
**PPL 백분율이 아니라 CE 차(nat)로 비교해야 하는 이유**,
지표가 코드 변경으로 **조용히 무효가 되는 조건**(행↔토큰 대응 붕괴),
그리고 게이트를 **분류기**로 보는 관점(거짓 음성이 더 위험한 이유: 깨진 구성은 대개 더 빠르다).

# 부록. 개념 지도

개념 사이의 의존을 한 장으로:

```
[토큰 → 임베딩 → residual stream]
                   │
                   ├─→ Attention (Q,K,V)  ─→ causal mask ─→ 앞 토큰 KV 불변
                   │        │                                    │
                   │        └─ O(S²)                             ▼
                   │                                        [KV 캐시]
                   ├─→ FFN (토큰 간 독립)                        │
                   │        │                     ┌──────────────┴──────────────┐
                   │        │                     ▼                             ▼
                   │        │              prefill (GEMM)              decode (GEMV)
                   │        │              compute-bound               memory-bound
                   │        │                     │                             │
                   │        │                     └─→ [TTFT] ←──────────────────┘
                   │        │
                   │        └─→ 나눌 축이 없음(폭만) ─→ TP
                   │
                   └─→ 깊이 순차 ─→ PP 의 구조적 대기
                            │
                            └─→ "건너뛸 수 없나?" ─→ [7부 선형대수]
                                                        │
                                    선형사상 → 최소제곱 → 랭크 → SVD → 저랭크 → 공유기저
                                                                            │
[하드웨어]                                                                   │
  메모리 계층 → 산술 강도 → roofline/balance ──────────────────────────────┘
                    │                              (83× 절감이 왜 결정적인가)
                    ├─→ GEMM 강도 = 배치 ─→ "청크 ≥ 32"
                    └─→ attention 강도 = T/2 ─→ 타일링 ─→ online softmax
                                                              │
[분산]                                                         ▼
  축 4개 → 집합통신 → 배리어/straggler          블록 로컬 attention ─→ anchor
              │                                        │
              └─→ latency vs bandwidth                 └─→ LSE merge (exact 병합)
```

**한 줄로 꿰면:**

> 깊이는 순차라 나눌 수 없고(1부), KV 캐시가 TTFT 의 전부이며(2부),
> SBC 는 메모리 대역폭이 부족해 배치가 작으면 아무것도 안 빨라진다(3~4부).
> 나눌 수 있는 축은 넷인데 각각 다른 대가를 치르고(5부),
> 토큰 축을 근사로 나누면 통신이 사라지며(6부),
> 아예 계산을 건너뛰려면 선형대수가 필요하고(7부),
> 근사인 이상 정확도를 같이 재야 의미가 있다(8부).
