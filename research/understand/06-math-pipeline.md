## 2. 파이프라인 시간 유도

### 2-1. 상황

레이어 `L` 개를 `N` 스테이지로 나눠 노드에 하나씩 준다.
마이크로배치 `M` 개를 순서대로 흘려보낸다.

```
시간 →
stage0 : [1][2][3][4]
stage1 :    [1][2][3][4]
stage2 :       [1][2][3][4]
stage3 :          [1][2][3][4]
         └──┬──┘        └──┬──┘
          채움(fill)     비움(drain)
```

### 2-2. 균형 잡힌 경우

모든 스테이지가 같은 시간 `t` 를 쓴다고 하자.

- 마이크로배치 1번이 마지막 스테이지에 **도착**하는 시각: `(N−1)t`
- 그때부터 마지막 스테이지가 `M` 개를 연달아 처리: `M·t`

```
T_N = (N − 1)t + M·t = (M + N − 1) · t
```

**검산**: `M=1` 이면 `T = N·t` — 한 번에 한 스테이지만 일하는 최악의 경우다.
`N=1` 이면 `T = M·t = T_1` — 맞다.

### 2-3. 불균형한 경우 (일반형)

스테이지 시간이 `t_1, …, t_N` 으로 다르면, **정상 상태의 주기는 가장 느린 스테이지**가 정한다.
느린 스테이지 앞에 큐가 쌓이고 뒤는 굶는다.

```
T_N = Σ_i t_i  +  (M − 1) · max_i t_i
      └── 첫 배치가 통과하는 시간 ──┘   └── 이후 M−1 개의 주기 ──┘
```

균형 잡히면 `Σt_i = Nt`, `max = t` 이므로 `(M+N−1)t` 로 환원된다. ✔

> **이 한 줄이 이 문서 전체의 뼈대다.**
> 앞항은 **지연(latency)**, 뒷항은 **처리량(throughput)** 이고,
> 뒷항에는 **평균이 아니라 최대값**이 들어간다.

## 3. 속도향상 공식과 그 극한

단일 노드는 마이크로배치 `M` 개를 전 레이어에 대해 처리하므로 `T_1 = M · Σ_i t_i` 다
(총 연산량이 보존된다는 가정 — 분할해도 FLOPs 는 그대로다).

균형 잡힌 경우 `Σt_i = N t`, `T_1 = MNt` 이므로:

```
        T_1        M N t              M N
S(N) = ───── = ───────────── = ─────────────
        T_N     (M+N−1) t          M + N − 1
```

**실측 검증** (S=448, B=16 → M=28):

| N | `MN/(M+N−1)` | 11-results 의 "모델 예측" |
|---|---|---|
| 2 | 56/29 = **1.93** | 1.93× ✔ |
| 4 | 112/31 = **3.61** | 3.61× ✔ |
| 8 | 224/35 = **6.40** | 6.40× ✔ |

공식이 그 표를 정확히 재현한다.

### 3-1. 두 극한

```
M → ∞ :  S → N          (노드를 늘린 만큼 빨라진다 — 이상적)
N → ∞ :  S → M          ← 상한이 M 이다
```

**두 번째가 중요하다.**

> **속도향상의 절대 상한은 마이크로배치 개수 `M = S / B_min` 이다.**
> S=448, B_min=16 이면 **28배**. 노드를 아무리 늘려도 이보다 빨라지지 않는다.
> **프롬프트 길이가 유효 노드 수의 상한을 정한다.**

### 3-2. 효율

```
        S(N)         M
η_bubble = ──── = ─────────
         N       M + N − 1
```

| N | `η_bubble` | 잃는 비율 `(N−1)/(M+N−1)` |
|---|---|---|
| 2 | 96.6 % | 3.4 % |
| 4 | 90.3 % | 9.7 % |
| 8 | **80.0 %** | **20.0 %** |
| 16 | 65.1 % | 34.9 % |

**효율이 50 % 이상이려면** `M ≥ N − 1`. 즉 `S ≥ B_min (N−1)`.
S=448, B_min=16 이면 `N ≤ 29`.

## 4. `M` 은 어디서 오나 — `B_min` 의 유래

`M = S / B` 이므로 `B` 를 작게 하면 `M` 이 커지고 버블이 줄어든다.
**그런데 무한히 작게 할 수 없다.**

[04-concepts §3-4](04-concepts.md#3-4-gemm-의-산술-강도가-배치-크기인-이유) 의 결과:

```
GEMM 산술 강도 = 2B / s        (s = 가중치 바이트/원소, Q4_0 은 ≈ 0.5625)
              ≈ 3.5 B          [FLOP/byte]
```

Pi5 의 machine balance 는 약 12 FLOP/byte 이므로 이론상 `B ≥ 3.4` 면 compute-bound 다.
그런데 **실측 포화점은 32** 다 (활성화 트래픽, 캐시 블로킹, 명령어 오버헤드 때문).

`B` 를 줄일 때 잃는 것은 **가중치 재스트리밍**이다.

```
가중치 총 읽기량 = (모델 가중치) × (청크 수) = W × S/B
```

`B` 를 반으로 줄이면 가중치를 두 배 읽는다. `B` 가 강도 임계 아래면 그 읽기가 곧 시간이다.

> **두 힘이 반대로 당긴다.**
> ```
> B 작게  →  M 크게  →  버블 감소       (파이프라인 이득)
> B 작게  →  강도 하락 →  노드당 시간 증가  (하드웨어 손해)
> ```
> **`B_min` 은 이 균형점이다.**

### ⚠ 문서 간 불일치 (기록)

| 문서 | 값 | 정의 |
|---|---|---|
| [04-concepts §3-4](04-concepts.md#3-4-gemm-의-산술-강도가-배치-크기인-이유) | **32** | 실측 **포화점** — 더 키워도 이득이 없는 지점 |
| [11-results §3](../11-results.md) | **16** | 스케일링 모델의 `B_min` — 효율이 아직 **유지되는** 하한 |
| [12-findings #11](../12-findings.md) | B=8 은 "최악 구간", 실효 32 로 맞춰 1.88× | — |

**서로 다른 것을 재고 있다.** 32 는 "여기까지 키우면 더 안 좋아지지 않는다",
16 은 "여기까지 줄여도 아직 견딘다"이다. 모델에 `B_min=16` 을 쓰면 `M=28` 이 나오고
그 예측이 실측 표와 맞으므로 모델용으로는 16 이 맞다.
**다만 인용할 때 어느 쪽 정의인지 밝혀야 한다.**
(→ [README §4 불일치 표](README.md#4-원본-문서-간-알려진-불일치))

## 5. 불균형을 식에 넣기

2-3 의 일반형에 **불균형 계수**를 정의해 넣는다.

```
       max_i t_i        max_i t_i
ρ ≜ ───────────── = N · ─────────         (ρ ≥ 1, 균형이면 ρ = 1)
      (Σ_i t_i)/N         Σ_i t_i
```

"가장 느린 스테이지가 평균의 몇 배인가"다. 이제 `Σt_i = Nt̄`, `max = ρ t̄` 이므로

```
T_N = N t̄ + (M−1) ρ t̄

          M · N t̄              M N
S(N) = ───────────────── = ─────────────
        N t̄ + (M−1)ρ t̄     N + (M−1) ρ
```

`ρ=1` 이면 3절의 공식으로 돌아간다. ✔

### 5-1. 실측에서 `ρ` 를 역산한다

[11-results §2](../11-results.md) 의 실측 배수를 넣고 `ρ` 를 푼다.

```
ρ = ( M·N / S_실측 − N ) / (M − 1)
```

| N | 실측 배수 | 역산된 `ρ` |
|---|---|---|
| 2 | 1.65× | **1.18** |
| 4 | 2.61× | **1.44** |
| 8 | 3.78× | **1.90** |

> **`ρ` 가 `N` 과 함께 단조 증가한다.** 이것이 이 데이터에서 읽어낼 수 있는
> 가장 중요한 사실이다. 하드웨어 개체차(`.166` 이 40 % 느림)만으로는
> `ρ` 가 `N` 에 따라 커질 이유가 없다 — 느린 기계는 어느 `N` 에서도 하나다.
> **`N` 에 의존해 커지는 것은 7절의 입자도뿐이다.**

`ρ` 는 여러 원인의 합성이므로 이 역산만으로 원인을 확정할 수는 없다
(스테이지별 계측이 필요하다 — [13-methodology §6](../13-methodology.md)).
다만 **어느 원인이 `N` 에 의존하는지**는 이 증가 패턴이 가려 준다.

## 6. 효율의 완전 분해 — 실측과 일치한다

측정된 총 효율은 두 인자의 **곱**이다.

```
η_total  =  η_bubble  ×  η_balance

           ┌─ M/(M+N−1)      구조적. 파이프라인이면 피할 수 없다
           └─ S_실측/S_예측   불균형. 분할을 고치면 줄일 수 있다
```

**검산** (M=28):

| N | `η_bubble` | `η_balance` (11-results) | 곱 | 11-results 의 "효율" |
|---|---|---|---|---|
| 2 | 96.6 % | 85 % | **82.1 %** | 83 % ✔ |
| 4 | 90.3 % | 72 % | **65.0 %** | 65 % ✔ |
| 8 | 80.0 % | 59 % | **47.2 %** | 47 % ✔ |

세 점 모두 1 % 이내로 맞는다.

> **이 분해가 실무적으로 중요한 이유:**
> N=8 에서 잃는 53 % 중 **20 %p 는 버블(구조적)이고 33 %p 는 불균형**이다.
> 분할을 완벽히 고쳐도 80 % 가 천장이다. 그 이상을 원하면
> **`M` 을 키우는 수밖에 없고**, `M = S/B_min` 이므로
> ① 프롬프트를 길게 하거나 ② `B_min` 을 낮추는(커널 개선) 것뿐이다.

## 7. 입자도 — 왜 N=8 에서 균형화가 실패하는가

### 7-1. 문제

스테이지 부하를 조절하는 유일한 손잡이는 **레이어를 몇 개 주느냐**다.
레이어는 쪼갤 수 없으므로 **조절이 이산적(discrete)** 이다.

```
조절 단위 = 레이어 1개
목표 스테이지 시간 = 전체/(N) ≈ (L/N) 레이어분

⟹  상대 조절 해상도 = 1 / (L/N) = N / L
```

| N | 스테이지당 레이어 | 조절 해상도 `N/L` | 06/11 의 실측 표기 |
|---|---|---|---|
| 2 | 16 | 6.3 % | — |
| 4 | 8 | 12.5 % | 11 % |
| 8 | **4** | **25 %** | **22 %** |
| 16 | 2 | 50 % | ~44 % |

### 7-2. 왜 N=8 에서 조정이 무의미해지는가

느린 노드에서 레이어 하나를 빼면 **그 레이어가 다른 노드로 간다.**

```
N=8, 균등 4레이어. 노드 .166 이 1.4배 느리다고 하자 (단위: 레이어 1개 = 1)

기본       :  .166 = 4 × 1.4 = 5.6   ← 최대
             나머지 = 4.0
             ρ = 5.6 / 4.2 = 1.33

.166 을 3레이어로:
             .166 = 3 × 1.4 = 4.2
             그 1개를 받은 노드 = 5.0   ← 새 최대
             ρ = 5.0 / 4.2 = 1.19
```

이론상 12 % 개선이다. 그런데 [11-results §2](../11-results.md) 의 각주가 말하듯
**세션 간 편차가 10 %** 다. **개선폭이 잡음에 묻힌다.**

실제로 [12-findings #14](../12-findings.md) 는 최적 배정 `5,4,3,4,5,4,4,3` 으로
7,165 → 7,360 ms — **개선 없음**을 기록한다.

N=4 에서는 8레이어씩이라 조절 해상도가 12.5 % 이고, 실제로 2.52 → 2.81× (11 %) 가 나왔다.
**같은 방법이 N=4 에서는 통하고 N=8 에서는 안 통한다. 차이는 입자도뿐이다.**

### 7-3. 일반 법칙

```
정적 균형화가 유효할 조건 :   N / L  <  달성하려는 개선폭  ,  그리고  개선폭 > 측정 잡음
```

> **`N` 을 키우면 두 가지가 동시에 나빠진다:**
> ① 버블이 커지고(`η_bubble ↓`) ② 균형화 수단이 무뎌진다(`N/L ↑`).
> 그래서 스케일링 효율이 47 % 까지 떨어진다.
>
> **탈출구는 `L` 을 늘리는 것 — 즉 레이어보다 잘게 쪼개는 것이다.**
> `attn | FFN` 경계로 나누면 조절 단위가 두 배가 된다(FFN 이 레이어 FLOPs 의 81 %
> 이므로 정확히 반은 아니지만 해상도는 개선된다).
> [12-findings #14](../12-findings.md) 의 "다음" 항목이 이것이다.

## 8. 이종 노드 분할은 정수계획 문제다

정식화하면 이렇다. 노드 `i` 의 레이어당 처리 시간을 `c_i`, 배정 레이어 수를 `n_i` 라 하면:

```
minimize    max_i ( c_i · n_i  +  e_i )
subject to  Σ_i n_i = L ,   n_i ∈ ℤ≥0
```

`e_i` 는 스테이지 고유 상수다. 이 프로젝트에서는 **마지막 스테이지의
final norm + lm_head = 약 35 ms** 가 여기 들어간다
([10 §8](../10-design-prune-pipeline.md) 이 위치 요인 ~65 ms 로 측정).

이것은 **makespan 최소화** 문제이고, 정수 제약이 없으면 닫힌 해가 있다.

```
연속 완화 해 :   n_i* = (L + Σ_j e_j/c_j) · (1/c_i) / Σ_j (1/c_j)  −  e_i/c_i
```

즉 **빠른 노드에 `1/c_i` 에 비례해 배정**하고, 상수 `e_i` 만큼 미리 빼 준다.

**정수 제약이 만드는 격차(integrality gap)** 가 7절의 입자도다.

```
반올림 오차 ≤ 0.5 레이어  ⟹  스테이지 시간 오차 ≤ 0.5 c_i
상대 오차 ≤ 0.5 / (L/N) = N / (2L)
```

N=8 이면 12.5 %, N=16 이면 25 %. **이 하한은 알고리즘으로 못 넘는다 — 오직
`L` 을 키우거나(서브레이어 분할) `c_i` 를 균등하게 만들어야(동종 하드웨어) 사라진다.**

### 8-1. `c_i` 는 무엇으로 재나

[13-methodology §7](../13-methodology.md) 의 **워커 순서 치환**이 여기 대응한다.
`c_i`(기계 요인)와 `e_i`(위치 요인)를 분리하려면 같은 기계를 다른 위치에 놓고 재야 한다.

```
기계 .166 :  rank2 에서 371 ms,  rank1 에서 354 ms   →  위치와 무관하게 느리다  ⟹ c_i 크다
rank3     :  .113 이 오면 303,   .191 이 오면 269    →  다른 위치보다 +65 ms    ⟹ e_i 있다
```

> **둘 다 정적이다.** 따라서 1회 프로파일 + 정적 분할로 처리된다 — PipeEdge 가
> 이미 하는 일이고 새로울 것이 없다. **동적 재분할이 정당화되려면 데이터 의존
> 요인이 있어야 하고**, 그것이 12절의 가지치기다.

## 9. Amdahl 과의 관계

Amdahl 의 법칙은 "직렬 비율 `f` 가 있으면 속도향상은 `1/f` 를 못 넘는다"이다.
파이프라인 버블은 이것의 **구조적 사촌**이다.

```
Amdahl   :  일부 구간이 원리적으로 병렬화 불가
파이프라인 :  전 구간이 병렬화 가능한데, 채우고 비우는 동안 일부 노드가 논다
```

버블을 "실효 직렬 비율"로 환산하면:

```
f_eff = (N − 1) / (M + N − 1)
```

| N (M=28) | `f_eff` | Amdahl 상한 `1/f_eff` |
|---|---|---|
| 4 | 9.7 % | 10.3 |
| 8 | 20.0 % | 5.0 |

**차이가 하나 있다.** Amdahl 의 `f` 는 문제의 성질이라 고정이지만,
**파이프라인의 `f_eff` 는 `M` 에 의존해 줄일 수 있다.**
그래서 GPU 학습에서 마이크로배치를 늘리는 것이 표준 처방이다.

**여기서는 그 처방이 막혀 있다.** `M = S/B_min` 인데 `S` 는 사용자가 주는 값이고
`B_min` 은 하드웨어가 정한다. **prefill 은 학습과 달리 `M` 을 자유롭게 못 늘린다.**
이것이 SBC prefill 고유의 제약이다.

## 10. 통합 원리: 병렬성과 산술 강도는 상충한다

[09 §1](../09-design-ring-cp.md) 의 논증을 유도로 다시 쓴다.

노드 하나에 **토큰 `B` 개**와 **가중치의 `f` 비율**을 준다. 레이어 하나에서:

```
연산량   =  B · f · C          (C = 레이어당 토큰 1개 FLOPs)
읽는 바이트 =  f · W            (W = 레이어 가중치 바이트, 활성화는 무시)

산술 강도 =  B f C / (f W)  =  B C / W
```

> **`f` 가 약분되어 사라진다. 산술 강도는 `B` 에만 의존한다.**

이 한 줄이 축의 성격을 가른다.

| | 토큰 축 (CP) | 텐서 축 (TP) | 깊이 축 (PP) |
|---|---|---|---|
| 노드당 `B` | **S/N** ← 강도 `1/N` 로 하락 | S ← 유지 | S/M 청크 단위, `N` 과 무관 |
| 노드당 `f` | 1 (전체 복제) | 1/N | 1 (자기 레이어는 전체) |
| 통신 | ring KV — attention 에만 | 레이어당 all-reduce ×2 | 경계 P2P 1회 |
| 잃는 것 | **산술 강도** | **배리어 횟수** | **버블 + 입자도** |

**PP 가 이 표에서 특이하다.** `B` 를 건드리지 않는다 — 각 노드가 마이크로배치 전체를
자기 레이어에 대해 처리하므로 강도가 유지되고, 통신도 경계 하나뿐이다.
대신 **깊이가 순차라 버블을 낸다.**

> [11-results](../11-results.md) 에서 PP 가 이긴 이유가 이 표에 있다.
> SBC 는 대역폭이 희소해 강도 하락(CP)과 배리어(TP)가 둘 다 비싸다.
> **PP 의 대가(버블)만이 `M` 을 키워 완화할 수 있는 종류였다.**

### 10-1. 하이브리드 = 인수분해 문제

`N = N_tok × N_ten × N_pp` 로 인수분해하는 문제가 된다.

```
T ≈ max( B f C / P , f W / BW ) · L  +  2 L N_ten τ  +  ring(N_tok)  +  버블(N_pp)
    └── 노드당 계산 (강도가 낮으면 오른쪽이 이긴다) ──┘
```

측정된 두 상수가 해를 결정한다.

| 상수 | 값 | 출처 |
|---|---|---|
| machine balance | 11~14 FLOP/byte | 110 GFLOPS ÷ 8~10 GB/s |
| 배리어 `τ` | 16.3 ms | TP2 syncWait 14,611 ms ÷ 896 회 |

**기존 연구는 축을 고정하고 최적화한다** (Ring Attention = 토큰, Megatron = 텐서,
Galaxy = 정적 하이브리드). 전부 GPU 전제라 대역폭이 넉넉해 **강도가 문제되지 않고
통신 비용만 본다.** 대역폭이 희소한 CPU 클러스터에서는 **분할 자체가 강도를 깎는다.**

## 11. 통신 모델 — 왜 PP 가 이겼는가

### 11-1. 전송 시간의 두 항

```
전송 시간 = 지연(latency) + 바이트 / 대역폭
```

1 GbE 에서 RTT ≈ 0.2 ms, 대역폭 ≈ 125 MB/s 이므로 **교차점은 약 25 KB** 다.

```
< 25 KB  →  지연 지배. 바이트를 줄여도 소용없다. 줄여야 할 것은 횟수
> 25 KB  →  대역폭 지배
```

### 11-2. 축별 통신량과 횟수

청크 폭 `B`, 청크 수 `M`, 레이어 `L`:

| 축 | 1회 크기 | 횟수 | 성질 |
|---|---|---|---|
| TP | all-reduce `2·B·h·4B` (B=16 → 512 KB) | `2·L·M` = 1,792 | **배리어** — 전원이 모여야 함 |
| PP | 경계 활성화 `B·h·4B` = 256 KB | `(N−1)` 홉 × `M` | **P2P** — 둘만 맞으면 진행 |
| CP | KV `B·kvDim·2·4B` × 앞 노드 수 | `L·M` | P2P, FFN 뒤에 은닉 가능 |

측정된 총량: **TP4 = 448 MB, PP4 = 21 MB, CP(N=8) = 168 MB**.

### 11-3. 그런데 바이트는 원인이 아니었다

[12-findings C](../12-findings.md) 의 반증표가 핵심이다.

```
TP4(448 MB) 와 PP4(21 MB) 가 21배 차이인데 시간이 같았다
```

이유는 [12-findings #9](../12-findings.md) 였다 — **`--workers` 는 자동으로 PP 라
TP 가 한 번도 실행된 적이 없었다.** 두 측정이 사실 같은 실행이었다.

> **이 사고가 방법론에 남긴 것**: 통신량 가설을 검증하려면
> 먼저 **그 구성이 실제로 실행되고 있는지**를 확인해야 한다.
> [13-methodology §1](../13-methodology.md) 의 정확성 게이트와 §4 의 md5 대조가
> 여기서 나왔다.

**바이트가 아니라 대기가 지배한다**는 관찰(`syncWait : syncXfer = 7:1`)은
여전히 유효하다. 다만 그 대기의 원인이 배리어가 아니라
**다른 노드가 무언가에 막혀 있는 것**이었다([13-methodology §6](../13-methodology.md)).

```
syncWait 이 크다  ≠  통신이 문제다
syncWait 이 크다  =  누군가 늦게 도착했다  →  왜 늦었는지는 그 노드에서 재야 안다
```

## 12. 가지치기가 이 모델을 어떻게 깨는가

[10-design-prune-pipeline](../10-design-prune-pipeline.md) 의 설계 근거를 이 모델로 쓴다.

### 12-1. 깊이별 부하가 상수가 아니게 된다

지금까지 `c_i`(레이어당 시간)를 노드 고유 상수로 취급했다.
레이어 `k` 이후 토큰을 잔존율 `r` 로 자르면:

```
레이어 l 의 토큰 수  =  B          (l < k)
                    =  r · B      (l ≥ k)

⟹ 레이어별 연산량이 깊이의 함수가 된다
```

`n_i` 개 레이어를 맡은 스테이지 `i` 의 시간은 이제

```
t_i = Σ_{l ∈ stage i} c · B_l
```

이고 **깊은 스테이지일수록 작다.** 균등 분할이 원리적으로 틀린 분할이 된다.

### 12-2. 연산 감축의 상한

레이어 `k` 이후를 `r` 로 자르면 총 연산비는

```
연산비 = 1 / ( k/L + (L−k)/L · r )
```

| k \ r | 0.7 | 0.5 | 0.3 |
|---|---|---|---|
| 4 | 1.36× | 1.78× | 2.58× |
| 8 | 1.29× | 1.60× | 2.11× |
| 16 | 1.18× | 1.33× | 1.54× |

**감축만으로는 2배 남짓이다.** 분산(3.78×)과 곱해 6~9× 가 목표 범위이고,
"몇십 배"는 정확 연산으로 불가능하다 — 단일 노드가 이미 하드웨어 피크의 68 % 다.

### 12-3. 왜 **온라인** 재분할이 필요해지는가

`r` 이 **고정**이면 위 식으로 스테이지 부하를 미리 계산할 수 있다.
그러면 8절의 정적 최적화로 충분하고 새로울 것이 없다.

`r` 을 **임계값 기반(데이터 의존)** 으로 두면 프롬프트마다 잔존 수가 달라
`t_i` 를 사전에 알 수 없다. **이때 재분할이 실행 중에 일어나야 한다.**

```
정적 요인 (c_i, e_i)      →  1회 프로파일 + 정적 분할  →  기존 방법 (PipeEdge)
데이터 의존 요인 (r 가변)  →  온라인 재분할            →  이 연구의 대상
```

### 12-4. 경계 이동이 공짜인 이유도 이 모델에서 나온다

PP 는 노드당 가중치가 `L/N` 레이어분뿐이다.

```
PP8 기본 (4레이어)     :  0.8 GB
PP8 + δ=2 (8레이어)    :  1.6 GB      ← 8 GB 노드에 6 GB 여유
```

경계 `±δ` 를 미리 보유하면 **실행 중 경계 이동에 가중치 전송이 0** 이다.
**PP 라서 가능하다** — 단일 노드는 6.3 GB 전체를, TP 는 슬라이스를 들고 있어
이 여유가 없다.

> **10절의 표가 여기서 한 번 더 값을 한다.**
> PP 를 고른 이유는 통신량이었는데, 그 선택이 **동적 재분할의 여지**까지 같이 준다.

### 12-5. 현재 상태 — 정직하게

[10 §9](../10-design-prune-pipeline.md) 기준으로, 단순 노름 기반 가지치기는 **실패했다.**

```
layer 8, keep 0.9  →  연산비 1.08×,  perplexity 1.633 → 2.32 (+41.8 %)
```

**1.08배를 얻으려고 품질 42 % 를 잃는다.** 트레이드오프가 성립하지 않는다.
다음 후보는 중요도 점수를 **attention 질량**으로 바꾸는 것이고,
그것으로도 곡선이 안 움직이면 이 방향의 감축 여력이 실제로 작은 것이다.

**이 모델의 관점에서 왜 그럴 수 있는가**: 12-2 표를 보면 `k=8, r=0.9` 의 연산비는
1.08× 뿐이다. **얻을 수 있는 최대가 8 %인 설정에서 품질을 42 % 지불하고 있다.**
의미 있는 감축(2배)은 `r ≤ 0.3` 이 필요한데, 그 영역의 품질은 P2 곡선에서
이미 붕괴한다. **트레이드오프가 성립할 여지는 곡선의 모양을 바꿔야만 생긴다** —
즉 더 나은 중요도 점수이거나, 중복이 많은 입력(긴 문서 QA)이다.
