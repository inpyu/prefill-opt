# 측정 환경과 방법론 — 이 클러스터에서 성능을 재는 법

**상태: 지속 갱신**  ·  작성 2026-08-24
관련: [16-derivepp.md](16-derivepp.md), [19-sharedpack-implementation.md](19-sharedpack-implementation.md)

> 여러 문서에 흩어져 있던 **측정 환경의 제약**과 **반복해서 틀린 방식**을 한곳에 모은다.
> 새 실험을 설계하기 전에 이 문서를 먼저 읽는다.

## 1. 하드웨어

### 1.1 클러스터

| | |
|---|---|
| 노드 | Raspberry Pi 5 × 8 (root 포함) |
| 메모리 | 4 × 16 GB + 4 × 8 GB |
| CPU | Cortex-A76 4코어, L1D 64 KB, **L2 512 KB/core, L3 2 MB 공유** |
| 최대 주파수 | 2.4 GHz |
| governor | `ondemand` — 단 부하 중 실효 주파수는 **이미 2.4 GHz** (§16 §7.15) |

노드별 보드 리비전과 RAM 이 다르다(104 는 Rev 1.0/8 GB, 113·166 은 Rev 1.1/16 GB).
**공변량으로 기록하되 성능 차이의 원인으로 귀속하지 않는다** — §16 §7.15 에서
연산자별 순위 역전이 재현되지 않았다.

### 1.2 네트워크 — 10배 비대칭

    스위치 A 군 내부   115.7 MB/s
    스위치 A ↔ B 군     11.7 MB/s      ← 100 Mb 업링크

`STAGE_NODES = root, 113, 166, 191 (A군) / 103, 94, 104, 54 (B군)`

**`N≤4` 는 A군만, `N=8` 은 B군을 포함**한다. 따라서 `N` 축 실험은 순수 `N` 효과가
아니라 **deployment plan `(N, π)`** 비교로 표기해야 한다.

공식 distributed-llama 가 정확히 이 업링크에서 붕괴한다(`N=4` 0.44× → `N=8` 0.12×,
§16 §7.16).

### 1.3 ⚠️ 저장장치 — SD 카드 불량 섹터

    /dev/mmcblk0p2   477 GB SDXC 한 장뿐.  SSD/NVMe/USB 없음
    OS · 모델(6.32 GB) · 빌드 · 로그가 전부 같은 카드에 있다

**증상**

    mmc0: Card stuck being busy! __mmc_poll_for_busy
    I/O error, dev mmcblk0, sector ..., op 0x0:(READ)

부팅별 발생 횟수:

| boot | Card_stuck | signal_warn | IO_error |
|---|---|---|---|
| b-3 | 13 | 30 | 17 |
| b-2 | 13 | 243 | **131** |
| b-1 | 8 | 46 | 16 |

**우리 실험이 원인이 아니다** — I/O error 124건이 **부팅 첫 초**에 집중되고,
`op 0x0:(READ)` 실패이며(쓰기 마모라면 write 에러여야 한다), b-3 부터 이미 존재한다.
매체의 불량 섹터다.

**다만 촉발 요인이다.** 매 실행마다 6.32 GB 모델을 읽으므로, 하루 150회면 약 1 TB 다.
`RequiredMemory 6.35 GB + 파일 캐시 6.32 GB = 12.7 GB / 15 GB` 라 페이지 캐시가 매번
축출되어 재읽기가 발생한다.

**실험 설계 시 회차 수를 SD 읽기량으로 환산한다.**

    anchor 17회 = 107 GB      부담이 크다
    10회        =  63 GB      현재 타협점

모델 무결성은 확인했다 — `sha256 = f03abb7c...` 일치(§19). 기존 측정은 유효하다.

**권고**: SD 카드 교체가 근본 해결. 그다음 USB SSD 로 모델·OS 이전.
SSD 만 추가하면 OS 영역 손상이 남아 crash 위험이 계속된다.

## 2. 측정 편차 — 이 기기의 실제 노이즈

### 2.1 층위별 편차

| 측정 | 편차 | 근거 |
|---|---|---|
| op profile (op 시간 직접 합) | 작음 | §19 §4c |
| microbenchmark (bench_*) | ±2% | best-of-N |
| **E2E `prefillMs`, wave on** | **최대 51%** | §19: 26,722 / 30,365 / 40,370 |
| `S=7212` E2E | range 38% | §16 §7.12 |

> **E2E 성능은 anchor 설계 없이 판단하지 않는다.**
> 단일 측정으로 판단했다가 철회한 것이 오늘만 네 번이다.

### 2.2 anchor 설계 (검증된 방식)

    warm-up 폐기 (단일 노드는 3회까지 필요할 수 있다 — §16 §7.17)
    A, B, A, B, A   정순
    B, A, B, A      역순

보정은 **기하평균 paired ratio**:

    R(B) = √(T_A,전 · T_A,후) / T_B

세션 드리프트가 곱셈적이므로 선형 보간보다 일관된다.

### 2.3 ⚠️ 두 설정의 비율은 같은 세션 안에서 잰다

`B` 축에서 이 함정에 빠졌다(§16 §7.18).

    B=32 곡선과 B=16 곡선을 **다른 세션**에서 재고 나눔  →  1.013×
    같은 세션 anchor 교차                                →  1.140×

`B=32` 측정이 세션에 따라 11% 흔들리는데, 곡선을 따로 재서 나누면 그 드리프트가
그대로 비율에 들어간다.

### 2.4 세션 오염

    실패한 실행(NET_TIMEOUT, crash) 다음 세션은 anchor 가 38% 흔들렸다
    → 실패가 나오면 세션 전체를 폐기하고 재시작한다
    → 데이터는 지우지 말고 invalid_session 으로 분리 보존

## 3. 계측 도구

| 도구 | 용도 | 주의 |
|---|---|---|
| `DLLAMA_OP_PROFILE=1` | op 이름별 시간 | **`--stage-timing 1` 필요**. wave off 여야 집계됨 |
| `[PREFILL ONLY]` 섹션 | prefill-only op sum | decode 가 섞이지 않은 값 (§19) |
| `DLLAMA_DUMP_LOGITS=<path>` | 정확성 reference | prefill 종료 후 f32 raw 1회 |
| `DLLAMA_SHARED_PACK=0/1` | 동일 바이너리 A/B | 그래프만 전환, 커널·순서 불변 |
| `prefill_bench/snapshot.sh` | artifact 고정 | manifest·hosts·checksum |

### 3.1 ⚠️ production 커널을 벤치한다

    ggml_gemm_q4_0_4x4_q8_0   production (block_q4_0x4 × block_q8_0x4)
    llamafile_sgemm           production 이 아니다 — 2.6배 느리다

WCEP 에서 후자를 baseline 으로 삼을 뻔했다(§17 §7.5.1). 그랬다면 결과가 2.6배
좋아 보였을 것이다.

### 3.2 정확성 reference

    N=1  (B=16, B=32 동일)   8b8178a50a97
    N=8  (B=16)              c52e50e37e65

`N=1` 과 `N=8` 이 다른 것은 **기존 시스템 특성**이다(q80 stage-boundary 양자화 왕복).
gate 는 **항상 동일 실행 구성끼리** 비교한다.

`B` 불변성(`B=16` ≡ `B=32`)은 현재 구현의 성질이며 **구조적 보장이 아니다** —
커널이 `B` 별로 다른 경로를 쓰면 달라질 수 있다.

## 4. 반복해서 틀린 방식

| 실수 | 횟수 | 대응 |
|---|---|---|
| `pgrep -f`/`pkill -f` 가 자기 명령줄 매칭 | 5 | `-x` 사용. **정리와 실행을 다른 명령으로 분리** (브래킷 트릭도 같은 줄에 대상이 있으면 실패) |
| `\| head` 가 SIGPIPE 로 실행 중단 | 2 | 긴 실행은 파일로 받고 나중에 grep |
| 소표본 관측을 일반 결론으로 확대 | 4 | anchor 설계 + 효과크기 사전등록 |
| 회계 단위 불일치 | 3 | baseline 과 최적화가 같은 단위인지 확인 (곱/덧셈 혼용, batch 축 누락, epilogue 포함) |
| 파일 포맷 오인 | 2 | **검증기를 먼저 쓴다.** byte 크기만으로 부족 — 이름·shape 를 loader 와 대조 |
| 두 프로젝트 자원 충돌 | 2 | 바이너리 이름과 **포트**를 분리 (dllama/dllama_up 이 9998 공유) |
| 교락 미분리 | 2 | 조건을 하나만 바꾼 대조 실험 |
| 기존 스크립트 경고 무시 | 1 | 새 시스템은 운영 스크립트를 먼저 읽는다 |
| 동시 실행으로 자기 실험 오염 | 1 | `flock` 배타 실행 |

### 4.1 가장 값비쌌던 것

**검증기를 나중으로 미룬 것.** WCEP Phase 1a 를 세 번 무효화했다
(회계 단위 → embedding 타입 → FFN 순서). 파일 포맷을 파싱하는 코드는
**검증기를 먼저 작성**해야 한다. 파싱이 맞다는 증거 없이 나온 통계는 전부 무의미하다.

### 4.2 가장 유용했던 것

**사전등록.** 효과크기와 kill criterion 을 결과 보기 전에 고정한 덕분에
WCEP(6~10주 예정)를 하루 만에, QCFuse 를 반나절 만에 종료했다.
"45.7% 절약" 같은 큰 숫자를 matched null 없이 성공으로 읽지 않을 수 있었다.

## 5. 운영 체크리스트

새 측정을 시작하기 전:

    [ ] flock 으로 배타 실행 — 다른 벤치와 겹치지 않는가
    [ ] 워커 바이너리 md5 일치 — 커널/계측을 고쳤으면 redeploy
    [ ] warm-up 폐기 회차 포함
    [ ] anchor 교차 배치 (비율을 주장한다면)
    [ ] 실패 시 세션 폐기 규칙
    [ ] 회차 수 × 6.3 GB 가 SD 에 감당 가능한가
    [ ] 출력은 파일로 (파이프 금지)
    [ ] 값이 나올 때마다 레포에 기록 (/tmp 를 한 번 잃었다)
    [ ] 종료 후 snapshot.sh 로 manifest·checksum 고정

공식 dllama 를 쓸 때 추가:

    [ ] 워커는 dllama_up (md5 1125dfb9). /home/ubuntu/dllama 는 prefill-opt 빌드다
    [ ] 워커는 root 세션 하나만 처리하고 종료 → 매 실행 직전 재기동
    [ ] TCP 프로브 금지 — 프로브가 세션을 소비해 워커가 죽는다
    [ ] 포트 해제는 워커 로컬에서 ss 로 확인
